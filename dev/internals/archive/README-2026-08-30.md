# war-dogs

war-dogs is one pi extension that turns pi into a full-screen coding cockpit. It rides on pi's own agent loop and never changes what that loop does; it adds tools and re-skins what you see. On, you get: a scrollback **pager** that becomes the reading surface; in-process **subagents** with a live station and per-run chat views; **WebFetch** (fetch-and-render, typed verdicts) and a direct Kimi **web search**; unified **image attachments**; the bundled **MCP adapter** (pi-mcp-adapter); and a re-skinned HUD — mascot banner, blue pulse spinner, re-coloured footer, subagent activity strip.

It is a copy-pasteable folder, not a package. Drop it into `~/.pi/agent/extensions/`; pi's jiti loader runs it with no build step, and everything it needs travels in `node_modules/`.

One principle governs the whole thing: **war-dogs is all or nothing, and OFF BY DEFAULT.** You activate it by adding `"war-dogs": { "enabled": true }` to `settings.json` — copying the folder in is not enough. On is the full experience. Off is pi exactly as `pi --no-extensions` renders it — the screen, the palette, and what the model is told, byte for byte — and that is not emulated but STRUCTURAL: when war-dogs is off at boot it registers NOTHING with pi (no tools, no commands, no renderers, no MCP, no theme), so there is nothing to diverge. There is no partial mode; the only customisation is editing this folder or building on top of it.

How to read this file: **using it** comes first (get going, the screen, keys, subagents, tools, the switch, configuration, portability, limits, troubleshooting); **how it works** next (layout, mechanics, pi's session lifecycle); **maintaining it** last (extending, debugging instruments, the upgrade contract, and the ledger of load-bearing decisions — every entry there was paid for with a real bug, and overturning one takes a demonstration, not an argument).

# Using it

## Get going

**Install, then activate.** `cp -r war-dogs ~/.pi/agent/extensions/`, then add `"war-dogs": { "enabled": true }` to `settings.json` — war-dogs is OFF until you do, and an off war-dogs is inert (pi is exactly stock). From a `git clone`, run `npm install` in the folder once (`node_modules/` is gitignored; the folder's `.npmrc` sets `legacy-peer-deps`, exactly as pi's own package manager does). If you had installed pi-mcp-adapter as a pi package before, run `pi remove npm:pi-mcp-adapter` — the bundled copy is the one that should run (until you do, war-dogs yields to yours and says so; see "MCP").

Optional, in `settings.json`: the feature keys under `war-dogs` tune the bundle and `war-dogs.theme` names the palette ("Configuration"). Do not set pi's own `"theme"` to a war-dogs palette by hand: `/war-dogs on` writes it there for you (your theme saved under `war-dogs._prevTheme`) and `/war-dogs off` puts yours back — set by hand it would be your OFF palette too.

```json
{ "war-dogs": { "enabled": true, "theme": "canopy" } }
```

**The stance (2026-08-25, maintainer, for going public):** war-dogs is centered on the maintainer's stack — Kimi-first, Chrome-assumed — and public as a gift, not as a neutral product; the GUIDE states this up front, every divergence degrades with an honest line, and "everyone" is welcomed but never the design center. Feature work is judged against the maintainer's needs first.

**The user guide.** `GUIDE.md` beside this README is the end-to-end USER manual — every affordance, edge case and configuration key, in user-facing voice (this README is the maintainer's book). It states facts this README owns, so keep the two true together: a behaviour change that lands here lands there in the same session.

**First ten minutes.**

1. Run `pi` in a project. The mascot banner — the box-soldier beside the WAR DOGS word art, its helmet in the theme's accent and its face in the identity hue — sits at the top with two lines beside its face: `v0.1.0 (📦 Pi v0.83.0) · Model: Kimi K3-256K (max)` (war-dogs' version — package.json's `version`, read once at load — pi's, then the model and thinking level; versions and values muted, `Pi` white, `Model:` the accent) and `Session: <id>` — `<id> (<name>)` once you `/name` it, `· not saved` under `--no-session` (2026-08-23, maintainer; the cwd left the banner — the footer carries it). The transcript is now the pager, a full-screen overlay that owns scrolling, folding and selection; the bottom is pi's own editor with the re-coloured footer under it and the activity strip below the footer (2026-08-27, maintainer; it sat above the editor since 2026-08-20 — the strip rows ride the footer's own render output now, since pi has no belowFooter widget placement and the pager already composites the footer; zero rows when nothing runs: agents, background bashes, and an /ask in flight as a third row in the same style). With MCP servers configured, the footer also carries `MCP: …` (the adapter's `🔌 MCP: …` status, its emoji dropped and repainted `dim` by the footer — quiet, and one emoji fewer for pi-tui to mis-measure) — right-aligned on the path line, above the model status; when path and status cannot share the row the status takes the next line, still right-aligned (never a third permanent row).
2. Scroll with the wheel or PgUp/PgDn. Every tool call rests as one dot-marked sentence: click it to open its evidence, click again to fold. `ctrl+o` expands or collapses everything.
3. `alt+s` opens the **station** — the subagent family tree of this session, each run with its task line (`❯` + one row, ~72 characters cut on a word, screen-relative, all dim — the glyph is punctuation here, not the prompt voice) and ONE configuration line of VALUES in muted — a self-representing value stands alone (`kimi-for-coding`, `background`, `9 tools`, the run id), one that is not carries its type (`depth 1`, `low effort`, `no timeout`, `inherited cwd`, `no extensions`); CTRL+HOVER or the arrow selection (which scrolls the WHOLE block into view) unfolds it into the FULL line — a ctrl+click toggle was added and rolled back the same day (redundant; note ctrl pressed with the pointer already resting is invisible until the pointer crosses a cell: a modifier press alone sends no terminal event) — — the tool names and extension lists in dim parentheses, then cwd, extensions and the run id — as one flowing text WRAPPED to the screen, continuations at the text column (2026-08-22c: fixed-width rows clipped on a small terminal; the task line cut is screen-relative too); a blank row with the rail through it before every nested run, elbows `└──`/`├──`; DRAG selects text here like the main view (press anchors, drag highlights, right-click copies from the drawn rows) and a click that never dragged opens the run on release; the tree's rail runs through those rows to the next elbow, so a child's `└─` connects); the run under the selection or the mouse opens the full block: every tool name the child was actually built with (`snapshotSession`, live runs included), exclusions, cwd, extensions, run id (three lines per run at rest read as a wall — 2026-08-22). `ctrl+s` goes back a level.
4. Ask for a subagent in plain words ("use a subagent to count the .ts files in this repo"). Its tree stays on the surface while it runs. Click its run row — or `↑`/`↓` then Enter in the station — to open its own chat view: the palette turns identity-blue (the `visor` theme) so a child conversation never reads as main; type to talk to that child; `alt+up` pulls its queued messages back into the editor; `ctrl+s` returns.
5. `/mcp` opens the adapter's panel (`/mcp setup` writes a server config if you have none).
6. `/war-dogs off` — the screen becomes stock pi, MCP included; `/war-dogs on` brings it back. The toggle is refused while anything is still working, on purpose.

**Ask an LLM about it.** `dev/SYSTEM-PROMPT.md` is a system prompt that makes any capable model proficient in pi and war-dogs — for a quick question, a screen that looks wrong, "is it still fine after `pi update`?", a new tool or feature, a change to an existing one, running it on another platform, or a design conversation. Give the model that file as its system prompt (and file access to this folder and to pi's install, or paste this README when it has none) and ask whatever you like; the prompt tells it where the truth lives, how to establish facts by instrument rather than by reading, and which principles never bend.

Runtime requirements beyond pi: a configured model (subagents and the WebFetch scout use it); a system Chrome/Chromium on `PATH` for WebFetch's render tier (nothing is downloaded — the static tier works without it, the render tier degrades to a typed error); `poppler` (`pdftotext`/`pdfinfo`) for PDF text (optional — absent, a PDF fetch reports an error status). Node ≥ 22.19 (`engines` in package.json).

## The screen

The resting screen renders the CONVERSATION, not the API traffic. Two kinds of thing exist and are told apart at a squint by glyph and colour tier, never by spacing (one blank line before every beat, always).

**Voice** — the model's narration: `●` in the gutter, text at the bright tier. An errored or aborted turn turns the dot red; state lives in the glyph column.

**Your prompt** — rows on the theme's `userMessageBg` box, one bg-painted empty row above the text and one below (the box breathes; the round-20 hug was retracted 2026-08-18), `userMessageText` white, and the `❯` in `wdPrompt` (blue `#79b4f2` canopy, purple `#b7a1e3` dune, steel `#82aacd` oxide, amber `#e3b566` inside a run view on visor) — a voice of its own.

**Attachments of a prompt** hang right under its box (2026-08-22): a SKILL invocation (`/skill:name words`) draws the box first — reading `/skill:name words`, the line as typed, the `/skill:name ` lead restored in front of the words since 2026-08-23 (maintainer: the box is the typed line, the way the `[^image N]` refs stay in it; pi splits the block off, so the lead is neighbour-derived and rides the render SIGNATURE — `renderSubCached(…, lead)` — never the component; pretty only, the wire stays pi's verbatim user text) — and the skill under it as an attached row — `⎿  [skill]` collapsed, concise and in the identity blue like the image rows; OPEN its head reads `user used skill <name>` in the lit tier (the user invoked it — maintainer, 2026-08-22b); ctrl+click the exact `<skill …>` wire (pi emits the skill component before the user component with a Spacer between; the pager pairs them across the spacer, statelessly on both sides so the prefix cache may cut between them; a no-args `/skill:name` gets a box too since 2026-08-23 (maintainer: every skill invocation is a prompt) — SYNTHESISED from the skill component (`skillBox` in `surface.ts`), reading `/skill:name`, what the user typed, with the same `⎿  [skill]` row under it. The box is built from the SKILL, never from the user component that may follow it: pi creates that component only for words after the block, and with no words it exists only because war-dogs' stamp is "words" to pi (it carries the stamp alone; a pre-2026-08-21 transcript has none at all) — so a box keyed on it would vanish with the stamp. The stamp-only component emits nothing; the synthesised box has no wire of its own, the `[skill]` row carries the block's. Before this a bare invocation stood alone as an act and clustered with the model's leading thinking — `used 1 skill, thought 1 time` with no prompt in sight) — and every image reference as `⎿  [^image N]` in the identity blue (concise — maintainer), CTRL+click opening the file in the system viewer (xdg-open; a missing file says so); the hover light covers the REF, never the `⎿`. The same `[^image N]` in the INPUT BAR is ctrl+clickable and underlines under the mouse like a link, resolved through the attachment store the submit pipeline reads. An in-terminal block-art preview (half-block cells, decoded through pi's bundled photon) was built and DROPPED the same day: at cell resolution a screenshot's text is unreadable, and screenshots are what gets attached — the viewer is the honest view.

**Machinery** — tool acts. Collapsed, each is exactly one line and, at rest, carries no gutter glyph at all; the dots (green success, red error, presence-blinking while running) are a working-only signal. Forms: `executed bash • find, wc`, `Read util/shell.ts (214 lines)`, `Wrote 6 lines to notes.txt`, `Edited x (+3 −1)`, `Fetched github.com — ok · ~8k tokens`, `Searched "q" — 6 of 11 results`, `started adhoc • tiny echo · 5s`, `called mcp list_files @ playwright` (the adapter's gateway tool: `calling`/`called`, `searching`/`searched`, `describing`/`described`, `connecting`/`connected`, `listing`/`listed`, `running`/`ran <action>`, `checking`/`checked mcp status` — its args JSON is evidence behind the fold, not a restatement), `ran mcp script (5 lines)` (the adapter's `mcpScript` tool — the JavaScript the model handed it is the evidence, highlighted as JavaScript and never cut; since 2026-08-20, before which it rested as the adapter's raw `mcpScript` card with its args JSON cut at 1500 chars and its output lost), `called mcp browser_tabs @ playwright` (an adapter DIRECT tool, `<server>_<tool>`, named from its definition's `MCP: <tool>` label — `mcpDirectParts` in `surface.ts`; the adapter's PER-SERVER gateway `mcp__<server>` — the tool in its args, the server in its name — reads the same way since 2026-08-29, when the real-model drive showed it as `called mcp playwright @ mcp_`), `background bash "title" finished in 61s (exit 0)` and `background subagent "title" (agent) finished in 66s` (the delivered results of background work — the state word bolds and is the sentence's verb), `executed bash in the background • sleep` (a `background: true` call, or a command whose last segment is backgrounded with a shell `&` — the latter is silent for good: pi's bash has no background mode, the shell returns at once, the child runs on detached and its output never comes back; the former delivers its output later, see Mechanics). Lowercase; present tense while running; numbers live in the sentence; durations only when ≥ 0.1s; an error paints the whole sentence red. The raw command, path or url never rests on the surface — a collapsed act is the sentence alone, no `⎿`, ever. The bash noun is a phrase, never a count: the model's `description` argument, else the program list `util/shell.ts` derives, and that derivation must not invent nouns (`2>&1` is fd plumbing, not a background `&`; heredoc bodies, `$(…)`, `((…))`, function headers and comments yield nothing).

**Thinking** is machinery. At rest it is one row at `wdCall` (`thought for N lines`); its OPEN text is `thinkingText`, italic, `muted` since 2026-08-22 (maintainer: "make it dim"; it had been the evidence tier since 2026-08-18, and the low white before that); the working window's moving tail and a thinking row resting inside a prose beat stay the low white (the working leak is quiet), with `◐` in the gutter in both fold states (`… (N lines total)` when cut); a one-liner that fits is complete and never changes. pi's `hideThinkingBlock` is respected — the hidden label is rendered as machinery too, so the prose `●` still lands on the model's answer — and child views follow main's setting.

**pi's own beats** are acts in this grammar, not foreign tools: a `!command` rests as `ran <programs>` (`running …` live, red on non-zero exit) and clusters as `ran N commands`; a `/compact` summary as `compacted 120k tokens of context`; a `/tree` branch summary as `branched at message N`; a skill invocation as `used skill <name>` (always hanging under its prompt box since 2026-08-23, so it no longer clusters; the `used N skills` verb stays for a transcript shape that produces a bare one; ctrl+click shows the exact `<skill …>…</skill>` block the model received) — its evidence is the skill text as the model got it, RAW and markdown-highlighted in the field palette, never pi's markdown render or its `customMessageBg` card (which leaked into the working window as a blue box). pi's own `(ctrl+o to expand/collapse)` hints are stripped from call and output rows: folding here is a click on the sentence, and `ctrl+o` is all-or-nothing.

**Clusters.** Consecutive machinery beats — errored acts, thinking and settled subagents included — merge into one summary beat (pi's own ERROR turns — a provider or transport failure with no text of the model's own, `Error: 429 …`, `Error: Connection error.` — are an act kind of their own since 2026-08-22: they cluster only with each other, a solo one IS its line — no summary row, no control — several read `errored N times` whose members neither light nor open (nothing to open), all red; a turn with partial prose plus an error stays a voice beat with the red dot): `thought 2 times, executed 2 bashes, called 1 mcp · 1 failed` (a solo thinking beat reads `thought for N lines`; `mcpScript` counts as `ran N mcp scripts`, every other unknown tool as an mcp; a delivered background result counts as `finished 1 background bash` / `received 1 agent reply`; every verb bolds). When the turn settles and its machinery folds into clusters, the new cluster headers FLASH (the ~½ s whole-row invert of the collapse-return) so the eye sees where the working rows went (2026-08-20, maintainer); a cluster that has already scrolled off-screen flashes unseen — the settle never moves the view. A batch of one shows the same phrase, and its click opens the act itself. Only prose, your prompt, an info/box beat, a still-running act or the working window separates clusters; a voice message's *leading* thinking splits into its own beat so it clusters with the acts around it. The header carries no glyph and wraps at word level via pi's `wrapTextWithAnsi` (1-column lead on continuations, never truncated). Open, the header is lit with its members tight below — a dim `⎿` on every member (first-only was retired 2026-08-18), member text two columns in, unbold; a collapsed thinking member is its label, expanded it opens its text under a `⎿`, muted italic. Hovering any row of a wrapped header lights all of them. Folding something whose head row is off-screen returns the view to it and flashes every row the folded beat now occupies for ~½ s — a working act's sentence plus its snippet, both rows of a wrapped cluster header (2026-08-20; the head row alone under-marked both); a fold whose head is visible — including one the shrink itself pulls into view — moves nothing and flashes nothing. A FOREGROUND subagent clusters once its whole run *family* has settled; while the family is live (any depth) it stays on the surface with its tree. A BACKGROUND launch clusters at the turn's settle like background bash — its call is a receipt, the act is done when the receipt lands; the strip is the live indicator and the delivered `subagent-result` carries the duration (2026-08-20, maintainer; until then a live background family kept its ticking tree on the surface). Tools outside our grammar (MCP) additionally go red on a *structural* error shape — a leading `Error`/`### Error` line, or a top-level JSON `ok:false`/`error`/`isError` — as does a scout run whose every verdict failed; visual only, the result the model sees is untouched (`errorShapedResult`).

**Working vs static.** Between `agent_start` and `agent_settled` the machinery after the last user prompt neither clusters nor hides: each collapsed act leaks a snippet — evidence-shaped (`⎿`, low white) but with no field background, so a deliberately opened panel stays distinct. Budgets: default 5 rows from the call (bash: command first, then output, never the output tail); write 15; edit the full diff; read/webfetch/kimi-websearch sentence-only; unknown tools and the `mcp` gateway their call's args only; the subagent's snippet is its verb plus run tree; a delivered background result (`bash-result`, `subagent-result`) leaks 5 rows of its text under a `⎿`, with the green glyph — the delivery itself starts or joins a turn, so the model is working when it lands. Working thinking is glyph view — no label, no `⎿`, no field: the `◐` carries the identity, a 5-row window of its non-blank text shows plain, WRAPPED (a still-streaming block shows its moving tail — the last rows of the last lines — a finished one its head; `… (N lines total)` whenever anything is out of view), a click opens the full text and grows it live. On settle the snippets vanish and the turn's machinery clusters; history stays clustered even mid-turn.

**The fold.** Hovering a sentence (a foreign tool's resting call line too, and a subagent tree row in either fold state — its click opens the run) lights it to the text tier, span-precise; a red (errored) row lights to a lifted red — each channel a third of the way to white — never to white, so a failure under the mouse still reads as a failure; an open panel's head is already lit and carries NO hover handle at all (2026-08-22, maintainer — the light substitution brightened its dim tail; a click there folds, so there is nothing to preview). Clicks that add are text-gated — the click must land on the lit text; clicks that remove are row-wide — anywhere on an open panel folds it. In the WORKING window (2026-08-20, maintainer): a collapsed act's sentence AND its leaked snippet rows are ONE control — they light together and each row is clickable over its own text, like the working thinking window; a sentence-only act (read/webfetch/websearch) keeps the sentence as the control. A settled act's snippet is a control whether or not it hides rows (2026-08-28, the maintainer: opening is for readability — the panel's field, its syntax — not only for hidden rows; until then a snippet that hid nothing "neither lit nor clicked", the rest rule for a fitting one-liner applied to the working view — retired, see Load-bearing; verified on the real model 2026-08-29: `echo hi` in a working child view, `hit=1`, `ev=toggle`); a FINISHED thinking block that fits its 5-row window whole is the one complete form that stays inert. While the token stream is still running — a thinking block still being written, an act whose verb is still `-ing` — it lights and opens whatever it has shown so far (maintainer: "if it's still streaming we can expand it"), and the open panel grows live. An EXPANDED working thinking text does not light either: open is already lit, a click anywhere folds. Expanded is one raised panel: the head row sits on the field (`toolPendingBg`, `toolErrorBg` when failed) at the bright tier — open = LIT, nothing more: the verb keeps the bold it has when collapsed, the rest of the sentence never bolds (a full-bold open head was tried and retracted by the maintainer); hover previews the light a click pins — and the evidence opens with a dim `⎿` on its first row, followed by two spaces before the evidence BLOCK's left edge (`⎿  $ command` for bash, `⎿  Prompt` for the subagent, `⎿  1 ┃` for a short read); a right-aligned line-number gutter (read/write, and edit's `sign + number`) keeps its own alignment padding inside that block, so line 1 of a 111-line file reads `⎿    1 ┃` — the block edge is where the rule holds, not the first digit (a left-aligned gutter with a fixed first-digit column was tried and retracted: ragged numbers read worse than the drift), everything below aligned under it. One field-painted empty row above the head and one below the last evidence row — the panel breathes inside its own field (an open thinking block too; never in the working window); inside an open cluster an expanded member is padded the same way, the first one included, and two adjacent expanded members on the SAME field share the row between them, so two empties never lie together — a red (error) panel above a green one keeps both rows, each in its own colour. webfetch/websearch raw JSON args stay hidden (they restate the sentence); an MCP call's args — JSON by protocol, for the gateway and every direct tool — are rebuilt from the SOURCE args with the adapter's own formatter (`formatJsonish`: `JSON.stringify(v, null, 2)`, 1500-char cut) and highlighted as JSON in the field palette, then wrapped ANSI-aware — highlighting the already-wrapped display rows lost every continuation's colour. Every highlighter output carries an open style across the row break (`carrySgr`): a docstring's middle rows are string-coloured. A padding row is part of the panel's fold range (a click on the breathing room folds). A cluster member's text-gated range is clamped to the width of the row actually drawn — a collapsed thinking member shows its label, not its text. OUTPUT is plain and low: bash's stdout and an MCP result keep pi's `toolOutput` tier on the field; the evidence tier is for what our own renderers paint (read/write/edit bodies, the bash command line).

**The wire view** (2026-08-22, maintainer: "what the user reads is clean; full transparency on demand"). The pretty surface hides the model's BOOKKEEPING: the trailing `[timestamp: …]` stamp everywhere it lands (util/stamp.ts is the model's clock; the UI shows relative times), the provenance first line of deliveries, and webfetch's `[webfetch: …]` head line (it restates the sentence). Degradation and truncation notices are NOT provenance and stay — `[Read lines …]`, `[answer truncated: …]`, `… [N lines omitted …]` tell the reader the pretty view is incomplete, and hiding them would make it lie. Run ids and a prompt's attachment footer (`---` + `[^image N]: path` defs) are wire-only since 2026-08-22 (maintainer): the station lists ids, and the `[^image N]` refs in the words are what the user typed. In exchange, CTRL+CLICK on a tool act, a delivery or the prompt box (anywhere that is not a path or URL — token-open wins) flips that ONE beat to the VERBATIM model-facing text — a tool's result text blocks (write/edit show `Successfully wrote …`, exactly what the model read, never the pretty body), the delivered message of a background result (provenance line, run id, stamp), the submitted prompt (stamp and attachment footer); ctrl+click again flips back, and on a collapsed act it expands straight INTO wire. A panel in wire view says so with a dim `· wire` on its head; the prompt box's visible stamp is its own tell. Per beat and STICKY — there is no global wire mode; `ctrl+r`'s raw-source view stays the whole-surface escape hatch. A still-running act has no result yet, so the gesture arms at settle. (A visible `raw`/`pretty` head-row button was built and RETRACTED the same day — maintainer: looks weird; and shift+click can never serve here — the terminal keeps shift for native selection and the report never reaches the pager.) Under `pager:false` there is no wire view, and the stamps of stock-rendered results (bash, MCP) stay visible there — only war-dogs' own renderers (read/webfetch/websearch) subtract theirs.

**The agent tool's `run`** is a uniform act: at rest one `started agent • title · elapsed` line (NO elapsed while the run is still working — every run replies by delivery, so the resting row never ticks; open it and the panel's tree shows the live clock); live, `starting`/`started agent` with the run tree below (the other actions — message, ask, wait, status, stop, list — rest as sentences: `messaged researcher • audit the cache`, `held for 2 replies`, `listed agents`) — `⎿`-led, depth by indent, root first, identity blue living in the tree so it never clashes with the prompt colour; expanded, one panel with the tree keeping its resting x-position and, since 2026-08-22 (the maintainer's sketch), the PROMPT under a `⎿` in the evidence tier and the RESPONSE nested one step deeper under its own `⎿`, muted, the run id last — no Prompt/Response headings; the pager builds both chunks from source (`args.message`, the result text), like the MCP args (the old `├─`/`│`/`└` trunk leaked its rail onto MCP JSON args — it does not come back). A `run` has no Response when its call settles — the tool text is a receipt, not the reply — so its nested chunk is the receipt (`Started "title" (name).`, or `Queued "title" (name) behind N working agents.`; upright since 2026-08-22). The id is on the wire only — text, blank line, `[agent stats: …]`, `[agent id: …]` (the LABEL is what stopped models quoting the id back, 2026-08-18; `splitTrailer` still reads every older shape) — and since 2026-08-22 the pretty surface never draws it: the station lists every run's id, and ctrl+click shows the wire. The reply itself arrives later as an `agent-result` message — which pi hands the model as a plain USER message with the content verbatim (`convertToLlm`: role `user`, no marker), so its first line says what it is: `[agent result, delivered by the agent tool; agent-authored, not typed by the user]` (bash's deliveries carry the matching `[background bash result, …]`; older transcripts carry the pre-rename `[background subagent result, …]` and `[Background … result — …]` shapes and the parsers accept them all; the parsers skip the line, the model reads it) — and in the pager it is a foldable ACT like every tool (`ownResultKind` in `surface.ts`): collapsed to one sentence, `agent "title" (name) finished in 66s` (state word bold; `timed out after` / `was stopped after` / `errored` paint red), the answer behind the fold under a dim `⎿` (no run id — wire-only), a 5-row snippet inside the working window, and — settled — it clusters as `received 1 agent reply`. Under `pager:false` the message renderer draws the same sentence-plus-`⎿` shape in pi's scrollback; while war-dogs is off it is pi's stock custom-message box (the renderer returns undefined, pi's fallback). Agent ids are `agent_` + 12 url-safe characters (`[agent id: agent_S56llA5Oo-Dm]`), the shape bash's jobs use (`bash_…`); manifests from before the renames keep their `subagent_…`/`tool_…` ids and resolve the same way. Informational beats (pi status lines, banners) render flush at the terminal edge with their `outputPad` lead sliced off; loaded-resource lists re-flow with a hanging indent; the `✸` turn marker wears the spinner's blue. pi's RETRY indicator (`Retrying (n/m) in Xs…`, amber braille) is repainted on the composited tail as the working grenade in the ERROR red (`retryTint`, 2026-08-20 — a stalled turn is the working pulse gone red; pi builds `RetryStatusIndicator` internally with no frame/colour API, so it is a display substitution like `tintTail`, safe because the tail is composed per frame and never cached); the loader also flips the working indicator's frames red on an assistant message ending in error while the clock runs. ## Agents

The tool is `agent` since 2026-08-24 (the contract is `dev/agent-contract.md`; the drafts before it are in git history; it was `subagent`, and old transcripts render through a toolmap alias). Since 2026-08-25 the DESCRIPTION carries the maintainer's doctrine layer, rewritten 2026-08-27 to draft 10 (`dev/agent-contract.md` Part 1, shipped on review): delegation as how the main session LASTS, errand-versus-worker at recruit time, the copy/own/sequence coordination ladder with worktrees as the copy rung, defining agents as engineering standards saved as named hires, leads and standing orders, ask as extraction/interview/assumption-check, steering demoted to a correction. The named-agents block is ALWAYS present and teaches the file shape with real paths. One call is one ACTION: `run` starts an agent, `message` steers a working one at its next tool boundary or continues an idle one as its next turn (transcript intact — resume and steer are one verb now), `ask` puts a question to it OUT OF BAND (a tool-less `completeSimple` over a snapshot of its transcript, streaming partial included — the agent's work is not interrupted and the exchange is never recorded; the wrapper tells the askee an in-flight tool call is "still running, not failed", because the snapshot serialises one with a synthetic empty result and a live trial showed the askee calling it a failure without that sentence), `wait` holds until an agent is IDLE and returns its latest reply, whoever started the turn — the tool's own runs through their per-turn work promise, a user-chatted turn through a status poll (2026-08-24: keying on the promise alone returned a stale reply during a user-driven turn, demonstrated and fixed), `status` is a read-only look (state, elapsed, last tools, the FIRST ~600 chars of its latest output — the head is the summary; bare `status`, no ids, reports every working agent), `stop` interrupts (the run stays continuable by `message`), `list` shows this session's agents as a tree from the registry. States are working / queued / idle / stopped / error (legacy manifests map at the read boundary); ids are `agent_` + 12 url-safe chars; every reply ends with `[agent stats: …]` (duration, tokens, tool calls, `context 61.0% (156k/256k)` from the settle snapshot — one decimal, the footer's rule (2026-08-29; `Math.round` read 0.9% as "1%") — and, for a lead, a `family` roll-up over SETTLED descendants with `· N still working` when any; `$` only under `agent.discloseCost: true` — 2026-08-27, maintainer: cost serves no goal the model owns) and `[agent id: …]`. `status` carries the same context figure live plus `· compacted N×`; bare `status` LEADS with this session's own window; `list` rows carry `· ctx N%`; a reply whose turn folded the child's context says so in one note line. A `schema` on `run` (parameter-only — the description never mentions it) hands the child a `reply` tool whose parameters ARE the schema; the recorded object is the reply, and a run that never called it says so and appends its prose.

An agent is a real pi `AgentSession` built in-process (~44 ms), on the same `ModelRuntime` as the parent — same auth, provider config and compat flags — with a decrementing depth budget (DEFAULT 0 since 2026-08-24: an agent cannot start agents unless the call hands it depth) and linked `AbortController`s, so stopping any node tears down its subtree. CONCURRENCY is an OWNED budget (`agents/slots.ts`): at most N agents work at once per owner (default 8, `agent.maxConcurrent` ceiling), further runs are recorded `queued` — the receipt says `Queued … behind N working agents` — and start as slots free; a child's cap never exceeds its parent's. There is NO `background` parameter and no foreground mode: every `run` and `message` returns a receipt at once and the reply is DELIVERED — at the receiver's next tool boundary mid-turn (a steering custom message), or as a turn of its own when it is idle (through pi's `sendUserMessage`, so the prompt hook runs — the delivery-turn rule, Load-bearing 2026-08-28), never after the user's Esc: from the interrupt to the next prompt every delivery rides pi's `nextTurn` queue and lands beside that prompt (the interrupted-agent rule, Load-bearing 2026-08-29) — to main in tui/rpc sessions, and since 2026-08-28 to the RUN that started the agent too (`deliverToRun`: every agent receives its agents' replies the way main does). Print/json sessions hold for replies with `wait`, and their description variant says so (`canDeliver`). THE LEAD RULE (2026-08-28, the maintainer's ruling): a run's reply reaches its principal only when its turn ends AND none of its own agents is still working — meanwhile it stays `working` ("waiting on N agents of its own" in status), its workers' replies wake it, and the turn that ends with an idle team is the reply. Its REACH (`reach: team | session`, default team, never wider than the granter's) bounds `message`, `wait` and `stop` to the agents it started; `ask`, `status` and `list` reach everyone, and a child never targets itself or stops its principal. Its transcript is written beside the session that spawned it (`subagents/<sessionId>/<runId>/`); when the run settles its token/cost stats are snapshotted onto the manifest and the session is *released*, so memory is O(runs actually working) and a later message rebuilds it from the transcript on demand. Every message after the task opens with a provenance line naming its sender AND where this turn's final output goes (2026-08-30): `[from the agent that started you • your final output goes back to it: agent_…]` (main: `… goes back to the main agent`), `[from your user • your final output stays with the user]` for a turn the user opens on an idle run, `[from your user • this turn is still the agent's; its final output goes back to it: agent_…]` for the user's steer inside an agent's turn or the follow-up inside an interrupt episode; the task itself arrives unmarked. The bound on delivery latency is the single longest tool call in flight — pi's loop checks the steer queue only between calls. **Deliveries are BATCHED** (2026-08-22, maintainer): every finished background job — bash or agent — enters one queue (`tools/delivery.ts`) and opens a 1.5 s window if none is running; when it closes, everything queued goes out as ONE message. A lone job keeps its own shape (`bash-result` / `agent-result`); two or more become a `background-results` message — its first line composed from what it holds (2026-08-30; it was a fixed string that called two agent replies "2 jobs, delivered by the bash and agent tools"): `[background results, 2 agent replies, delivered by the agent tool; not typed by the user]`, `[background results, 1 agent reply and 1 bash job, delivered by the agent and bash tools; …]`, a powershell job named the same way — then the single shapes stacked, each self-identifying by its sentence and id line, one stamp at the end — so five jobs finishing together are one turn, not five (pi hands parallel tool results over as one batch; this is the same courtesy for background work). The window is never extended by later arrivals, so a trickle cannot starve delivery; `WAR_DOGS_DELIVERY_WINDOW_MS` overrides it (0 delivers at once). In the pager a batch is one act — `2 background results finished` (`· k failed` red; `stopped` when every section is a stop), each result a section under the fold with its own sentence — and clusters as `finished N background results`; the queue is cleared at session_shutdown with the jobs.

**Background bash** is the same shape for a shell command (`tools/bash-background.ts`): pi's bash has no background mode, so war-dogs' bash gains `background: true` — the command runs detached from the turn (Esc does not kill it), the tool returns a receipt with a run id at once (`Started "title" in the background. The output and exit code will arrive in a separate message as soon as the command exits. …`), output is captured (head + tail, capped at 200 lines for the model; when the cap fires the FULL output is saved to a temp file the omission notice names — the omitted middle used to exist nowhere), and on exit a `bash-result` message arrives through the same steer delivery path — in the pager an act exactly like the subagent's delivered answer: `background bash "title" finished in 61s (exit 0)` collapsed, `⎿  OK` behind the fold (the run id is wire-only), a 5-row snippet while the model works, `finished 1 background bash` once clustered, red on a non-zero exit or a signal. The receipt's own panel carries no `Took` row: war-dogs' bash `renderCall` starts pi's clock only for a foreground call, since a receipt returned at spawn is not a timed run (it read `Took 0.0s`). Jobs are SESSION-scoped: any `session_shutdown` (quit, `/new`, `/fork`, `/resume`, `/reload`) kills the running ones, because pi invalidates the `pi` handle a job would deliver through — the receipt tells the model so. While a job runs the activity strip shows it (`╱ 1 background bash · title · 12s`, its own row under the subagents'; the strip sits ABOVE the editor since 2026-08-20 — it was below, between editor and footer — stacking with, never hiding, the attachments widget; its spinner is the classic ASCII line `|/-\` at ~250 ms — and since 2026-08-22 the subagent's own launch/tree spinner turns the SAME line at the same cadence (maintainer: one spinner; the tree's braille frames are retired) — the box-drawing `─╲│╱` was tried and recalled the same day: its glyphs differ in stroke weight per frame, which at 120 ms read as a green/dim blink, not a turn). There is no station for jobs and no way to stop one short of ending the session: a job has no conversation to open and its output arrives whole, so the strip row plus the transcript's receipt and delivery are the whole affordance — a kill control, if it is ever missed, belongs in the existing station as a jobs section, not in a new surface. A child's bash has no `background` at all (its CHILD form — see "What a child gets").

**What a child gets** — deliberately: the parent's model and thinking level, war-dogs' own tools (`webfetch`, `kimi-websearch`, the MCP tools the adapter currently wants active, and `agent` itself while depth remains), the FOUR SKINS built for the child's own cwd (2026-08-22 — read since 2026-08-21): numbered reads, bash with its `description` param in its CHILD form (no `background`: a job's result delivers through the parent's ExtensionAPI, which a child session lacks), edit's atomic-batch wording, every result stamped — one contract for parent and child — plus the project's context files (`AGENTS.md`) — pi's stock `grep`/`find`/`ls`/`powershell` are trimmed from children like from main (`stockTools: true` restores; the trim rides excludeTools on BOTH build paths, since createAgentSession defines them regardless) — a subagent working in this repo must know the same house rules main does. It gets no skills, no prompt templates and no extensions; the tool's description tells the model so. Since 2026-08-30 an adhoc child's SYSTEM PROMPT is MAIN's BASE, verbatim (`prompt/child-base.ts` returns `BASE_PROMPT`; from 2026-08-27 until then it was a generated regrounding, `prompt/child.ts`, "principal" for "user" — the maintainer's ruling retired it: one prose, one voice, and everything that is different about being a subagent lives in the exchange block). A named agent's body still replaces it and a call systemPrompt beats both. REVISED the same day (maintainer: SYSTEM.md is MAIN's): a SYSTEM.md no longer flows to children at all — the user's child default is `SUBAGENT_SYSTEM.md` (`<cwd>/.pi/` when trusted, then `<agentDir>/`), and the EXCHANGE BLOCK — since 2026-08-30 the maintainer's own words: what a subagent is, how the first line of every message reads and what it tells you (who sent it, whether this turn's final output goes back to the agent that started you), and the one-way rule (name what you lack in your final output; `ask` first when it needs no decision from the user, and say so) — is APPENDED to whichever base wins on every path — the memory pattern, because the boundary mechanics must survive any user context engineering and may depend on no base and no tool. ## Tools

**WebFetch** (`webfetch`) returns a typed verdict, never just bytes: `ok`, `login-wall`, `consent-wall`, `js-shell`, `bot-wall`, `paywall-hard`, `not-found`, `error`, … decided the same way on every tier (the static HTTP tier ≈ 300 ms, the Chrome render tier through one shared daemon per machine, `auto` escalating on the gate). Both tiers run the same extractor (HTML → structured markdown with tables, fenced code, resolved links), decode charsets, and cut long pages at a *reading* limit (2000 lines / 50 KB) with the whole page saved to disk and an honest resume instruction. Every degradation is in the TEXT the model reads. The SSRF guard covers every hop on both tiers, DNS-pinned on the static tier, with IPv6 judged as numbers. With `expect` set, a **scout** — a headless `pi -p` (the very pi this runs inside) — fetches and judges candidate URLs and returns verdicts plus the useful content only; configure it under `war-dogs.expect` (profiles, `maxUrls`, `timeoutMs`; the header of `tools/library/webfetch/scout.ts` documents the shape). **PowerShell** (`powershell`, 2026-08-30): pi's built-in, re-skinned under the SAME contract as bash — consistent, not identical: our own self-contained description, the optional `description` sentence the pager shows (`executed powershell • …`, `executed N powershell commands` in a cluster), `background: true` on main (the job runner speaks PowerShell through pi's `getPowerShellConfig`, the same receipt, the same `bash-result` delivery reading `Background powershell "title" finished in Ns (exit 0):` under `[background powershell result, delivered by the powershell tool; not sent by the user]`, the same manifest and the same session-end notice), the child form without `background`, results stamped, pi's `Command aborted` completed with who; pi's execute untouched, snippet and guidelines pi's verbatim. No rg/fd line: that is bash's. ## The master switch

`/war-dogs [on|off]` (`status` reports). war-dogs is **default OFF**; control is SETTINGS-ONLY (one exception, itself a boot state: the `WAR_DOGS_ENABLED` env override — see Configuration): the command WRITES `war-dogs.enabled` into `<agentDir>/settings.json` and then `reload()`s, so every on and every off is a clean BOOT state, not a live apply. This is the whole design: a live apply is what froze the pager (its scroll/fold input is wired at `session_start`, which a mid-session registration misses) and what left rendering residuals (pi cannot unregister). A reload re-runs the extension factory fresh, so ON registers everything at load — before `session_start`, so the pager's input handler is in place — and OFF registers nothing at all. `installOnce()` (all tools, renderers, pager, HUD, MCP, the theme-file install) runs once at load when `bootEnabled()`; a boot with war-dogs off makes ZERO registrations and is stock-in-fact, not stock-by-emulation. The `/war-dogs` command itself is the one thing registered unconditionally (the way back). If settings.json cannot be written the command says so and asks you to edit it and `/reload`.

**Off is stock, verified on three axes** (the screen is only one): `dev/acceptance-test.sh` boots with `enabled:false` and diffs the rendered screen and its palette against `pi --no-extensions`; the prompt-parity check in "Debugging" diffs what the *model* is told (byte-identical); and a boot-off replaying a transcript full of MCP/subagent/bash/webfetch calls is byte-identical to `--no-extensions`, because those tools are not registered so pi renders every call in its own generic form. There is ONE off — the boot state — and it is complete: `/war-dogs off` reaches it by writing the setting and reloading, so there is no live-off residual to reason about (a reload rebuilds every component from the new boot state). The harness also smoke-tests that war-dogs ON boots its surface.

**The toggle is refused while any work is in flight** — the agent streaming, a queued message, a compaction summarising, any subagent run unsettled at any depth — because mid-flight is where incoherent states live. (No runs can be in flight when war-dogs is off, since the subagent tool is not registered then; the guard matters when turning off — a reload mid-turn would abandon it.) The guard lives in the command handler, not the host (pi runs extension commands even while streaming, and `ctx.isIdle()` cannot see a manual compaction). Two gaps are accepted as low-risk: a user `!bash` and next-turn "aside" messages. For the same reason `/new`, `/fork`, `/resume` are refused while a subagent run is in flight (wait, or abort from the station).

**What off leaves behind**: the theme files `installOnce` copied into `<agentDir>/themes` linger (harmless — off reads the same dir as stock, so off still equals stock; a user who never turns war-dogs on never gets them, and Uninstall lists them for a manual `rm`); and the `/war-dogs` command stays in the slash list (the way back on). Nothing else — a reload rebuilds every surface from the boot state, so there is no on-screen rendering residual and no stranded command or skill.

**`ctrl+q` does nothing and there is no live "pager off"**: the station and run views are reached only through the pager. The feature key `pager: false` exists for people who want only the tools/HUD/MCP bundle in pi's own scrollback — a documented degradation, not a mode.

## Configuration

`war-dogs.enabled` (default **false**) is the master switch — war-dogs does nothing until it is `true`. The feature keys under `war-dogs` then decide what "on" includes; all default on: `pager`, `subagent`, `tools`, `toolRenderers`, `banner`, `footer`, `loader`, `attachments`, `theme`, `mcp`, `peers` (2026-08-25: off = no socket, no registry entry, not addressable and not reaching — the peers paragraph leaves the agent tool's description too; agents unaffected), `prompt` (2026-08-26: the inherent system prompt + first-turn session brief — off keeps pi's stock prompt; a user SYSTEM.md wins either way), `canvas` (2026-08-26: the `/canvas` serve command; the pager's canvas act rides `pager`, and `war-dogs.canvas.port` pins the port), `inject` (2026-08-28: the user's injected messages — `inject/SESSION_START.md` once per session, `inject/PER_TURN.md` every turn, global and trusted-project; off reads and injects nothing) (`paster` is honoured as an alias for `attachments`). `stockTools: true` (2026-08-27) restores pi's stock `grep`/`find`/`ls` (and `powershell`): by default war-dogs TRIMS them from the active set and from children — bash with rg/fd covers them, and four overlapping schemas were a per-request tax plus noise in the agent tool's grantable enum; `powershell` is trimmed only beside a present `bash` (on a pi where powershell IS the shell, trimming it would disarm the model). Only booleans toggle a feature; a string under `theme` names the palette while keeping the feature on. Example: `{ "war-dogs": { "banner": false, "theme": "oxide" } }`.

**Trust.** The block is read the way pi reads settings: the agent-dir block with the project block (`<cwd>/.pi/settings.json`) merged over it per key — and the project file only when the project is **trusted**. pi ignores an untrusted project's settings entirely and treats an *undecided* one as untrusted until you answer its prompt; war-dogs mirrors that through `ctx.isProjectTrusted()` and, before `session_start`, pi's own trust store plus the `--approve`/`-a`, `--no-approve`/`-na` flags. Everything project-scoped goes through that one gate: the feature block, `packages` (the MCP yield), `war-dogs.expect` (whose profiles name a `cmd` that is spawned) and `.pi/subagents/*.md` (whose frontmatter can name `extensions`), and `.pi/inject/`. pi's own answer has a SHORTCUT war-dogs does not follow: a project with none of pi's trust-requiring resources is reported trusted without a prompt, regardless of the store — for war-dogs' own project resources (`.pi/inject/`, `.pi/memory/`, `.pi/subagents/`) that is not consent, so pi's TRUE counts only when pi had something to decide, else the store decides, and a never-asked project holding those gets one warning at session start naming `/trust` (Load-bearing, 2026-08-28).

**Theme.** war-dogs' palettes belong to war-dogs (`visual/theme/*.json`) but are applied THROUGH PI, not in memory: `/war-dogs on` writes `settings.theme` = the war-dogs palette (`war-dogs.theme`, else `canopy`) — saving your prior theme under `war-dogs._prevTheme` — and reloads, so pi applies the palette to chrome AND content consistently and OFF restores your theme. This replaced an in-memory `setTheme(object)`, which raced pi's own reload: pi rendered the transcript in the old palette first, and war-dogs' later object apply left the CONTENT stale-cached in the wrong colours while the chrome was right (demonstrated — code spans stayed the dark theme's). The theme files self-install into `<agentDir>/themes` on the first ON (so `settings.theme` resolves them and `/settings → Theme` lists them, pickable while on); non-destructive — nothing is ever deleted, and a user who never turns war-dogs on gets no files. The pager's `visor` sub-theme (the subagent view's blue canvas) is still applied as an object, because it is scoped to that view, not pi's global theme.

**Environment.** `PI_CODING_AGENT_DIR` is pi's own agent-dir override; war-dogs resolves the dir through pi's `getAgentDir`, so a private agent dir relocates the whole install — themes, transcripts, MCP caches. `PI_WARDOGS_TRACE=<file>` arms the pager's layout trace, read once at module load. `WAR_DOGS_DELIVERY_WINDOW_MS` sets the background-delivery batching window (1500; `0` delivers each result at once). `WAR_DOGS_ENABLED` forces the MASTER switch for one invocation (2026-08-25, maintainer): `0`/`false` boots war-dogs off, `1`/`true` on, anything else defers to `war-dogs.enabled`. The kill-switch scripts and `pi -p` runs needed without editing settings.json. `WAR_DOGS_MEMORY` forces the MEMORY feature the same way (`0`/`false` off, `1`/`true` on, else `memory.enabled` — see "Memory"). ## Portability and uninstall

Copy the whole folder, `node_modules/` included, into another machine's `~/.pi/agent/extensions/`; nothing in `settings.json` is required. Cross-platform edges, each handled at its one site: the file/URL opener picks `xdg-open`/`open`/`cmd start` by platform (`util/opener.ts`) and reports a missing one instead of crashing; `~/` expands through `os.homedir()` (Windows has no `$HOME`); the render daemon's spawn lock reads `/proc/<pid>/stat` on Linux and degrades to pid-liveness elsewhere; the peer socket is a Unix socket under `$XDG_RUNTIME_DIR`/tmp on POSIX and a named pipe on Windows; a background job is process-grouped and killed with `-pid` on POSIX, by pid on Windows. What is still Linux-only and awaits a real Windows/macOS pass: the peer transport end to end, the three native binaries (`npm install` on the target), inline terminal images, and the alt-screen/mouse escapes (a VT terminal is assumed). A folder copy is **same OS, same architecture**: three runtime packages (`tsx`→`esbuild`, and the adapter's `@napi-rs/keyring`, `recheck`) resolve a platform-gated native binary, so a copy on another platform needs one `npm install` (or `npm rebuild`) there — until then the render tier fails loudly (25 s once, then instantly, naming `@esbuild/<platform>`) and MCP OAuth storage is unavailable. For a copy you will not develop in, `npm ci --omit=dev` is ≈ 130 MB instead of ≈ 460 and runs identically — only `npm run typecheck` is unavailable, because the pi type declarations are devDependencies (pi's loader aliases `@earendil-works/*` and `typebox` to its own copies at runtime, so nothing runtime-side resolves them from the folder). `npm install` may report vulnerabilities and offer `npm audit fix --force`: they sit inside the pinned pi devDependency's subtree (type-only) and `--force` would silently repin the declarations — do not run it here.

To uninstall, delete the folder; pi is stock on the next start (a session that recorded war-dogs' `gen-time` entries still opens — pi skips a custom entry with no renderer). What is left behind, none of it required by pi: `<agentDir>/themes/{canopy,canopy-cobalt,dune,oxide,visor}.json`, installed on the first ON (never by a boot-off); delete them freely — `/war-dogs off` restores your own `settings.theme`, and if the name still lingers pi prints `Failed to load theme … / Fell back to dark theme.` and continues; subagent transcripts beside their sessions plus the legacy pool `<agentDir>/subagent-runs/` (also where `--no-session` runs land — a run *is* its transcript, so even an ephemeral parent's children are written); `${XDG_CACHE_HOME:-~/.cache}/war-dogs/` (render-daemon state, spawn lock, its log) and `<os.tmpdir()>/war-dogs-webfetch-<uid>/` (saved fetch bodies, 0700); the adapter's own `<agentDir>/mcp-cache.json`, `mcp-npx-cache.json`, any `mcp.json` you wrote, and OAuth credentials in the system keyring; `<agentDir>/peers/` registry entries (removed at shutdown; a crash leaves one until the next sweep notices the dead pid) and the `wd-peers-<uid>` socket dir under the system tmp; and the `war-dogs` block in `settings.json` — `enabled`, plus `_prevTheme` while on, are the only keys `/war-dogs` writes (and `theme`, which it sets on and restores on off).
## Known limitations

Each is the documented consequence of a mechanism, not a bug awaiting a fix; where a load-bearing entry exists it is the authority.

- **`/war-dogs` itself stays listed while off** — it is the way back, and the one thing registered unconditionally. (Under the old live toggle an off also left the adapter's `/mcp` commands and `skill:mcp-scripting` listed; control is settings-only now, so off is a boot that never registers them — verified 2026-08-19: `/war-dogs off`, then `/mc` completes to nothing but pi's own `/compact`.)
- **`pager: false` is a degradation, not a mode.** No station, no run views, no fold-and-cluster surface; subagents still run and their transcripts still land on disk. The tool renderers honour pi's own `expanded` there, like stock. No per-beat wire control either, and the `[timestamp: …]` stamps of stock-rendered results (bash, MCP) stay visible there — only war-dogs' own renderers subtract theirs.
- **Emoji cost one column.** Terminals that ignore `U+FE0F` draw `base + VS16` in one column while pi-tui counts two, so a row carrying one renders a column short and the scrollbar sits a column in. Not fixable from inside the extension ("Load-bearing").
- **Complex scripts clip at the right edge.** The emoji offset's mirror: pi-tui UNDER-measures Indic/Myanmar clusters (a base+matra counts one column; many terminals draw the matra as its own cell — `[অসমীয়া]` measures 6, draws 8), so a row carrying them is drawn wider than the terminal. Autowrap is disabled while the pager is open (`?7l`, restored with the mouse modes on every exit path), so such a row CLIPS at the last column — losing its tail and that row's scrollbar cell — instead of wrapping, which scrolled the frame and left stale fragments (a second title bar) until a full repaint. pi-tui's wrap decisions still use its own measure, so those lines may also break earlier than they visually need to ("Load-bearing").
- **Mouse mode 1003 replaces the terminal's native selection.** While the pager is open the terminal hands every button and motion to pi: native selection needs its modifier (`shift`+drag in kitty, Ghostty, iTerm2, xterm) and middle-click paste is unavailable inside the pager. Off restores stock (pi enables no mouse mode at all).
- **Images typed during a compaction reach the model unresolved** (see "Tools").
- **`--no-session` children still write transcripts**, in the legacy pool (see "Portability and uninstall").
- **Replies are not delivered in print/json sessions or to children** — no conversation to wake (`canDeliver`); those sessions hold for replies with `wait`, and their tool description says so. A `pi -p` that never waits ends with the child killed at process exit.
- **The cold flatten of a huge session blocks pi's UI**: on a 15 MB / 4,902-row session, ~5.5 s for the first flatten, ~5 s for `ctrl+o` expand-all (~28,900 rows), ~4.5 s collapse-all; steady state p50 ≈ 2 ms.

**An idle-time delivery under `pager:false` draws as a prompt.** The delivery-turn rule sends it through pi's `sendUserMessage`, so pi's own scrollback renders it as `❯ [agent result …]`; the pager draws the act. The wire is identical either way.

## Troubleshooting

**pi exits with `Tool "mcp" conflicts with …`.** pi-mcp-adapter is installed as a pi *package* as well as bundled here, in a way war-dogs could not detect (it detects any `packages` entry containing `pi-mcp-adapter` and yields; a fork under another name is the case that reaches the hard exit). `pi remove npm:pi-mcp-adapter`.

**`[war-dogs] <name> failed to load: …` on stderr.** One feature's registration threw; the rest is up. Everything is wrapped so a broken feature degrades instead of taking pi down, which makes this line the only signal — reproduce with `echo '{"id":"1","type":"get_state"}' | pi --mode rpc --no-session`; silence on stderr is a clean load.

**`/war-dogs on` reloads into pi's dark theme, with `Failed to load theme …` at the top.** A war-dogs theme JSON could not be written into `<agentDir>/themes` (usually permissions — `installThemes` is silent by design, since a stderr line lands in pi's TUI pane), so the `settings.theme` the command wrote does not resolve. Fix the permissions and `/reload`, or copy `visual/theme/*.json` there yourself.

**`[war-dogs] agents: <file> — <reason>`.** A named-agent file was skipped — almost always frontmatter with no body. If a *project* agent file is not read at all, the project is untrusted or undecided.

**The surface is frozen after a `pi update`** — `!echo` never shows, and turning war-dogs off makes it come back. pi changed its root layout; the pager sees bare containers instead of messages and signs them as never-changing. `unwrapContainers` in `surface.ts` handles the known shapes; the probe is in the Upgrade Contract.

**Moving the mouse types junk into the shell** after a crash or `ctrl+z` — or long shell lines CLIP at the right edge (autowrap left off). All paths are hooked now; if you land there anyway: `printf '\e[?7h\e[?1049l\e[?1006l\e[?1003l'` or `reset`.

**`/mcp` is not a command pi knows.** war-dogs is off, and MCP is part of war-dogs — nothing of it is registered while off. `/war-dogs on`.

**`Can't switch war-dogs while <reason> — try again when idle.`** The busy guard, naming which of the four states it saw. Wait, or abort the run from the station. A compaction flag can no longer wedge it: pi emits `session_compact` only on success, so the flag is also cleared by the compaction's abort signal, by the next input or session start, and by age (10 min).

**`Refused: N subagent runs are still working …` on `/new`, `/resume`, `/fork`.** A switch tears down every in-flight run; wait or abort from the station (`alt+s`, the run's ✕). TUI only.

**Render fetches fail with `no Chrome/Chromium binary found`.** Install a system Chrome/Chromium on `PATH` (`google-chrome`, `google-chrome-stable`, `chromium`, `chromium-browser`, `chrome` are probed). The static tier keeps working.

**A render fetch waits ~25 s and fails.** The daemon could not come up; the message quotes the daemon's own fatal line and the failure is memoised for 60 s. If it names the spawn lock, the lock carries its owner's pid and start time and is broken automatically when the owner is gone, recycled, or 10 s past the spawn budget; the text names the lock directory.

**The scout produces no verdicts.** It runs `pi -p` with this machine's configured model; configure one, or name a pinned profile under `war-dogs.expect.profile`.

## Mechanics

**A keystroke to a rendered frame.** pi owns the editor and builds its component tree as always. `mod.ts` opens a full-screen `ctx.ui.custom` overlay and *detaches* pi's chat containers from pi's root, so pi's own frames stay tiny and cannot flicker through; the pager holds the refs and renders them itself. Each frame `surface.ts` flattens those containers into display lines — with a prefix cache keyed by per-component signatures, so steady-state cost is O(streaming tail) — folds tool output against its *source* text, draws the scrollbar, and composites the live bottom UI (status, editor, footer) inside the overlay. The overlay sits on the alt screen with any-motion mouse reporting; both are war-dogs' terminal state and are restored on every exit path, including an uncaught exception and `ctrl+z`. Terminal input arrives through `ctx.ui.onTerminalInput` (the yield rule); assistant tokens mark the surface dirty via `message_update` so it follows the stream the way stock pi does.

**An agent call to a finished run.** The `agent` tool resolves config (`agents/config.ts`), records a run (`agents/run.ts` — the record is published *with its build reserved*, so a chat arriving during the build joins it instead of forking the transcript), and builds the child in-process (`tools/agent.ts`); a later chat rebuilds a released session through `ensureSession()` (`agents/session.ts`) with the same hand-over on both paths. Progress streams to the tool's renderer and the station; the run's own chat view (`runview.ts`) is built the way pi builds main — one component per message, updated in place. Sends to a run are serialised behind pi's `preflightResult` acceptance, so a message typed at a run mid-turn becomes a steer, never a rejected second turn.

**A pasted image to the model.** Drop, CTRL+V and typed paths become refs through the live editor component — never `ctx.ui.setEditorText`, which clears the paste registry and drops the caret — with the paste registry transformed alongside the text; a `!bash` or `/command` buffer is never rewritten (pi dispatches those itself). At submit the pipeline re-registers any footer defs already in the message (a `/fork` or `/tree` restores messages pi wrote), refreshes each ref's bytes, resizes, and writes the footer. The id space is rebuilt from the *entered* session at every session start and on `session_tree`/`session_compact` (headless runs included); history's def table — not the store — decides which ids are taken.

**The switch.** `/war-dogs on|off` is refused while busy, then writes `war-dogs.enabled` into `<agentDir>/settings.json` (temp+rename, every other key preserved; on: `settings.theme` ← the war-dogs palette with yours saved under `war-dogs._prevTheme`; off: yours restored, the marker deleted) and calls `ctx.reload()`. pi's reload tears down every extension surface (`resetExtensionUI`: overlays, terminal-input listeners, header, footer, widgets, statuses, autocomplete wrappers) and builds a fresh `ExtensionRunner` from re-imported modules, so the new state is a clean boot: `installOnce()` at load (or nothing at all), then `activate()` inside `session_start` — HUD, attachments, pager, the MCP adapter's `session_start`, and the custom tools into the active set in canonical order (pi's as they are, then ours in registration order, MCP names only as the adapter wants them). There is no reverse path in the code; off is the absence of registration.

**The MCP facade.** The adapter's factory is invoked with a Proxy over pi's ExtensionAPI that forwards everything — events, commands, flags, the active set — and RECORDS at two points: `registerTool` keeps every name and definition (the direct-tool set is dynamic — `<server>_<tool>` names appear after an async init) for the pager's toolmap, the child-tool source and the canonical active order; `setActiveTools` notes what the adapter itself wants active (`wanted`), never a tool it deactivated, and passes the write through untouched. The adapter receives pi's `session_start`/`session_shutdown`/everything directly, as a standalone extension would; because its handlers were registered during `installOnce` (load) and war-dogs' own `session_start` handler after, the adapter's init has run by the time `activateCustomTools()` orders the active set. Each registered definition also goes into the pager's toolmap and to children through a live keyed source, which is how a subagent uses MCP on the parent's servers. (The facade once carried a live-off mode — a virtual active set, command refusal, captured and re-dispatched events, skill parking; all gone with the live toggle, 2026-08-19.)

## What pi does on each transition, and how war-dogs follows

Measured on pi 0.83.0 with a tracer extension. Two facts drive everything: pi **re-runs every extension factory** on `/new`, `/fork` and `/resume` — against a fresh Extension object, the previous `pi`/`ctx` invalidated — but **re-imports the module only on `/reload`** (and on a cwd change), so module-level state survives `/new`. Anything done at load, or kept in module state, must expect to run again against a new `pi` with its old state still there.

| Transition | Events, in order | Factory re-run | Module re-imported |
|---|---|---|---|
| boot (`pi`, `--continue`, `--session`, `--no-session`) | `session_start{startup}` → `resources_discover{startup}` | first run | yes |
| `/reload` | `session_shutdown{reload}` → factory → `session_start{reload}` → `resources_discover{reload}` | yes | **yes — state reset** |
| `/new`, `/resume` | `session_before_switch` (cancellable) → `session_shutdown{new\|resume}` → factory → `session_start` → `resources_discover{startup}` | yes | no (yes if cwd changed) |
| `/fork`, `/clone` | `session_before_fork` (cancellable) → `session_shutdown{fork}` → factory → `session_start{fork}` → `resources_discover{startup}` | yes | no |
| `/tree` | `session_before_tree` (cancellable) → `session_tree` | no | no |
| `/compact`, auto-compaction | `session_before_compact` (cancellable) → `session_compact` **only on success**; Esc, failure or cancel emit nothing more | no | no |
| `/quit`, ctrl+d, double ctrl+c, SIGTERM/SIGHUP | `session_shutdown{quit}`, awaited before exit | – | – |
| dead terminal, uncaught exception | **no `session_shutdown`** | – | – |

`resources_discover` follows every `session_start`, with reason `reload` only after a reload. pi `await`s `session.abort()` on the outgoing session before `session_shutdown`, so in-flight turns settle into the old session first. RPC `new_session`/`switch_session` emit `session_start` twice (a pi bug; harmless — `activate()` re-sets header/footer/widgets and the MCP adapter keeps a lifecycle generation of its own).

The rules war-dogs derives, each paid for: the MCP adapter is instantiated once per factory run with its capture maps reset first; child-tool sources are keyed, not pushed; `installThemes()` runs once per process; `/war-dogs` is a settings write plus reload, never process state; the compaction flag closes on the event's abort signal, the next input or session start, or age — never by waiting for `session_compact`; a switch or fork is refused while a run is in flight; the attachment id space is rebuilt from the entered session; `session_tree`/`session_compact` tell the pager the content was replaced (`contentReplaced()`), and `agent_settled` ends the follow-hold (`turnSettled()`), so neither a removed message nor the settle collapse is held on screen; the shared browser closes only on `reason:"quit"`.

## Extending

**Before changing what a tool says or returns, read `dev/tool_mechanism/`** — the per-tool reference of every model-facing string and situation — and after the change re-run `node dev/tool_mechanism/dump-definitions.mjs` (definitions.md is generated from the live code) and update the tool's page by hand.

**Time awareness** (2026-08-21): pi's default system prompt carries NO date or clock at all, so the model was clockless for the whole session. Every tool result, error, receipt, delivery, and USER PROMPT now ends with one fixed line, `[timestamp: 2026-08-21 14:32:07 +07:00]` (local time with offset, completion time; a few hours of 2026-08-21 shipped the shorter `[at …]` label — the parsers and display strips accept both) — `util/stamp.ts`, applied at every registration choke point (`reg()`, the subagent publishes, the MCP facade's `registerTool`), in the input pipeline for prompts (registered after attachments, so transforms compose; idempotent — appendStamp replaces an existing trailing stamp, which is what keeps a `/fork`-restored message from stacking two), on the run-view routing path for child-directed messages, and on the child's FIRST prompt — the task the parent hands over (2026-08-22; it arrived clockless, since the parent's input pipeline never sees it) — and on a SKILL invocation: pi emits `input` BEFORE expanding `/skill:name args` into `<skill …>…</skill>\n\nargs`, so the stamp rides the args and lands last (the no-args form gets it after a SPACE — pi finds the name at the first literal space, and a newline made `name\n\n[timestamp…]` an unknown skill, sent raw). The transform had skipped every slash-prefixed text as a command; prompt templates still are (their args substitute mid-body). Uniform on purpose: tools run constantly, so stamping everything gives the model a continuously updating clock as a side effect. The `timestamp:` label matches the house bracket grammar and keeps a log tail's own bare timestamp line from impersonating it. Self-teaching: NO description mentions it. Children's results are stamped too since 2026-08-22 (their skins are stamped at build; until then stock bash/write/edit left a child clockless on its three most-used tools). The stamp is the FINAL line of everything, so `splitTrailer` consumes it after the run id; on the pretty surface it is hidden EVERYWHERE (the wire view shows it back — see "The wire view"); read's NOTICE test knows the form.

**A new tool's TEXTS follow the house register** (the tool-descriptions proposal, implemented 2026-08-21; the proposal doc is in git history): everything in `description` — no `promptSnippet`, no `promptGuidelines` (a SYSTEM.md replaces pi's prompt; the description travels in the request always); ZERO-DIRECTION IS RETRACTED (maintainer, 2026-08-23): a description may guide — when to use, how to write a task — so long as every sentence is true of the tool and changes a decision (the agent tool's contract in `dev/agent-contract.md (Part 1; draft 8 is in git history)` is the model); tools stay SELF-CONTAINED — nothing the model needs may depend on a system prompt, skill or context file; one-line-per-paragraph, machine metadata as `[…]` bracket lines at the end of results; a description STATES THE SUBSTANCE and never names another tool as the only route (2026-08-27, maintainer: tools and their schemas are customizable context — `webfetch` being off must not strand a model that could curl; "read the page itself", never "webfetch it") (`[agent id: …]`, `[Read lines …]`), and schemas that are AUDIENCE-SOUND: a parameter inert for its reader is omitted from that reader's schema, not documented as inert; values a description names (defaults, caps) are interpolated, never guessed.

**A model-facing tool needs three registrations or it half-works**: `pi.registerTool` (the model can call it), `registerToolDef` in `visual/pager/toolmap.ts` (a subagent transcript renders it with the real renderer instead of raw JSON), and `setChildExtraTools` in `agents/childtools.ts` (children load no extensions, so they must be handed it). Wire all three from `index.ts`, inside `installOnce` — that is what makes it vanish when war-dogs is off (a boot-off never runs it); add its name to `WAR_DOGS_TOOLS` so it takes its place in the canonical active order. (The toolmap also keeps render aliases `WebFetch`/`Kimi-WebSearch`/`subagent` for transcripts recorded before the renames — render-only, never model-facing.) A tool set that is not known at load — the MCP adapter's is: direct tools appear after an async init, and it deactivates ones it stops offering — registers a keyed live source instead: `setChildExtraToolsSource("mcp", () => mcp.childToolDefs())`, consulted at child-build time; keyed, not pushed, because the factory re-runs per session.

**A tool renderer** lives in `visual/tools/`; `renderCall`/`renderResult` return a pi-tui `Component` and run inside pi's render loop under a try/catch that silently falls back — keep it pure and cheap. For a built-in re-skin follow `tools/read.ts`: spread the stock tool, re-declare `promptSnippet`/`promptGuidelines` from the `create*ToolDefinition` factory, pass `stockToolOptions()`, attach the renderer. Re-declaring is not optional ("`wrapToolDefinition` drops prompt metadata", Load-bearing); `createBashTool` is the one factory that `Object.assign`s them back.

**A pager view** is a new branch in `PagerComponent.render()` plus its key/mouse handling in `mod.ts`. Reuse `flattenLive`/`renderSubCached` for anything that shows pi components and `childEntriesToRawLines` for the raw fallback. Fold against source text (`srcLines`), never display rows.

**A named beat** (something pi draws that should read as an act) owes `foldName()` a name, `actSentence` a case, `sigFor` its own O(1) state, and the cluster summary a verb. **A component of ours in pi's tree** (a header, a status) that renders from state rather than text owes `sigFor` a `wdSignature()` — or the cache freezes it at its first frame (Load-bearing, `flatten.ts`).

Where the extension lacks authority — spacing or layout stock pi hardcodes outside renderer reach — do not hack around it: implement fully in the pager, which war-dogs owns end to end, do what is cleanly possible inline, and report the gap with the mechanism. A documented limitation beats a fragile workaround.
## Debugging

pi loads this TypeScript through jiti with no typecheck, and wraps every renderer and event handler so a throw is swallowed into a silent fallback. Nothing tells you a change is broken: a type error, a missing import, a shadowed binding, a wrong arity after a refactor all present as "the UI is a bit off" — a missing stats line, a tool rendered as raw JSON, a row laid out wrong. So correctness is established by asking the machine, escalating through these instruments.

**Typecheck after every change — non-negotiable.** `npm run typecheck` (or `npx -y -p typescript@5.9 tsc -p tsconfig.json`). The tsconfig is self-contained: the pi type declarations are pinned devDependencies resolved by relative paths, `pi-mcp-adapter` maps to `mcp/pi-mcp-adapter.d.ts`, and it covers the whole tree at zero errors with `noUnusedLocals`/`noUnusedParameters` and the incremental strict flags. Full `strict` is not on — the pi boundary is `any`-heavy by necessity — so this catches the silent-failure classes, not everything. **Formatting is enforced**: `npm run format` / `format:check` (prettier, tabs, 120 columns; `.editorconfig` covers editors; markdown is in `.prettierignore` and hand-wrapped). Run `git config blame.ignoreRevsFile .git-blame-ignore-revs` once per clone so blame skips the one-time reformat.

**Run one module in isolation** through pi's own jiti — the same loader pi uses, so what runs is the real module (`tsx` cannot: it resolves the pinned packages to their `.d.ts` entries and dies; plain `node` against pi's `dist/` works only for pi's own classes). `util/` needs only the pi-tui alias; a module that imports pi's agent API needs `@earendil-works/pi-coding-agent` mapped to `<pi>/dist/index.js` too.

**Settle geometry with the trace, never with arithmetic.** `PI_WARDOGS_TRACE=/tmp/wd-trace.log` (read once at process start) records the pager's per-frame layout plus click and fold events, written only on change. Per-frame fields: `src` (main/child/raw), `rows`, `tail`, `raw` (the flatten's own height), `total` (rendered after a follow-hold), `drop`, `held`, `hw`, `cacheN`/`liveN` (this flatten's cache hits / fresh renders), `body`, `offset`, `follow`, `ms` (the last flatten's cost — healthy p50 1–2 ms; a cold render legitimately spikes once). ## Load-bearing — the ledger

Every entry here was paid for with a real bug: the constraint, the mechanism, what it cost. Re-verify the rationale before touching it; overturning one takes a demonstration, not an argument. Grouped by area.

### Children and runs

**Child sessions are configured by us, not by pi.** `createAgentSession` only reloads a `ResourceLoader` it created itself, so a loader we pass must be `await loader.reload()`-ed or it reports no system prompt and no extensions. Everything a child needs — system prompt, tools, model, thinking level, model runtime, context files — is handed over explicitly on **both** paths, spawn (`tools/agent.ts`) and rehydrate (`agents/session.ts`), continue included. A missed value fails silently: the run answers, with the wrong prompt, model or thinking level or a missing tool (the thinking level was inherited by neither path until a probe compared the manifest against the parent's `--thinking`). Keep the two call sites identical; the child-parity check is how you prove it.

**The 2026-08-24 rename is structural, not cosmetic.** `subagent` became `agent` with seven actions on one schema (the contract: draft 8, `dev/agent-contract-3.md`, now in git history; live: `dev/agent-contract.md (Part 1; draft 8 is in git history)`); states became working / queued / idle / stopped / error, mapped from legacy manifests at the READ boundary (`listManifests`), never rejected — reject and every old run vanishes from the station. `stop` interrupts and the run STAYS continuable (`message`); only a provider/build failure is `error`. Depth defaults to 0; concurrency is an OWNED budget (`agents/slots.ts` — acquire under the run's own signal, release exactly once at settle via `rec.slotHeld`; a copied cap overshoots, the fan-out rule the research demonstrated 30/30). There is no foreground: every run and message returns a receipt and the reply is delivered where a conversation exists (`canDeliver`), held for with `wait` elsewhere — `wait` races the work promise against the call's signal, and an interrupted wait leaves the run working. `ask` is a tool-less `completeSimple` over a transcript snapshot (live messages + streaming partial), auth via `runtime.getAuth` (an Upgrade Contract reach beside `sharedModelRuntime`), pi-ai's compat module loaded by ABSOLUTE path from the running pi — the jiti alias covers `@earendil-works/pi-ai`, not its subpaths. The `message` verb is promptRun for a working run (steer; the owning turn delivers one reply covering both) and the continue flow for an idle one; the two must not each deliver.

**The 2026-08-24 stress audit — six mechanisms, each paid for by a reproduced bug** (an Opus auditor drove the mock rig; findings in the commit trail). (1) A CLAIM is per-turn: `rec.claimed`/`rec.schemaReply`/`rec.activity` are cleared at every owner-turn start in `sendToRun` — left set, the next turn's delivery was skipped forever (a wait then a message: the message's reply reached the model ZERO times). (2) Only the send that OWNS a turn gets a work promise and a delivery (`onAccepted(ownsTurn)`): a steer that joined another send's turn resolved at acceptance and delivered the PREVIOUS reply as a fresh completion. (3) wait treats a pending send/build as working (`hasPendingSend`) and claims a work promise the moment it appears mid-poll — the acceptance gap made wait return "(earlier)" during a message it should have held for. (4) The pager's prefix rollback must never cut inside a component's own rows: a class-change drain mid-component (an errored message's thinking, then its error-class act) froze the flushed thinking into the prefix while `flatPrefixComps` stayed at that component, and every fast-path frame re-emitted it — the "thinking rendered twice" screenshot; `drainPending(keepComp)` keeps the current component's tail pending under a fresh mark. **A run IS its transcript.** Continuing a run means opening the file it wrote; `SessionManager.create()` is not a fallback for a missing one. Both continue paths read `run.sessionFile` and, when an older manifest lacked it, silently started a BLANK conversation beside the real transcript — the child answered with no memory of its task. `transcriptFor()` (`agents/run.ts`) finds the file the manifest names, else the newest `.jsonl` in the run's directory, and with none both paths refuse ("this run's transcript is missing"). The same discipline binds ids: `findRun()` matches exactly first, and a fuzzy candidate must be ≥ 8 characters and unique — the old bare `find()` resolved `"a"` to whichever run came first, and `abort`/`resume` then hit a run nobody had named. Ambiguity is thrown back with the candidates, never guessed.

**A child's failure lives in its stop reason, not in its text.** A turn that dies at the provider still produces an assistant message — `stopReason:"error"`, an `errorMessage`, no content blocks — and `prompt()` resolves. Reading text blocks alone reported a 401, a context overflow or a truncation as `(no output)` on a run settled `done`: silent wrong output. `lastAssistantOutcome()` carries the stop reason beside the last text (from different messages on purpose — "I found 3 of 10 files…" then a 401 is partial output *plus* a failure); both call sites settle `failed` with the provider's message, and the tool THROWS, since a thrown error is the only way a tool result reaches the model marked as an error. `stopReason:"length"` says so in the body. Aborts keep the same discipline: expiry, a user's ✕ and a parent tearing down its subtree are three sentences, so every `abort()` is given a cause (`abortCause`/`abortKindOf`) and the body, the manifest and the background follow-up all read it — "finished in 4s" on a run that quietly timed out is the same lie in a friendlier voice.

**No timeout means NO TIMER.** `timeout_s` is undefined unless the call, an agent file, or settings asked for one (the 2026-08-21 no-default-timeout change) — but the abort timer stayed armed unconditionally, and `Math.max(1, undefined) * 1000` is `NaN`, which `setTimeout` treats as 0: EVERY run without an explicit timeout aborted the moment it spawned — settled `failed`, delivered `(timed out after undefineds — no output)` — silent wrong output on every default-config subagent, shipped for a day and demonstrated with the mock's `sub` (fixed 2026-08-22). The timer is gated on the value now. The general rule: an OPTIONAL number must never meet arithmetic that feeds a timer, cap or budget without an explicit undefined branch — `setTimeout(fn, NaN)` fires immediately, it does not throw.

**Children get the skins in their CHILD form, built for the child's cwd.** Until 2026-08-22 children had pi's STOCK bash/write/edit (the "accepted hole": unstamped results, no `description`, pi's one-edit batch error) because the parent's bash could not be handed over as-is — its `background` branch spawns a job whose result delivers through the parent's `pi.sendMessage`, which a child `AgentSession` does not have. ### The inherent prompt and the brief

**The base is swapped per turn, and a user SYSTEM.md stands everything down.** `prompt/index.ts` rides `before_agent_start`: when `systemPromptOptions.customPrompt` is falsy it returns `buildSystemPrompt({...options, customPrompt: BASE})` — pi's own assembler, reached from `dist/core/system-prompt.js` through pidist.ts because pi's package index does not export the function — so APPEND_SYSTEM.md, context files and skills survive exactly as under a user SYSTEM.md, and compaction survival is free (the hook runs on every turn, idle-time deliveries included since the delivery-turn rule below; there is no re-injection path to maintain). When `customPrompt` is truthy the handler returns NOTHING — base and brief both: the user's context engineering is honored whole. The base prose is GENERATED byte-exact from `dev/system-prompt-scratchpad-v2.md` into `prompt/base.ts` (the extraction is verified by importing the module through pi's jiti and comparing against the fence — edit the scratchpad and re-extract, never the string; the prose is the maintainer's). VERIFY ON THE WIRE, never via `ctx.getSystemPrompt()`: at `session_start` that accessor returns the BASE pi built, not the per-turn override, so an sp.ts dump "proving" the ON swap proves nothing — the sp.ts prompt-parity check stays OFF-only by design, and the ON checks read the mock's `DUMP=` request bodies (demonstrated 2026-08-26: the first wire check "failed" for exactly this reason before the instrument was corrected).

**The memory rider is STAGE 2, outside the stand-down.** The prompt handler's stage 1 (base + brief) returns nothing under a user SYSTEM.md; memory appends AFTER that decision, to whichever prompt is in force — moving it inside stage 1 silently kills the contract's survival requirement (the rider exists precisely to outlive a foreign base; demonstrated on the wire: `My own prompt…` + `# Keep the memory` in one request). Scaffolding rules, each honest: `reference.md` is the HARNESS's and is rewritten whenever its bytes differ; `MEMORY.md` is the MODEL's and is created (legend only) but never overwritten — a scaffold that "refreshes" the index destroys the memory. Everything gates per turn on `memory.enabled` (+ `WAR_DOGS_MEMORY`), so `/memory on|off` needs no reload and OFF appends and reads nothing.

**A persisted custom message is its OWN entry type — scan for both shapes.** The brief's once-per-session check reads the transcript, and a custom message lands on disk as `{type:"custom_message", customType:…}` (session-manager.d.ts), NOT as a `.message`-wrapped message entry; scanning `.message` alone re-injected the brief on every `pi -p --continue` (demonstrated on the wire: two `[session brief:` messages in one request). `briefAlreadyInSession` reads both shapes and memoises by session id only after SEEING one in the branch — never at injection, so a first turn that dies before persisting cannot mark the brief as delivered. A `/fork` copies the entries, so the brief travels with the fork and is never doubled.

**A turn that a DELIVERY starts skips `before_agent_start` — "per turn" means per USER prompt.** pi emits the hook only inside `AgentSession.prompt()` (agent-session.js:882); a background agent reply, peer message or bash result that lands while main is idle goes through `sendCustomMessage(…, {triggerTurn})` → `_runAgentPrompt` directly (1062-1094, 744-757), no hook. Demonstrated: the wake turn's request carries the base and memory prompt and a fresh PER_TURN message after the delivery.

**One `before_agent_start` handler yields ONE message; several messages need several handlers.** `BeforeAgentStartEventResult.message` is singular and the runner pushes each handler's into `messages` in registration order (runner.js `emitBeforeAgentStart`), then agent-session persists each as its own `custom_message` after the user's prompt. The inject feature therefore registers four handlers (one per file × scope) rather than concatenating — concatenation would have lost per-file acts and per-scope once-per-session, and a combined message could not be told apart in the transcript scan. ### The pager and rendering

**A working snippet is a control, complete or not (2026-08-28, overturning 2026-08-20).** The rule was: in the working window the sentence and its leaked rows light and click as one control, but a snippet that hid nothing was "complete — no light, no click", and an own-kind act (the session brief, a delivery) registered a handle for its sentence alone. Now every lit snippet row is a handle and a per-row fold range on both branches (`snippetRows`, `ownSnippetRows`; `groupHandles` on both), so hovering the body lights the whole act and clicking it toggles. Demonstrated with injected mouse bytes and the trace (`ev=toggle tool=session-brief before=0 after=1` from a click on its body while main worked; before: `hit=0 span=none`).

**A steered delivery is held until pi consumes it.** While main streams, a delivery rides pi's steering queue (`sendMessage(deliverAs:"steer")`), and pi's Esc handler clears every queue (`restoreQueuedMessagesToEditor({abort:true})`): typed text goes back to the editor, a custom message has nowhere to go, and a worker's reply that arrived during a long foreground bash was simply gone when the user pressed Esc (the maintainer's question, 2026-08-29; verified: no `agent-result` in the transcript, nothing on the next prompt). `sendDelivery` now stamps each steered delivery with a nonce in `details`, holds it, drops the hold on `message_start` with that nonce (pi consumed it), and re-sends whatever is still held at `agent_settled`. Under the interrupted-agent rule (the entry below) that re-send rides pi's `nextTurn` queue: the first build took the prompt path and woke a turn right after the Esc, which was never the intent. Demonstrated: Esc on main mid-bash, nothing for seven seconds, then the reply beside the next prompt (`user` → `agent-result` in the transcript and on the wire).

**An interrupted agent is woken by nothing on its own (2026-08-29, the maintainer's rule; the silent loss).** The 2026-08-29 audit reproduced the maintainer's report by harness and in the TUI: a depth-1 lead interrupted mid-`wait` (Esc in its view), followed up by the user, its worker finishing, the lead summarising — and main never told (`dev/agent-scenarios.mjs leadinterrupt`, before the fix `deliveries=0`). A second face: alt+x stopped the team and the stopped worker's report woke the lead into a fresh turn (`leadaltx`). The maintainer's rule replaced the flag dance: an interrupt ends everything the agent was doing, the team hold included (`holdForTeam` returns on `userInterrupted`, `interruptRun` wakes it through `rec.holdWake` and counts a held lead as interruptible), the run settles idle inside the episode at once, and NOTHING wakes it on its own — while it is idle inside the episode, or the interrupt is still unwinding (`parkedForInterrupt`, agents/run.ts), its agents' replies park on `rec.pendingDeliveries` (`deliverToRun`) and are appended to its transcript as plain custom messages ahead of its next turn, whoever starts it (`sendToRun`'s owner block, `sendCustomMessage(…, {triggerTurn:false})` on the idle session). Same eight scenarios green.

**A delivery to a run is a steer only with `triggerTurn: true` (2026-08-29, the real-model audit, drive 2: a lead told main its worker was still working after the worker had replied).** pi's `sendCustomMessage` reads `triggerTurn` in its STREAMING branch too — `isStreaming && triggerTurn !== false` is the steer (`agent.steer`) — and since 0.84.4 a streaming session given `triggerTurn: false` takes its fourth case: the message is deferred to the turn's end (`_pendingCustomMessages`, flushed at `turn_end`) and appended to `agent.state.messages` and the transcript. **`flatten.ts` is the render cache, and it is never cleared.** Folded tools are drawn by flipping `setExpanded`, which rebuilds their children, so they can never hit pi's own one-width cache; measured on a 938-component session: warm ~6 ms, cleared ~2.7 s. Staleness is handled by the per-component signature and by the cache *generation* — never by clearing — and components must be stable across frames or they miss this cache and defeat the prefix cache too. **`sigFor` is the correctness surface**: a component that signs as a constant is frozen at its first frame, and pi puts one in the chat container — `showStatus()` keeps ONE `Text` and rewrites it in place, so the pager showed the session's first status forever. The generic signature is content-aware (text length plus an O(1) hash of its tail), and any future signature must keep that shape: cheap, and blind to nothing that changes on screen. A component of OURS mounted in pi's tree that renders from state it reads at render time — the HUD banner — has no text to hash and signed the constant `p`: a `/name` never reached the header (2026-08-23; the old banner's `Model:` would have frozen the same way on a `/model` switch, masked by the footer). Such a component exposes `wdSignature()` — everything its render reads, O(1), clockless — and `sigFor` consults it before the text heuristic. The banner's session name is cached on `getLeafId()`: pi's `getSessionName()` filters a copy of every entry per call, and every appended entry (a `/name`'s `session_info` included) advances the leaf, so the leaf is the O(1) key. **Cached renders carry no clocks**: a glyph that should blink is cached with the phase-free `BLINK` (`\x00b`) prefix and the render loop decides glyph-or-blank at paint time; anything time-varying baked into a cached render freezes at a random phase (the 500 ms blink sampled by a 1 s signature bucket rendered blank 100% of the time). The tail is cached by signature like everything else — an always-fresh tail once re-rendered `/changelog`'s 491 KB markdown on every keystroke — and the one-column dedent of informational beats is a splice of the literal lead space, not a `sliceByColumn` re-emit (674 ms per flatten on 8683 rows).

**Clustering happens at assembly, and the prefix cache never swallows an OPEN cluster.** Merging is done in `emitSub`'s pending buffer, so member render caches are untouched and a toggle bumps `clusterGen` — part of the flatten key, because no component signature changes on that click (thinking toggles key on a per-component PRE key, so a message's thinking beat and prose beat never collide in `beatRows`). The prefix cache ends BEFORE a batch still forming (`flatPrefixComps`): the old forced drain at the boundary split the last turn's cluster permanently, since the boundary always sits two components from the end; the straddling beats re-emit each pass from their per-component caches. The follow-hold that smooths a streaming handoff dip must be released by `contentReplaced()` (`/tree`, compaction) and `turnSettled()` (the settle collapse) — both looked like dips and were held for 1.5 s.

**An `export let` read by another module is BROKEN under jiti.** The cache generation was `export let cacheGen`, imported by `surface.ts`; jiti compiles that import to a snapshot, not a live binding, so `bumpCacheGen()` climbed one copy while every comparison read a frozen `0` — `invalidate()` retired nothing and a live theme change left the transcript in the old palette. It is a function now (`getCacheGen()`), and the rule is general: cross-module mutable state travels through a function. Audit with `grep -rn "^export let"`.

**Not every foldable is a tool — the act branch is gated on a NAME.** Four of pi's own components answer the `setExpanded`/`expanded` duck-type without being tools (`!command`, `/compact` and `/tree` summaries, skill invocations); everything inside that branch reads `toolName`/`args`/`result`/`isPartial`, so all four signed the same constant and the cache served their first frame for the session — a running `!command` showed its opening border and never a byte of output — while clustering called them `called 1 mcp`. `foldName()` names them, the branch is gated on it, and each named beat owes an `actSentence` case, its own O(1) state in `sigFor` and a cluster verb.

**A delivered background result is an ACT, and its fold state lives in the pager, not in pi.** The `subagent-result` and `bash-result` custom messages are `CustomMessageComponent`s — no `setExpanded`, no `expanded`, no `toolName` — so they fell to the generic branch and rendered as a flat box: never folded, never clustered, no glyph, the whole answer on the surface (demonstrated). `ownResultKind()` names them and `renderSubFresh` builds the act itself from the renderers' shared parsers (`parseSubagentResultMessage`, `parseBashResultMessage`), keying the toggle on the component through `toolOverride` like every tool; `sigFor` signs them by fold state (`r0`/`r1`) because the text is immutable after delivery, and the snippet flag rides in the cache key as for every beat. Do not route them back through the tool branch: it reads `callRendererComponent`/`result`/`isPartial`, none of which exist here.

**A tool's result can arrive WITHOUT a result renderer — and a call without a call renderer.** When `renderResult` is missing or throws, pi leaves `resultRendererComponent` undefined and adds a plain `Text` of the whole output to the render container (`createResultFallback`). The evidence split read only the field, so those results vanished — and the bundled adapter's `renderMcpToolResult` throws on any result with no `details`, i.e. every server that answers in plain text. The split now falls back to the render container's children; the blank-row heuristic cannot serve, because pi's fallback `Text` sits flush against the call. The mirror case (2026-08-20): a definition with NO `renderCall` — the adapter's `mcpScript` — gets `createCallFallback` (the bold name alone) with `callRendererComponent` undefined and the result component right under it, no blank between; the whole-render blank-row split then read name + result as ONE call block, and the args rebuild that splices in after row 0 replaced the result with the args — an mcpScript panel showed its code and never its output (demonstrated). Same cure: child 0 of the render container (`selfRenderContainer` for a `renderShell:"self"` tool, else `contentBox`) is the call, the rest is the result.

**Raw markdown is not authored markdown: highlight.js's emphasis rule spans lines.** Its `_…_` emphasis opens at any `_` not followed by space and runs to the NEXT `_` — across lines — and nothing highlights inside the span. The mcp-scripting skill's second line is a path (`…/node_modules/pi-mcp-adapter/…`), so the one underscore in `node_modules` italicised and un-coloured the whole rest of the skill, headings and fences included, carried row to row by `carrySgr` (demonstrated 2026-08-20; the maintainer saw "why is it italic" and a heading that was not a heading). A `.md` read with a path in it did the same. `syntax.ts` registers `markdown-field` — the markdown grammar minus emphasis — on pi's own highlight.js instance and highlights every markdown body under it; `**strong**` keeps its bold. Do not paint markdown with the stock grammar again, and do not "fix" it by stripping italic from the painter: the span would still swallow the highlighting of everything after it.

**Thinking classification must never compare raw text.** pi rebuilds the assistant component's children on every streamed token, from TRIMMED blocks with empties skipped, so an exact-text match failed on transient whitespace, classified thinking as prose for a frame, rendered the full markdown (17–35 ms) and swung the beat's height by hundreds of rows — the "expands and recollapses" flicker. The structural marker (Upgrade Contract) is the fix; a text-length memo made a transient mismatch permanent and must not return. And streaming means the message is open AND nothing landed after the thinking — pi's partial messages carry `stopReason:"pending"` to the very end, so detection tests `!stop || stop === "pending"`; a bare truthiness test read every streaming message as settled, which is how the moving tail silently never fired.

**The working thinking window WRAPS; it never truncates.** The moving tail was the last 5 non-blank source lines each cut at the width, and a thinking paragraph is one long source line: once it outgrew the row its visible prefix stopped changing while every further token streamed invisibly until the newline — the view froze for 200–500 ms and jumped, on every paragraph, which read as "streams, then freezes, then batches" (demonstrated with `dev/mock-llm.mjs` `seq2`, a 400-column thinking line: 14 screen gaps > 150 ms against stock's 1; wrapped, 2 vs 1, both the tool's own sleep). The window is 5 display ROWS built from the wrapped source lines nearest its edge (from the end for a tail, from the start for a head), so cost stays O(rows shown) and the height never changes; the counter still says lines. Truncating a streaming line anywhere on the surface reintroduces this.

**pi's root layout is a shape, not a count.** 0.83 mounts header, loaded-resources and chat containers directly on the TUI; 0.84.2 wraps them in one `documentContainer`. The flatten reads one level below each head kid, so on 0.84.2 it saw three bare Containers, signed them as generic and froze on its first frame with no error. `unwrapContainers` expands a bare `Container` whose every child is a bare `Container` — by class identity, because message components carry `.children` too and a structural test would flatten messages into their parts.

**pi's `theme` is a LIVE PROXY, so captured references stay current** — a closure that calls `theme.fg(...)` in `render()` repaints after a theme change even though pi never re-invokes header/footer/widget factories. What goes stale is anything BAKED into a string at install time (`setWorkingIndicator({frames})` froze the spinner's palette until the frames were rebuilt on `agent_start`), and an IDENTITY comparison against the proxy is dead code — the same object on both sides of every change, which is why the pager's theme sync and its baked-SGR cache never noticed one. Compare a value: `theme.fg("accent","\0")` differs the moment the palette does.

**The field palette runs on pi's highlighter, reached from the running pi.** pi's public `highlightCode` paints with the live theme's `syntax*` tokens and nothing else, so prose code blocks and panel evidence had one palette; `visual/tools/syntax.ts` loads pi's `dist/utils/syntax-highlight.js` (`highlight(code, {language, theme})` — a scope→painter table over highlight.js) from `realpath(process.argv[1])`'s directory — argv[1] is the `pi` bin symlink, not `dist/cli.js` (demonstrated: the un-realpath'd test failed and every panel silently fell back to the stock palette) — and paints with `wdSyntax*`; a miss falls back to `highlightCode`. Read/write/edit/bash keep every character (highlight.js wraps, it never transforms). And the pager no longer strips EVERY background from tool rows: pi's card tint is removed sequence-exactly (`stripBgSeqs` with the theme's tool*Bg opens and the `49m` closers), so a diff tint or a code pill survives; the old `stripBg` made a tinted diff impossible.

**The model's prose is the terminal's colour unless a theme says otherwise.** pi's `getMarkdownTheme` paints headings, links, code, quotes, bullets — never the paragraph — and `AssistantMessageComponent` builds prose with no `defaultTextStyle`, so the body reaches the screen with no foreground SGR at all; the theme's `text` var was never on it, and an ivory `text` changed nothing (demonstrated by the gallery: the captured prose row carried no fg). `wdProse` is the token that does reach it, through `renderProseChild`'s shadow Markdown; `""` keeps the terminal default. Do not paint prose by wrapping rendered rows — the inline `\x1b[39m` resets after every code span end the wrap mid-row.

**A truncator is not a splitter.** `wrapPlain`'s hard-break called pi-tui's `truncateToWidth` with no ellipsis argument, so it appended `"..."` plus a reset and `head.length` counted characters never shown — 30 in, 14 out. Use `sliceByColumn` for splitting: a true prefix for plain text, lossless across ASCII, CJK and emoji, with `strict` keeping a wide grapheme inside the column. **`stripAnsi` handles APC (`\x1b_ … BEL`) before the catch-all** — pi marks the hardware cursor that way and the subagent renderer marks run rows the same way — and strips the charset designators (`ESC ( 0`, `ESC ) B`, `ESC *`, `ESC +`) and `ESC #`/`ESC %` whole, because the two-byte catch-all left their payload byte as text (`\x1b(0lqk\x1b(B` → `0lqkB`).

**The wire view rides CTRL+CLICK; the head-row button is retracted.** The first build (2026-08-22, morning) put a visible `raw`/`pretty` control on every expanded head row; the maintainer retracted it the same day ("looks weird") for ctrl+click — `ctrl?: boolean` on a click range, invisible to plain clicks, resolved in `handleCtrlClick` AFTER token-open (a path still opens) and BEFORE the "Can't open" notice. Three mechanisms the button paid for, still load-bearing: (1) rows out of a renderer's `render(width)` arrive WIDTH-PADDED with trailing spaces (the `spanOf` rule), so appending anything to a head row — today the dim `· wire` tell — parks it past the edge where the render loop slices it off, invisible (demonstrated on the subagent head: the trace logged `ev=wire` for a control nobody could see); slice to the visible width (`sliceByColumn`) first and reset attributes so an open bold never bleeds in. (2) A solo cluster summary takes its click action from the beat's first `s === 0` range — with ctrl ranges on collapsed beats that find must SKIP them, or every solo summary silently becomes a wire toggle instead of a fold. (3) `renderSubCached` copies RenderedBeat fields EXPLICITLY into the cache — the button's `wireBtn` field was never added to that list, so cluster members rendered from cache silently lost it (latent, removed with the field); any new RenderedBeat field must be added to that copy list or it exists only on fresh renders.

**Every row a beat contributes must fit AFTER its seat shift — width-10 for evidence, width-5 for a sentence.** A beat renders once and is drawn in two seats: standalone, and as a cluster MEMBER three columns to the right (its evidence chunks deeper still). Three cut-offs were paid for on 2026-08-22 before the rule was written down: a thinking text wrapped at width-6 lost its last characters as a member (`Now the fina`), pi's error rows taken at the full width did the same (`please try aga`), and head sentences truncated at width-2 overflowed by one column as members. So: every wrapped body wraps at `width - 10` (the tool branch's `toolW`, the own-result branch's `inner`, thinking, error turns, wire evidence), every head sentence truncates at `width - 5`, and nothing appends to a row without slicing it to its visible width first. The INSTRUMENT is the trace: `PI_WARDOGS_TRACE` logs `ev=overflow` for any row that breaks this (emitBeat and emitMember check every row of a fresh beat against the content width plus its shift — trace-only, zero cost otherwise). The audit that ships a change to any renderer: replay a session with every tool kind, `ctrl+o`, and `grep -c ev=overflow` at 140, 80 and 60 columns — zero each (2026-08-22: 0 / 0 / 0 on the 4,900-row reference session).

**Emoji width is a known, unfixable one-column offset.** Terminals that ignore `U+FE0F` draw `base + VS16` in one column while pi-tui counts two. Correcting our own measurement makes the line `width + 1` by pi-tui's reckoning and `compositeOverlays` truncates overlay lines with *its* measure — taking the scrollbar. A bar one column in beats no bar; do not retry this from inside the extension.
### The mode switch and pi's surfaces

**CONTROL IS SETTINGS-ONLY; OFF-AT-BOOT REGISTERS NOTHING.** pi cannot unregister a tool, command, renderer or message renderer, and it wires a tool's input and renderers at `session_start`/build time — so a LIVE toggle both froze the pager (registering its `onTerminalInput` handler after `session_start` had already fired left the overlay deaf) and leaked rendering into off (a component holds the tool wrapper it was built with). The robust answer is to have no live apply at all: `/war-dogs on|off` WRITES `war-dogs.enabled` into `<agentDir>/settings.json` (`writeEnabledSetting`, preserving every other key, temp+rename) and calls `ctx.reload()` — every state is a fresh BOOT. `installOnce()` (all tools, skins, pager, HUD, MCP, attachments, the theme-file install) runs once at LOAD when `bootEnabled()`, BEFORE `session_start`, so the pager's input handler is in place when it fires. A boot with war-dogs off calls `installOnce` never; the ONLY unconditional registrations are the `/war-dogs` command (the way back on) and the invisible lifecycle handlers. So a boot-off is byte-for-byte stock because the extension made no calls — proven by replaying a transcript full of MCP/subagent/bash/webfetch calls under boot-off and diffing against `--no-extensions` (identical, text and colour). Default is OFF (`settingsEnabled()` is `enabled === true`). Do NOT reintroduce a live apply or move registration off the load path — that brings back the freeze and the leak. The live-toggle machinery was deleted 2026-08-19 once each piece was proven unreachable (no caller, or a flag with no writer): `applyMode`'s off branch and its stock-definition re-registration, the HUD/attachments/pager `disable()`s, `resyncToolComponents`, the renderer gates (`gateRenderersOnMode`), the in-memory `enabled` flag and every `isEnabled()` gate, the slash-list filter, the MCP facade's skill parking and `disable()`. What makes the deletion safe is pi's own `setBeforeSessionInvalidate(() => resetExtensionUI())` plus a fresh `ExtensionRunner` on every `/new`, `/resume`, `/fork` and `/reload`: nothing registered in one boot state can be reached from another, so no gate has anything to defend. The ON system prompt was byte-identical before and after the deletion; off = stock on every instrument.

**A skin re-declares prompt metadata and passes `stockToolOptions()` — `wrapToolDefinition` is why.** An extension tool REPLACES the built-in in the registry the system prompt is built from (`_refreshToolRegistry`; `_toolPromptSnippets`/`_toolPromptGuidelines` derive from it with no built-in fallback), and `wrapToolDefinition` — which every `create*Tool` factory returns — drops `promptSnippet`, `promptGuidelines`, `renderCall`, `renderResult` and `renderShell` (`createBashTool` alone `Object.assign`s its metadata back). Registering a bare `create*Tool` result under a built-in's name therefore strips its snippet and guidelines from the prompt — it did, for as long as the old live-off path re-registered the stock factories (three snippets and six guidelines gone whenever war-dogs was off); renderers fall back to the built-in, prompt metadata does not. And an option-less definition is not the stock one: the skins pass `stockToolOptions()` — `settings.shellPath`, `shellCommandPrefix`, `images.autoResize` — because without them the model's commands ran in a different shell than stock. The skins check in Debugging is how you prove the four stay byte-identical to pi's definitions.

**Anything PERSISTED needs its renderer ABSENT while off, not only its write site gated.** `loader.ts` appends `gen-time` entries into the session JSONL and pi has no `unregisterEntryRenderer`, so gating only the append left every earlier session drawing `✸ Generated in …` while off. Under the live toggle the renderer returned a falsy component when disabled — exactly stock (`addCustomEntryToChat` bails on a missing renderer, `CustomEntryComponent.rebuild` on a falsy one; it must not throw, which paints an error box). Today the renderer is simply never registered on a boot-off (`installOnce`), which is that fallback by construction; the rule that remains is never to register an entry or message renderer outside `installOnce`.

**Never "restore" pi's header/footer/widget slots from the extension.** pi keeps ONE `customHeader`/`customFooter` slot and `setHeader(undefined)` restores pi's built-in — no stack, no memory of a previous owner — so the old live-off's restore, when ungated, evicted a surface war-dogs never installed (with `{"banner": false}`, turning off tore down another extension's header). There is no restore path any more: pi's `resetExtensionUI` clears the slots before every session switch and reload, and off never installs. Do not add one.

**Off restores the theme pi HAD, not a theme war-dogs derives.** Stock resolves the startup theme from `settings.theme`; re-deriving a default painted a different palette than `--no-extensions` for anyone with a non-default theme (`light` → off showed dark), and a hand-rolled COLORFGBG rule disagreed with pi's on 88 of 256 indices. So the user's theme is SAVED, never derived: `/war-dogs on` keeps it under `war-dogs._prevTheme` and `/war-dogs off` writes it back. **The MAIN theme is pi's, set via `settings.theme` + reload; only the pager's `visor` sub-theme is an in-memory object.** war-dogs installs its palette FILES into `<agentDir>/themes` on the first ON, and `/war-dogs on` writes `settings.theme` to the war-dogs palette (saving `_prevTheme`) and reloads — pi then applies it to chrome and content in one pass, no race. An in-memory `setTheme(object)` was tried and RETRACTED: it ran AFTER pi's reload had already rendered the transcript, so pi's content components cached the old palette while war-dogs' chrome showed the new one (code spans stayed dark). Because control is settings-only (reload), the save/restore is clean: OFF puts `settings.theme` back exactly (deleting it when there was none). `visor` stays an object — it is the subagent view's own canvas, not pi's global theme, and `warDogsTheme`/`loadThemeFromPath` (via `pidist.ts`) build it on demand. No stderr on the happy path (any stderr line lands in pi's TUI pane and would fail the harness).

**Project settings are ignored unless the project is TRUSTED, and war-dogs must mirror that exactly.** pi blanks `<cwd>/.pi/settings.json` for an untrusted project and treats an undecided one as untrusted until the prompt is answered. Reading it regardless booted war-dogs OFF from a file pi had refused to load, and made the MCP adapter yield to a `packages` entry pi never installed. `settings.ts projectAllowed()` is the single gate (`ctx.isProjectTrusted()` once pi says; before that pi's `ProjectTrustStore` plus `--approve`/`--no-approve`); the feature block, `packages`, `war-dogs.expect` and `.pi/subagents/*.md` all go through it, and anything new that reads a project file must too.

**Never let the adapter see its own tools missing from the active set.** Its init calls `setActiveTools([...real, "mcp"])`, and the facade reads the adapter's writes as its intent (`wanted`): a tool of its own absent from `real` at that moment reads as "the adapter no longer wants it" and is dropped from `wanted` for good — demonstrated under the old live toggle (off stripped the set; off→on came back without `mcpScript`). So the facade never strips or parks MCP names any more — pi activates every registered tool at boot, the adapter's writes go through untouched, and `activateCustomTools()` only reorders (pi's tools as they are, then ours in registration order, MCP names as the adapter wants them), which is why the prompt's tool list is the same on every boot. Anything that removes an MCP name from the active set behind the adapter's back re-creates the bug. **One adapter instance per factory run**: pi re-runs the factory on `/new`, `/fork`, `/resume` without re-importing the module, and keeping the previous instance's captured handlers dispatched `session_start` to N instances while a stale forwarding set left the new object with no shutdown forwarder — MCP servers outlived pi. `register()` resets every capture map before installing.

**The sanctioned model-facing changes in the built-in re-skins, each deliberate; a new one needs the same scrutiny.** (5, 2026-08-30) The powershell skin carries exactly bash's set — our description, the `description` and `background` params, the background branch of `execute`, the abort completed with who — and nothing else; snippet and guidelines pi's verbatim; the rg/fd line is bash's alone.  (1) All four DESCRIPTIONS are ours since 2026-08-21 — one voice, zero direction, facts and contract only (the tool-descriptions proposal, git history, is the implemented spec); `promptSnippet`/`promptGuidelines` stay pi's verbatim on all four. (2) bash's optional `description` and `background` params, and the background branch of its `execute` (the only bash behavior divergence). (3) edit's `execute` wrapped only to make a rejected BATCH say so — pi applies a batch atomically but its error names one failing `oldText`, and the model retried edit-by-edit believing the others had landed. (4) read's TEXT path is ours (2026-08-21): cat -n numbered results, a bracketed metadata line on every read, an explicit `limit` honored past the cap (pi re-cut even explicit asks), the default cap pi's numbers line-aligned; images and all errors delegate to pi's execute byte-stock, and children are handed the same read. The custom tools (subagent/webfetch/kimi-websearch) carry NO snippet/guidelines — description-only, because a SYSTEM.md replaces pi's prompt and those fields reach nobody there. The skins check in Debugging verifies what must still match.

**It is one extension, not several.** pi loads each extension via a separate jiti call, so two extensions cannot reliably share a module; an earlier version passed state through `globalThis.__pi*` handles. One `index.ts` makes them ordinary imports; split it back apart and that coupling returns.

### The terminal and input

**Autowrap is OFF while the pager owns the screen (DECAWM, `?7l`).** pi-tui UNDER-measures complex-script graphemes — its clustering gives a Devanagari/Bengali base+matra ONE column while the terminal draws the matra as its own spacing cell (`[अंगिका]` measures 5, draws 7 in tmux; `[বিষ্ণুপ্রিয়া মণিপুরী]` measures 11, draws 18) — so a composited row padded to width-1 by pi-tui's count can be DRAWN past the terminal width. With autowrap on, the terminal then inserted a physical line break, the screen SCROLLED, and pi-tui's diff model no longer matched the screen: stale frame fragments — a second title bar with a stale scrollback %, banner shreds mid-panel, URL tails at column 0 — persisted until a full repaint (demonstrated 2026-08-22: the maintainer's Wikipedia fetch in VTE, reproduced byte-for-byte in tmux with the cached fetch file). `?7l` rides `MOUSE_ENABLE` and `?7h` rides `MOUSE_DISABLE` and every restore path (close, exit hook, SIGTSTP; the crash-recovery `printf` in Troubleshooting carries it too), so an overwide row now CLIPS at the last column — the benign, emoji-class artifact. Do NOT fix this by correcting the measurement instead: that is the emoji entry's dead end (compositing truncates with pi-tui's measure — the scrollbar goes). Stock pi never touches DECAWM, so the unconditional `?7h` restore is always right.

**A missing opener is an ASYNC crash, not a caught throw (2026-08-30).** `spawn("xdg-open", …)` for a binary that is not on PATH does NOT throw — it returns a child with no pid and emits `error` a tick later, and an `error` event with no listener is an uncaught exception, so pi exits 1 with no `session_shutdown` (the alt screen and mouse modes stranded, the entry below). The old ctrl+click openers wrapped the `spawn` in `try/catch`, which the async error walks straight past. `util/opener.ts` (`openExternal`) listens for `error` and `spawn` and resolves `{ ok, reason }`, so a ctrl+click on a machine with no opener says `Open failed: xdg-open: spawn xdg-open ENOENT` on the footer instead of taking pi down (probed: a scrubbed PATH returns `ok:false` and the process stays alive; with `xdg-open` present, `ok:true`). It is also the one place the opener command is chosen by platform — `xdg-open` on Linux, `open` on macOS, `cmd /c start "" <target>` on Windows (the empty title argument keeps a quoted path from being read as the window title); the non-Linux commands are reasoned from their manuals, not yet driven. The general rule this pays for: a `spawn` whose failure must not crash pi needs an `error` listener, never only a `try/catch`.

**The alt screen and mouse reporting are OUR terminal state; pi restores only what it enabled.** Two exits bypass every hook — an uncaught exception (pi calls `process.exit(1)` with no `session_shutdown`) and `ctrl+z` (pi stops its TUI and SIGTSTPs the group) — and both left the shell in the alt screen with mouse tracking on, moving the mouse typing junk into the prompt. While the pager is open `mod.ts` registers a `process.on("exit")` restore, a SIGTSTP hook that restores the modes, parks the cursor below pi's stale frame and then really stops (SIGSTOP — a listener replaces node's default), and a SIGCONT hook that re-enters; all removed at teardown. On a quit the teardown must run synchronously inside `session_shutdown`: pi's `done()` settles our promise on a microtask, and pi printed its resume line and exited before that ran. When pi owns the alt screen itself (0.84+ fullscreen) none of the 1049 writes happen — DECSET 1049 is not reference-counted and our close dropped pi out of its own alt screen.

**Esc takes an accidental prompt back by rewinding the leaf, never by holding the prompt (2026-08-30, the maintainer's ask).** Two designs were weighed: hold every prompt for a window before sending (nothing ever enters the transcript, but every submit pays the delay and the held text must be re-fed through the stamp and attachment transforms by hand), or rewind after the fact with pi's own primitive. The rewind won: `navigateTree(id)` is what `/tree` does — it moves the leaf, rebuilds the agent's context from the branch, emits `session_tree` (the pager already follows it), and destroys nothing (the entries stay on the abandoned branch). The rule that makes it safe: the undo runs only when the aborted turn was the one the prompt started (recorded at `input`, taken by the next `agent_start`) and every entry after the remembered leaf is the prompt, war-dogs' own riders on it (the brief, the inject files — re-injected honestly on the next prompt, since the once-per-session scan reads the branch) or the cut assistant message; a tool result or a DELIVERY after the leaf refuses it with a status line — a reply consumed into the turn would be lost with the branch, the maintainer's worry, and background agents and jobs are process state the rewind never touches. A reply that arrived while the turn streamed prose is a different case: it waits in pi's steer queue (a steer is read at a tool boundary), pi's Esc clears that queue, and the held-delivery rule re-sends it with the next prompt — so the undo proceeds and nothing is lost (asserted: the job's reply rides the prompt after the undo). Two pi facts paid for: `navigateTree` is on the COMMAND context only (`ExtensionCommandContext`; event handlers get the general context), so the settled hook arms the undo and dispatches `/war-dogs undo` through `sendUserMessage({expandPromptTemplates:true})` — pi executes an extension command before it persists or emits anything (`agent-session.js prompt()`); and the raw text is what the recorder sees because it is registered FIRST among the input handlers, before the attachment and stamp transforms. Regression `dev/undo-test.sh` (tmux, the mock): Esc mid-stream restores the prompt and clears it from the branch; Esc after a tool ran keeps it; Esc after a delivery landed in the turn keeps it.

**The external editor is a TUI stop, not a signal (2026-08-30, the pi-settings review).** `ctrl+g` (`externalEditor`) makes pi `ui.stop()` its TUI, spawn the editor, `ui.start()` again; the SIGTSTP/SIGCONT hooks never fire and pi restores only the modes it enabled, so the editor ran inside the pager's alt screen with any-motion mouse reporting on (demonstrated: a script as the editor read `alternate_on 1, mouse_any_flag 1` from tmux). `this.ui` is a Proxy that resolves the method on the live TUI at call time, so the pager overrides `stop`/`start` on that instance (arguments forwarded — `stop` takes options), restoring the modes on stop and re-entering on start, and puts the originals back at teardown. Inside the editor: `0 0`; the pager back after. Regression: the acceptance harness's `--editor` leg. Two smaller findings of the same review, fixed: a background bash job ran without the user's `shellCommandPrefix` (the foreground skin passed it through pi's option; the job spawned the raw command — `bgprefix`); and the trust gate read the store alone for a never-asked project while pi reads the store, then `defaultProjectTrust` (`always`/`never`), so a user whose global policy was `always` saw war-dogs refuse `.pi/inject`/`memory`/`subagents` that pi itself allowed (`dev/inject-test.sh`, the `always` case). And the review's method: every key in pi's `docs/settings.md`, its reader in `dist/`, its reader in war-dogs — recorded under Configuration.

**Close OUR overlay, never "the top one".** pi's `done()` → `hideOverlay()` pops the LAST overlay — the adapter's `/mcp` panel or any extension overlay pushed after ours vanished with its promise never resolving while ours stayed drawn. `done()` is used only while we are the top; otherwise the `OverlayHandle` from `onHandle` splices our entry by identity and the promise stays pending (pi leaves it pending on `/reload` too). And `wantOpen` gates the 120 ms open timer: a teardown inside that window (then a live off; now a `session_shutdown`, e.g. an immediate `/reload`) finds nothing to close and the timer would open the pager anyway — demonstrated as war-dogs off with the pager live.

**`onTerminalInput` runs before the focused component.** While a selector, the `/mcp` panel or a dialog holds focus every key is theirs — the pager's `ctrl+s`/`ctrl+r`/`ctrl+o`/PgUp bindings swallowed their save/reconnect/cycle keys (`/scoped-models` ctrl+s never saved). The handler bails whenever `tui.focusedComponent` is not the editor; `CTRL_O`/`CTRL_R` name the exact modifier (`;5u` — the loose form matched shift+ctrl+o, pi's tree filter cycle); PgUp/PgDn/Home/End and the station arrows follow Enter's yield rule (typing wins); a bracketed paste is one event and never a mouse report (a paste containing `ESC [ <` was swallowed whole as clicks); the station composites the live bottom UI like every view — pi's editor keeps focus everywhere, and a station without it was an invisible, live input bar (an unseen confirm dialog was answered Yes).

### The editor and attachments

**Rewriting the editor goes through the LIVE COMPONENT, never `ctx.ui.setEditorText`.** Turning a 45-character `/tmp/pi-clipboard-<uuid>.png` into `[^image 1]` is the feature, and it must work mid-sentence, because that is where people paste (drag/drop rewrites its bytes before the editor sees them; CTRL+V cannot — pi reads the clipboard itself and calls `insertTextAtCursor` with the temp path). The public route cannot do it: `setEditorText` is `editor.setText()`, which clears the paste registry and drops the caret at the end (a tail-only guard was tried and rejected — it left exactly the mid-sentence case broken), and `getEditorText()` returns EXPANDED text, so a collapsed `[paste #N +M lines]` block is inlined by any round-trip. So `syncEditorPaths()` walks the TUI (captured from our own widget factory — `ctx.ui.getEditorComponent()` returns the factory) to the live `EditorComponent`, reads `getText()` (marker form), snapshots `pastes`/`pasteCounter`/`getCursor()` around the write and restores the caret via `state.cursorLine` + `setCursorCol` — replacements never add newlines, so only the column moves, by the delta of every ref substituted before it. Every reach is optional: a missing field skips the write rather than doing it badly. Two rules bound the write: the paste REGISTRY is transformed with the text and read when the pipeline scans the editor (a ref inside a collapsed paste is invisible in the marker text and very much part of the message — scanning the expanded view while writing the marker form renumbered such a ref and left the text naming the old id); and a `!bash` or `/command` buffer is never touched — pi dispatches those itself, and a rewrite made the command run on the ref (`ls: cannot access '[^image'`).

**The attachment store survives `teardown()`, and its id space is PER SESSION.** Clearing it on teardown orphaned any unsubmitted `[^image N]` — no image, no def, dangling text — and because the watermark survived while the store reseeded from it, the id went to the next paste and the stale ref rebound to a different image. `rebuildFromHistory` carries editor-referenced entries back, and rebuilds the watermark from the ENTERED session alone: pi replaces the session on `/new`, `/fork`, `/resume` without restarting the process, and carrying the previous session's high-water mark let a pending `[^image 1]` (blue.png) resolve to the resumed session's `[^image 1]` (red.png) — the model described red. A collision never lets the visible ref mean the other file: with a live editor the pending ref is renumbered and the text rewritten in place; without one, the pending attachment keeps the id and history's def moves. Three rules of the same family: the rebuild is driven by the SESSION, not the UI — it runs from `session_start` (headless `pi -p --continue` attached without ever anchoring: one transcript held two files under `[^image 1]`) and again on `session_tree`/`session_compact`; the authority for "is this id taken" is HISTORY's def table, not the store (a def whose file was deleted freed its id, and the next message defined the same label for a different file); and a message pi RESTORES into the editor (`/fork`, `/tree`) carries its own footer, whose defs are re-registered before the footer is stripped — stripping them against a store that never saw those ids sent a bare `[^image 1]` and deleted the path the user could plainly read.

**Never send bytes pi's own image pipeline refuses, and never send bytes older than the file.** `resizeImage` returning null (or throwing) is a REFUSAL, exactly as pi's `processImage` reads it; keeping the raw bytes let a file with valid magic and undecodable content reach the provider, come back `400 failed to decode image`, and — the message being persisted — fail every later request in that session. A refusal attaches nothing, drops the def, says `[^image N] omitted: …` in one line and shows in the widget. Freshness: attachments are keyed by PATH and each matched ref is re-stat'ed at SUBMIT (`refreshAttachment`), because the old check ran only while the raw path was still in the text — a screenshot tool overwriting the same file re-sent the first capture for the rest of the session.

### WebFetch

**A tool's TEXT is the only thing the model reads — `details` is for rendering.** WebFetch rendered its `notes` only in the error branch, so every warning on a successful-looking fetch went nowhere (an empty extraction printed `[webfetch: ok · …]` and nothing). Empty says so; a small curated set of degradation notes rides on non-error statuses — small, because the fix for an unheard warning is not a wall of notes. **When you add a status rule, add it everywhere the status is decided** — the oracle (HTML), the non-HTML render branch and the static tier each decide, and each has been the one missed (no 401 case → a sign-in page classified `ok`; the ≥400 catch-all lived only on the non-HTML branch → a 402/451 error page with a paragraph of body was read as the article). Two cache rules of the same family: a FORCED refresh must REPLACE the cached entry (`noCache` used to bypass read and write, serving the superseded copy right back), and the in-flight dedupe must key on the render options as well as the url.

**A route handler fires ONCE, and a redirect is a second request.** Playwright calls `context.route` for the intercepted request and never again for a 30x it is allowed to follow — not after `route.continue()`, not after `route.fulfill()` of the 30x — so every render-tier SSRF check ran on the ENTRY url only, and a public page that 302'd to `127.0.0.1` was handed back as the article, `ok`, on `render` and on the default `auto`. The handler now owns the chain: `route.fetch({ maxRedirects: 0 })` per hop, `guardUrl` on every `Location`, a hop cap, cookies and `Authorization` dropped across an origin change, the final response fulfilled at the original request — so `finalUrl` comes from a requested→resolved map and HTML gets a `<base href>` injected. `context.request` (the PDF byte fetch) is not route-intercepted and follows its own guarded chain. Client-side vectors were always blocked; only the transport-level redirect was free.

**An IP is a number, not a string.** `isPrivateIp` matched IPv4-mapped IPv6 with a regex for the dotted form, but the WHATWG parser normalises `::ffff:127.0.0.1` to `[::ffff:7f00:1]` — which walked through every guard on every private range. The v6 test parses the eight groups and judges the embedded v4 target of v4-mapped, v4-compatible, v4-translated, NAT64 `64:ff9b::/96` and 6to4 `2002::/16` with the v4 rules; anything that does not parse is denied. Never re-introduce a textual match for an address family with many spellings of one address.

**One extractor, both tiers.** The static tier ran Readability+Turndown while the render tier ran `extract.ts`, so one URL gave two answers and the cheap one was quietly the worse: no table rule anywhere in that path (Wikipedia's S&P-500 list came back as 4 KB of prose, 0 table rows, gate `static-ok`, notes `[]`), unresolved relative hrefs, empty alts, and `structured`/`links` hard-coded empty. Both tiers run `extract()` on the HTML now (verified by identical saved-content hashes). Fork the two paths again and you have re-created a tool that answers differently depending on how fast the page was.

**A cap the reader cannot see is a lie about the page.** `extract()` and `pdf.ts` cut at 200 KB silently, and `capContent()` computed "showing 1860 lines of 7223" from the already-capped string and saved that string — "read the rest from line 1861" pointed at a file holding a third of the page. Those caps are memory bounds now (5 M chars), announced in the content and in a note when they fire, and the saved file is the uncapped extraction; the reading limit is `truncate.ts` alone. Related: `cut()` counted a partially kept line, so "resume at `keptLines + 1`" skipped that line's tail (a one-line 200 KB page said "resume at line 2"); `CutResult.partial` says when the cut landed inside a line and the text hands over a byte offset instead.

**Bytes are not UTF-8, and text is not binary.** `res.text()` decodes UTF-8 unconditionally, so Shift_JIS/GBK/latin1 pages arrived as mojibake, `ok`; the static tier decodes by Content-Type charset, then the document's declaration, then UTF-8, with a windows-1252 retry only when nothing was declared and the bytes are invalid UTF-8. `text/plain` threw on that tier (a null `documentElement` for a body with no leading tag) while the render tier captured the text and called it "binary resource", `ok` — robots.txt, raw READMEs and RSS were unreadable on every tier while reporting success. Textual bodies are returned verbatim, XML/RSS goes through the extractor, only real binaries get the placeholder; the three content-type tables (`static.ts`, `render.ts`, `fetch.ts`) must stay in step.

**A lock nobody owns is a lock nobody can break.** The daemon's `mkdir` spawn lock recorded no owner and was released only in a `finally`, which does not run when a process is killed; its window is the whole 25 s spawn-and-poll, so one Ctrl-C could wedge the render tier permanently. The lock carries its owner's pid AND that pid's `/proc/<pid>/stat` start time, and is broken on ESRCH, on a start-time mismatch (a recycled pid), or once it outlives the spawn budget by 10 s whoever holds it (an "alive" lock that could never be broken was as permanent as an unowned one — a 2-hour-old lock on a recycled pid cost every fetch 25 s, forever). On a dead pid break immediately — falling through to an age check kept a fresh orphan honoured for another 35 s. The refusal names the lock directory. And the daemon is spawned via `process.execPath` + `tsx`'s cli, with an `error` listener: a missing or non-executable `.bin/tsx` shim was an uncaught `spawn ENOENT` that killed pi.
