# war-dogs — the user guide

Everything you need to use war-dogs, end to end. This is the user's book: what you can do, what you'll see, and every fact that matters in practice. (The `README.md` beside it is the maintainer's book — internals, design history, debugging.)

**Where war-dogs comes from — read this first.** war-dogs is built around its maintainer's own stack and is public because sharing beats hoarding, not because it aims to be provider-neutral: it is Kimi-first (the web search tool runs on your Kimi login; the agent doctrine was validated on Kimi K3) and assumes Chrome is around (webfetch's render tier, the bundled Playwright-style MCP browsing — a system Chrome/Chromium is encouraged for the full experience). Everything degrades honestly elsewhere: without Kimi auth the search tool reports it plainly, without Chrome the fast fetch tier still works — and on OpenAI-API providers two tool descriptions exceed OpenAI's 1024-character cap and the API refuses them (Anthropic-shaped providers have no such cap). If your stack differs, war-dogs still works; it just fits best on a stack like the maintainer's.

war-dogs turns pi into a full-screen cockpit: a scrollback you can scroll, click, fold and select; agents — real pi sessions your model starts, steers, questions and waits on, plus other pi sessions on your machine it can message; a station showing every agent at a glance and a chat view for each; web fetch and web search tools; image attachments; a bundled MCP adapter; and a re-themed screen. Off, it is exactly stock pi — not approximately: byte for byte, verified.

## Turning it on and off

- **Install:** copy the folder to `~/.pi/agent/extensions/`. From a git clone, run `npm install` in the folder once. If you previously installed pi-mcp-adapter as a pi package, `pi remove npm:pi-mcp-adapter` (the bundled copy takes over; until then war-dogs steps aside and tells you).
- **On/off:** `/war-dogs on`, `/war-dogs off`, `/war-dogs status`. The command edits `war-dogs.enabled` in your settings and reloads — every switch is a clean boot. Equivalent by hand: `"war-dogs": { "enabled": true }` in `~/.pi/agent/settings.json`, then `/reload`.
- **Per-invocation:** `WAR_DOGS_ENABLED=0 pi …` forces off for that run, `=1` forces on; unset defers to settings. Handy for scripts, cron, and one-off `pi -p` runs. While the variable is set, `/war-dogs` tells you it's pinned instead of pretending to switch.
- **The switch is refused while anything is working** (a streaming turn, a running agent, a compaction). Wait, or stop the work first.
- **Themes are handled for you:** turning on saves your theme and applies a war-dogs palette; turning off restores yours. Pick a palette with `"war-dogs": { "theme": "canopy" }` (`canopy`, `canopy-cobalt`, `dune`, `oxide`) or live via `/settings → Theme`. Don't set pi's own `theme` key to a war-dogs palette by hand — let the switch manage it.
- **What off means:** stock pi, MCP included (it's part of the bundle). Two harmless traces remain: `/war-dogs` stays in the slash list (your way back), and the palette files stay in pi's themes folder.

**You'll want:** a configured model (agents and the fetch scout use it). Optional: a system Chrome/Chromium on PATH (webfetch's render tier; without it the fast tier still works), `poppler` for reading PDFs. Node ≥ 22.19.

## Reading the screen

The resting screen shows the conversation, not API noise:

- `●` white text — the model talking. A red dot marks an errored/aborted turn.
- Your prompts sit on a tinted box with a `❯`.
- Tool calls rest as **one-line sentences**: `executed bash • find, wc`, `Read util/shell.ts (214 lines)`, `Fetched github.com — ok · ~8k tokens`, `started agent • audit the pager`. Red = failed.
- Thinking rests as `thought for N lines`.
- When a turn finishes, consecutive tool lines merge into a **cluster**: `thought 2 times, executed 2 bashes · 1 failed`. While the model is working, each call instead leaks a few live rows so you can watch.

**Everything opens on click.** Click a sentence → its evidence unfolds (the command and output, the diff, the file body, the agent's reply). Click again → folds. Clusters open into their members; members open individually. `ctrl+o` expands/collapses *everything* at once.

**Wire view — full transparency on demand.** The pretty surface hides bookkeeping (timestamps, delivery headers, run ids). `ctrl+click` any tool act, delivery or prompt box to flip that one item to the verbatim model-facing text; `ctrl+click` again to flip back. `ctrl+r` is the whole-screen raw view — the escape hatch if a renderer ever looks wrong.

**Links and paths:** `ctrl+click` a URL or file path opens it in your system browser/viewer. Hover underlines what would open.

**Selection:** drag to select, right-click to copy. Your terminal's *native* selection needs its modifier (usually `shift`+drag) while the pager is open, because the pager owns the mouse.

### Keys

| Key | Does |
|---|---|
| wheel / `shift`+wheel | scroll vertically / horizontally |
| `PgUp` `PgDn` `Home` `End` | scroll / jump (they type into the editor when you have text typed) |
| click | open/fold a tool's evidence; open an agent's chat |
| `ctrl+click` | open link/path, or flip the item to wire view |
| `ctrl+o` | expand/collapse everything |
| `ctrl+r` | raw-source view on/off |
| `alt+s` | the station |
| `ctrl+s` | back one level (an agent's chat → the chat of the agent that started it, or main; the station → the view it was opened from) |
| `↑` `↓` + `Enter` in the station | pick and open an agent (only when nothing is typed) |
| `alt+up` in an agent's chat | pull that agent's queued messages back into the editor |
| drag / right-click | select / copy |

Everything not listed behaves exactly as stock pi; typing always wins over pager keys.

## Agents

Ask in plain words — "use an agent to audit the error handling", "spawn three agents, one per module" — and your model runs real pi sessions in the background. Each agent:

- **has its own context** — it knows nothing of your conversation except what the model writes to it (the model is taught to brief it fully);
- **shares your working directory** — its edits are simply there, for you and for every other agent;
- **keeps its transcript** — it can be continued, re-tasked and questioned later, even across pi restarts;
- **replies by delivery** — the answer arrives as a message in your conversation when it finishes (with duration, tool-call count and how full the agent's context window is; tokens and dollar cost only if you set `agent.discloseTokens: true` / `agent.discloseCost: true` — the model doesn't need them, you still see them in the station). Several finishing together arrive as one message. An agent that started agents of its own receives THEIR replies the same way, and its own reply reaches whoever started it only once its team is done (see the facts below).

### What the model can do with them (and what you'll see)

`run` start one · `message` steer a working one / continue an idle one · `ask` question one out-of-band without interrupting it · `wait` hold for its reply · `status` cheap peek · `stop` stop it and everything under it (it stays continuable; the reply says how many unread messages were dropped) · `list` show them all. On screen these rest as one-line acts (`started agent • title`, `messaged agent`, `held for 2 replies`…), each openable to its full text.

### Watching and steering — your controls

- **The activity strip** below the footer shows what's running right now — agents, background commands, and an `/ask` in flight, one living row each.
- **The station (`alt+s`)** is the tree of every agent this session started (a resumed session's included): state glyphs (`✳` working, `◌` queued, `✔` done, `⊘` stopped, `✘` error), each run's task and configuration, a `✕` to stop one. Arrows + Enter or a click opens a run.
- **A run's chat view** is a full conversation with that agent, on a blue canvas so you always know you're not in main. **Type to talk to it directly** — your messages are marked as from you on the wire (the mark is hidden on screen like the timestamp; ctrl+click shows it), and images you paste reach it too; `Enter` steers a working agent at its next tool boundary, `alt+Enter` queues a follow-up for after its turn, exactly like main. What you and the model each say to the agent share one transcript. Slash commands still go to your main session.
- **Your hand on an agent, from its view:** `Esc` interrupts its current turn only — it stays alive and idle, its own agents keep working, and the model is NOT told yet. Type to it and the reply to your follow-up is what reaches the model, as the agent's reply (once the agent's own agents are done). If you don't follow up for ten minutes the model gets one transparency notice with what the agent had; the agent stays continuable. `alt+x` does the same and stops the agent's team. `ctrl+alt+x` stops it for good (the station's `✕`) and the model is told at once. In main, `Esc` is pi's own and never touches agents. After any interrupt — yours in a view, or `Esc` in main — nothing wakes that agent, or your session, on its own: what its agents reply, or what arrives for your session, waits for the next message to it (your follow-up, or your next prompt) and is read with it. Every key answers with a one-line notice under the run's footer.
- **`/ask <question>`** asks whatever conversation you're looking at — a focused agent, or your own session — *out of band*: the answer appears for you alone, costs no one's context, interrupts nothing, is never recorded. `/ask @<id> <question>` targets any agent or session by id. `/ask!` additionally hands the Q&A to your model as context.

### Facts worth knowing (the edge cases)

- **Stopping is not killing.** A stopped agent keeps its transcript; the model (or you) can continue it later with a message.
- **Messages never vanish silently.** A message to a *queued* agent (waiting for a concurrency slot) is held and handed over the moment it starts — the receipt says so. A failed send is an error, never a false "Delivered".
- **Deliveries batch:** results finishing within ~1.5 s arrive as one message (`WAR_DOGS_DELIVERY_WINDOW_MS=0` delivers each instantly).
- **`/new`, `/fork`, `/resume` ask first while agents or background commands run** — one dialog names what would be aborted; `Enter` proceeds, `Esc` keeps the session. `/reload` cannot ask (pi handles it before extensions see it) and quitting pi stops everything running; either way the model is told at its next prompt which agents and background commands died and why, once; an agent you continue later is told the same about its own agents. Such a run is filed `stopped` (⊘, with the reason on its station row), never as an error.
- **Leads and teams.** An agent that starts agents of its own is a lead. Its reply reaches whoever started it only when its own agents are done: ending a turn while they work sends nothing, their replies wake it, and the turn that ends with an idle team is what travels. Meanwhile `status` says it is "waiting on N agents of its own". By default an agent can `message`, `wait` on and `stop` only the agents it started itself (`reach: "session"` opens the whole session to it; a grant is never wider than the granter's); `ask`, `status` and `list` reach everyone; nobody can stop its own principal.
- **Headless (`pi -p`) has no deliveries** — there's no conversation to wake. The model is told so and holds for replies with `wait`. Works fine; just different plumbing.
- **Agents are session-scoped, for the model and for you.** The station and the model's `list` both show this session's runs only (verified 2026-08-28: a second session in the same folder sees none of them). Other sessions appear as peers, not as runs.
- **What an agent gets:** the same model and thinking level as your session (unless configured otherwise), pi's file tools in war-dogs' form, webfetch, web search, active MCP tools, and your project's `AGENTS.md` context. Pi's stock `grep`/`find`/`ls` are trimmed for agents and for your own session alike — bash with rg/fd covers them; "war-dogs": { "stockTools": true } brings them back. It gets **no skills and no prompt templates**, and no agent tool of its own unless granted `depth`. A `tools` list is exact: `tools: ["read"]` means read and nothing else. Its own numbers — how many agents it may start and keep running, its per-turn time limit, whom it may reach — are stated in its agent tool's parameter descriptions. Agents run on the same base prompt as your session, verbatim. Your `SYSTEM.md` is main's alone and never reaches agents; to set your own agent default, write `SUBAGENT_SYSTEM.md` (in `~/.pi/agent/`, or `<project>/.pi/` once trusted). A named agent's body always wins, and every agent additionally gets a short standing note on being a subagent (what it is, how the first line of every message tells it who wrote and whether this turn's output goes back to the agent that started it, and that communication is one way — wrapped in `<agent-exchange>` tags so it reads as the tool's voice, not your prompt's), whatever prompt it runs on — `"agent": { "exchange": false }` turns that note off if you want custom prompts left entirely alone. Every message you type in an agent's view reaches it as `[from your user • …]`, the rest of the line saying whether your turn stays with you or, mid-task, still goes back to the agent that started it.
- **Very long replies** are cut at 200k characters; the whole text is saved to a temp file and the note names it and the line the rest starts at (the same rule as background bash output). Several long replies arriving together are cut to their share of one message.
- **Every message and result carries a timestamp**, so the model always knows what time it is. These are hidden on the pretty screen (ctrl+click shows them).
- **The model sees context windows** — each agent's fill on status/replies/list, its own session's at the top of a bare `status`, and a note when an agent's context was compacted mid-run — so it can judge when a worker is worth re-tasking and when its own window needs care.

### Named agents — your own roster

Drop a markdown file in `~/.pi/agent/subagents/` (or `<project>/.pi/subagents/` — read only once you've trusted the project):

```markdown
---
description: reviews diffs ruthlessly
model: kimi-coding/k3
effort: high
tools: read, grep, bash
---
You are a code reviewer. You hunt correctness bugs first, style never. …
```

The body is the agent's system prompt (required — a file without one is skipped, with a reason). Frontmatter may set any run parameter: `model`, `effort` (`thinking` works too), `tools`, `excludeTools`, `cwd`, `timeout_s`, `depth`, `concurrency`, `reach`, `extensions` — but not `systemPrompt`/`appendSystemPrompt`: the body IS the system prompt (a stray one is ignored with a warning; callers can still override per run). The model sees your roster with descriptions and picks by name; call arguments override the file.

### Configuration and budgets

In `settings.json`, an `agent` block sets defaults for every run (same keys as frontmatter), plus three **ceilings nothing can raise**: `maxDepth`, `maxTimeout_s`, `maxConcurrent`.

Built-in defaults: `depth 0` (an agent can't start agents unless granted), `concurrency 8` (more queue, then start as slots free; a grant is never more than the granter's own), `reach team` (an agent reaches only the agents it started), **no timeout** (a run works as long as it needs; a timeout is per turn and re-arms each time the agent is given work; set one per call, per file, or in settings — the model is told to leave it alone unless a runaway would cost more than a late reply). `discloseTokens` / `discloseCost` put token counts / dollars back on the model's surface. Your own agent default is `SUBAGENT_SYSTEM.md`, your own agent append `SUBAGENT_APPEND_SYSTEM.md` (in `~/.pi/agent/`, or `<project>/.pi/` once trusted); pi's `APPEND_SYSTEM.md` is main's alone, like `SYSTEM.md`. `extensions` is a file-and-settings key only; a named agent naming war-dogs itself is refused with a note.

### Peers — your other pi sessions

Every pi session with war-dogs on (on the same machine) is addressable: the model's `list` shows them as `session_…`, and it can `message` or `ask` them — so two of your terminals can collaborate, or an agent can report to another session (an agent reaches your session's main agent by `ask` always, by `message` only with `reach: "session"`). Two sessions may talk for as long as they like; nothing stops them but you. You can too: `/ask @session_… <question>`. Facts: message storms are throttled (rate limit + duplicate detection, always answered honestly); a closed session simply refuses ("no longer running") — there is no inbox; nobody can `stop` a peer — it has its own user. Don't want your sessions addressable at all? `"peers": false` — no socket, no Peers anywhere, agents unaffected.

## The tools you gain

**webfetch** — fetches a URL and returns *typed truth*, not just bytes: `ok`, `login-wall`, `bot-wall`, `js-shell`, `paywall-hard`, `not-found`, … A fast HTTP tier escalates to a real-Chrome render tier when needed (`auto`). Long pages are cut at a reading limit (2000 lines / 50 KB) with the full page saved to disk and the model told how to resume. Private/internal addresses are blocked on every hop. With `expect` set, a scout can fetch-and-judge candidate URLs for the model (`war-dogs.expect` in settings configures it). Env knobs: `WEBFETCH_CACHE_TTL_MS` (60000), `WEBFETCH_CONCURRENCY` (4), `WEBFETCH_DAEMON_IDLE_MS` (600000). For yourself: `npm run fetch -- <url>` in the folder is the same engine on the command line.

**kimi-websearch** — web search through your existing Kimi login (no extra key; it uses the same credentials pi uses for the kimi provider). Supports `site:`, `-term`, `"exact phrases"`, `after:`/`before:` dates.

**Background bash** — the model can run `bash` with `background: true`: the command detaches from the turn (Esc won't kill it), the output arrives later as a delivery with the exit code. Output is capped at 200 lines for the model, with the full output saved to a file it's told about. Jobs die with the session (`/new`, quit). Note: a command merely *ending* in `&` detaches silently and its output never comes back — the model is expected to use `background: true` instead.

**Image attachments** — drag a file into the terminal, `ctrl+v` a clipboard image, or type a path (several separated by `,` or `;`): each becomes a `[^image 1]` reference in your text, sent as a real image. Works mid-sentence, works after `/skill:…`, works when typing at an agent. `ctrl+click` a reference to view the image. One gap: images typed *during* a compaction arrive unresolved.

**MCP** — the pi-mcp-adapter ships inside: `/mcp` (panel), `/mcp setup` (write a server config), `/mcp-auth`, the `mcp` gateway tool, per-server direct tools, and an `MCP:` status in the footer. Configure servers in `.mcp.json`, `~/.config/mcp/mcp.json` or `<agentDir>/mcp.json`. Agents get MCP tools too. All of it turns off with war-dogs.

- **PowerShell** gets the same treatment as bash where it is your shell (Windows): a `description` sentence on screen, background commands with the same receipt and delivery, stamped results, and agents inherit it. Off Windows pi does not run it, and neither does war-dogs.

## What your model is told

war-dogs gives your model its own system prompt — a conduct base (how to verify, when to ask, how to report; no tool docs, those travel with each tool) replacing pi's stock default. On the first turn of each session the model also receives a one-time **session brief**: your OS, user, shell, date and timezone, the working directory and its git state, pi's and war-dogs' versions and paths, and — for models war-dogs knows (Kimi K3) — a knowledge-cutoff note. On screen the brief rests as one dim line (`session brief · environment and runtime`, or `received the session brief`); click it for the facts, ctrl+click for the verbatim text the model received.

- **Your own SYSTEM.md always wins, whole.** Put one in `~/.pi/agent/` or `<project>/.pi/` (once trusted) and war-dogs stands down completely — your prompt, no brief, exactly as stock pi behaves. `APPEND_SYSTEM.md` still appends over either base.
- `"war-dogs": { "prompt": false }` keeps pi's stock prompt while the rest of war-dogs runs.
- If war-dogs cannot reach pi's prompt assembler after a pi update, it says so once on stderr and pi's stock prompt stays in force; the brief still arrives.

## Injected messages — your own standing text

Two plain files, sent to your model word for word as messages (no wrapper, no rewording): `~/.pi/agent/inject/SESSION_START.md` arrives once per session, on the first turn; `~/.pi/agent/inject/PER_TURN.md` arrives with every prompt you send (not on a turn that an agent's reply starts by itself while you are idle — pi does not announce those to extensions). A project can carry its own pair in `<project>/.pi/inject/` — once the project is trusted — and both pairs ride when present, global first. Use SESSION_START for standing context that should be read once (who you are, what this machine is for, a long brief) and PER_TURN for the line or two that must never fall out of the model's attention (a rule you keep catching it breaking). Facts to know: each PER_TURN copy stays in the conversation, so the model re-reads every earlier copy too until compaction — keep that file to a few lines; SESSION_START is remembered per session (a `/fork` keeps it, a resumed older session gets it at its next turn) and compaction may fold it into the summary; a blank file sends nothing; your own SYSTEM.md does not switch these off (they are yours too); agents never receive them. On screen each arrival rests as one dim line (`injected PER_TURN.md · global`; `received 4 injected messages` when clustered) — click it for the text, ctrl+click for the exact bytes sent. `"war-dogs": { "inject": false }` turns the feature off.

**A project pi never asked about.** pi asks "trust this project?" only when it finds its own kinds of project files under `.pi/` (`settings.json`, `SYSTEM.md`, `APPEND_SYSTEM.md`, `extensions/`, `skills/`, `prompts/`, `themes/`) or a `.agents/skills/` up the tree. A project whose only `.pi/` content is war-dogs' (`inject/`, `memory/`, `subagents/`) is never asked — and war-dogs does not read those until you say so: it warns once at startup, `/trust` (pi's own command) records the decision, and `pi --approve` allows it for one run.

## Memory — what your model keeps between sessions

Off by default. Turn it on with `/memory on` (or `"memory": { "enabled": true }` in settings — a top-level block, not under war-dogs; `WAR_DOGS_MEMORY=1|0` per run). On, your model is told to keep a memory: plain markdown notes — global ones in `~/.pi/agent/memory/`, project ones in `<project>/.pi/memory/` (created once the project is trusted) — with an index (`MEMORY.md`) injected every turn, so a new session starts knowing what earlier ones learned. The notes are ordinary files: read, edit or delete them yourself whenever you like; `/memory` shows where they live and how many there are. Your own SYSTEM.md does **not** switch memory off — the notes ride any prompt (that's the point); `/memory off` is the switch. The index is capped (25k chars per store, `memory.indexBudget`); when it fills, the model is cued to consolidate. Agents never get your memory — what one needs is carried into its task.

## Canvas — where deliverables land

When an answer deserves study — a report, a big table, a diagram, an interactive explainer — your model writes it as a file under `canvas/` in your working directory (self-contained html for human eyes; csv/markdown/svg for machine readers) and tells you the path. On screen such a write rests as `created canvas • <its title>` (`revised …` when it rewrites one); click it for the path, size and source, or **ctrl+click the title** to open the file straight in your browser/viewer — no path needed on screen.

To view canvases in a browser — this machine or your phone — type **`/canvas`**: it serves `<cwd>/canvas/` over HTTP and prints the URLs (localhost and LAN). Plain facts: it starts only when you type it and dies with pi; **every device on your network can read everything under canvas/ while it runs** (the command says so each time); the port is stable per project so bookmarks survive restarts (`"war-dogs": { "canvas": { "port": N } }` overrides); the index page lists the folder; there is no stop switch beyond quitting or `/reload` — it exists only on demand.

## Configuration reference

Everything lives under `"war-dogs": { … }` in `~/.pi/agent/settings.json` (project `.pi/settings.json` merges over it once the project is trusted):

| Key | Meaning |
|---|---|
| `enabled` | the master switch (default `false`) |
| `theme` | `false` to keep your theme, or a palette name (`canopy`, `canopy-cobalt`, `dune`, `oxide`) |
| `pager`, `subagent`, `tools`, `toolRenderers`, `banner`, `footer`, `loader`, `attachments`, `mcp`, `peers`, `prompt`, `canvas`, `inject`, `stockTools` | feature switches, all default on (`inject: false` = no injected messages; `pager: false` = tools without the full-screen surface — a documented degradation; `prompt: false` = pi's stock system prompt, no brief; `canvas: false` = no /canvas command; `stockTools: true` = keep pi's stock grep/find/ls — default trimmed, bash+rg/fd covers them) |
| `expect` | the webfetch scout's profiles |

Plus the `agent` block (previous section), the top-level `memory` block (`enabled`, `indexBudget` — see Memory), and pi's own `shellPath` / `shellCommandPrefix` / `images.autoResize`, which war-dogs honours identically.

Environment: `WAR_DOGS_ENABLED` (force on/off per invocation) · `WAR_DOGS_MEMORY` (force memory per invocation) · `WAR_DOGS_DELIVERY_WINDOW_MS` (delivery batching) · `WEBFETCH_*` (above) · `PI_CODING_AGENT_DIR` (pi's own — a different agent dir is a complete separate profile: settings, agents, transcripts).

## Rough edges to know about

- With `"pager": false`, an agent reply that arrives while you are idle draws in pi's own scrollback as a prompt line (`❯ [agent result …]`); the pager draws it as an act. The model reads the same thing either way.

- While the pager is open, the terminal's native text selection needs `shift`+drag, and middle-click paste is unavailable.
- A row containing an emoji can render one column short; complex scripts (Indic, Myanmar) can clip at the right edge. Terminal measurement limits, not fixable from inside.
- The very first render of a *huge* session (thousands of beats) can take a few seconds; afterwards it's instant.
- Your terminal may underline/open URLs on its own, doubling war-dogs' hover underline — that's the terminal's feature (in xfce4-terminal: `MiscHighlightUrls=FALSE`).
- `pi --no-session` runs still write agent transcripts to disk (a run *is* its transcript).

## When something looks wrong

- **`/mcp` unknown / tools missing** → war-dogs is off. `/war-dogs on`.
- **`[war-dogs] built against pi …` on stderr** → your pi version is outside the range this war-dogs was verified on; nothing is blocked, but if the screen looks subtly wrong, this line is the likely reason — update war-dogs or pin pi.
- **`[war-dogs] <name> failed to load: …` on stderr** → one feature failed, the rest is up; report it with that line.
- **Screen frozen after a `pi update`** → pi changed internals; `/war-dogs off` returns you to stock while it gets fixed.
- **Sent a prompt by accident?** Press `Esc` while the model is still answering it: the prompt comes back into the editor as you typed it, and the conversation is as if it was never sent. If the model already ran a tool on it, or an agent's reply arrived meanwhile, the prompt stays (a status line says so) and `/tree` is the way back.
- **`ctrl+g` (external editor) and `ctrl+z`** get a stock terminal: the pager drops its screen and mouse modes around them and takes them back after.
- **Mouse movements type junk into your shell** after a crash: `reset`, or `printf '\e[?7h\e[?1049l\e[?1006l\e[?1003l'`.
- **`Can't switch war-dogs while …` / `Refused: N agents still working`** → the busy guard; wait or stop the work (station `✕`).
- **Theme fails to load after `/war-dogs on`** → the palette files couldn't be copied into pi's themes dir (permissions); fix and `/reload`.
- **A render fetch fails naming Chrome** → install a system Chrome/Chromium; the fast tier keeps working meanwhile.
- **A named agent isn't offered** → its file has no body, or the project isn't trusted; stderr names the file and reason at startup.

Anything deeper: the folder's `dev/SYSTEM-PROMPT.md` turns any capable LLM into a war-dogs expert — give it that file as a system prompt plus access to this folder, and ask.
