# war-dogs

war-dogs is one pi extension that turns pi into a full-screen coding cockpit. It rides on pi's own agent loop and never changes what that loop does; it adds tools and re-skins what you see. On, you get: a scrollback **pager** that becomes the reading surface; in-process **agents** with a live station and a chat view per run; **WebFetch** (fetch-and-render, typed verdicts) and a direct Kimi **web search**; unified **image attachments**; the bundled **MCP adapter** (pi-mcp-adapter); and a re-skinned HUD — mascot banner, blue pulse spinner, re-coloured footer, subagent activity strip.

It is a copy-pasteable folder, not a package. Drop it into `~/.pi/agent/extensions/`; pi's jiti loader runs it with no build step, and everything it needs travels in `node_modules/`.

One principle governs the whole thing: **war-dogs is all or nothing, and OFF BY DEFAULT.** You activate it by adding `"war-dogs": { "enabled": true }` to `settings.json` — copying the folder in is not enough. On is the full experience. Off is pi exactly as `pi --no-extensions` renders it — the screen, the palette, and what the model is told, byte for byte — and that is not emulated but STRUCTURAL: when war-dogs is off at boot it registers NOTHING with pi (no tools, no commands, no renderers, no MCP, no theme), so there is nothing to diverge. There is no partial mode; the only customisation is editing this folder or building on top of it.

This is the ENGINEERING BOOK — the reference an LLM or a maintainer reads to work in this tree. It is the project's only memory: it holds what the code cannot tell you no matter how many times you read it — the architecture, the design decisions, and the invariants that a change would otherwise break. To fill any gap it leaves, read the code — not a dig through git history, and not a stale note. History tells you how something changed; this book and the code tell you what it is now. The user-facing manual — install, the screen, keys, agents, tools, the switch, the full configuration reference — is the root `README.md`; do not duplicate it here.

It reads in order: **how it works** (the layout, the data flows, pi's session lifecycle), **design decisions** (why the shape is what it is, and what was rejected), **maintaining it** (extending, the debugging instruments, the pi boundary to re-verify after each `pi update`), and **the invariants** (the load-bearing ledger — the rules that must hold and why).

# How it works

## Layout

Dependencies fan in toward `index.ts`, the only file that knows about everything. The rule that keeps it legible: **`tools/` is what a tool *does*; `visual/tools/` is what it *looks like*** — a `ToolDefinition` carries both, so `tools/*.ts` imports its matching renderer. What never happens: `agents/` importing `visual/`; `tools/library/` importing any pi API (it is shared with the CLI); `util/` importing anything of pi beyond pi-tui's text primitives (`sliceByColumn`, `visibleWidth`, `truncateToWidth`) — the one edge that makes the jiti recipe below need the pi-tui alias. Read `index.ts` → `mode.ts` → `agents/run.ts` → `tools/agent.ts` → `visual/pager/surface.ts` for a first pass.

## Mechanics

**A keystroke to a rendered frame.** pi owns the editor and builds its component tree as always. `mod.ts` opens a full-screen `ctx.ui.custom` overlay and *detaches* pi's chat containers from pi's root, so pi's own frames stay tiny and cannot flicker through; the pager holds the refs and renders them itself. Each frame `surface.ts` flattens those containers into display lines — with a prefix cache keyed by per-component signatures, so steady-state cost is O(streaming tail) — folds tool output against its *source* text, draws the scrollbar, and composites the live bottom UI (status, editor, footer) inside the overlay. The overlay sits on the alt screen with any-motion mouse reporting; both are war-dogs' terminal state and are restored on every exit path, including an uncaught exception and `ctrl+z`. Terminal input arrives through `ctx.ui.onTerminalInput` (the yield rule); assistant tokens mark the surface dirty via `message_update` so it follows the stream the way stock pi does.

**An agent call to a finished run.** The `agent` tool resolves config (`agents/config.ts`), records a run (`agents/run.ts` — the record is published *with its build reserved*, so a chat arriving during the build joins it instead of forking the transcript), and builds the child in-process (`tools/agent.ts`); a later chat rebuilds a released session through `ensureSession` (`agents/session.ts`) with the same hand-over on both paths. Progress streams to the tool's renderer and the station; the run's own chat view (`runview.ts`) is built the way pi builds main — one component per message, updated in place. Sends to a run are serialised behind pi's `preflightResult` acceptance, so a message typed at a run mid-turn becomes a steer, never a rejected second turn.

**A pasted image to the model.** Drop, the paste-image key (`ctrl+v`; `alt+v` on Windows — pi's own default there, since Windows terminals keep `ctrl+v` for themselves) and typed paths become refs through the live editor component — never `ctx.ui.setEditorText`, which clears the paste registry and drops the caret — with the paste registry transformed alongside the text; a `!bash` or `/command` buffer is never rewritten (pi dispatches those itself). At submit the pipeline re-registers any footer defs already in the message (a `/fork` or `/tree` restores messages pi wrote), refreshes each ref's bytes, resizes, and writes the footer. The id space is rebuilt from the *entered* session at every session start and on `session_tree`/`session_compact` (headless runs included); history's def table — not the store — decides which ids are taken.

**The switch.** `/war-dogs on|off` is refused while busy, then writes `war-dogs.enabled` into `<agentDir>/settings.json` (temp+rename, every other key preserved; on: `settings.theme` ← the war-dogs palette with yours saved under `war-dogs._prevTheme`; off: yours restored, the marker deleted) and calls `ctx.reload`. pi's reload tears down every extension surface (`resetExtensionUI`: overlays, terminal-input listeners, header, footer, widgets, statuses, autocomplete wrappers) and builds a fresh `ExtensionRunner` from re-imported modules, so the new state is a clean boot: `installOnce` at load (or nothing at all), then `activate` inside `session_start` — HUD, attachments, pager, the MCP adapter's `session_start`, and the custom tools into the active set in canonical order (pi's as they are, then ours in registration order, MCP names only as the adapter wants them). There is no reverse path in the code; off is the absence of registration.

**The MCP facade.** The adapter's factory is invoked with a Proxy over pi's ExtensionAPI that forwards everything — events, commands, flags, the active set — and RECORDS at two points: `registerTool` keeps every name and definition (the direct-tool set is dynamic — `<server>_<tool>` names appear after an async init) for the pager's toolmap, the child-tool source and the canonical active order; `setActiveTools` notes what the adapter itself wants active (`wanted`), never a tool it deactivated, and passes the write through untouched. The adapter receives pi's `session_start`/`session_shutdown`/everything directly, as a standalone extension would; because its handlers were registered during `installOnce` (load) and war-dogs' own `session_start` handler after, the adapter's init has run by the time `activateCustomTools` orders the active set. Each registered definition also goes into the pager's toolmap and to children through a live keyed source, which is how a subagent uses MCP on the parent's servers. Right after the factory, the default browser is registered on the same facade object through the adapter's `registerMcpServer` (Design decisions, MCP). (The facade once carried a live-off mode — a virtual active set, command refusal, captured and re-dispatched events, skill parking; all gone with the live toggle,.)

## What pi does on each transition, and how war-dogs follows

Measured on pi 0.83.0 with a tracer extension. Two facts drive everything: pi **re-runs every extension factory** on `/new`, `/fork` and `/resume` — against a fresh Extension object, the previous `pi`/`ctx` invalidated — but **re-imports the module only on `/reload`** (and on a cwd change), so module-level state survives `/new`. Anything done at load, or kept in module state, must expect to run again against a new `pi` with its old state still there.

| Transition | Events, in order | Factory re-run | Module re-imported |
|---|---|---|---|
| boot (`pi`, `--continue`, `--session`, `--no-session`) | `session_start{startup}` → `resources_discover{startup}` | first run | yes |
| `/reload` | `session_shutdown{reload}` → factory → `session_start{reload}` → `resources_discover{reload}` | yes | **yes — state reset** |
| `/new`, `/resume` | `session_before_switch` (cancellable) → `session_shutdown{new\|resume}` → factory → `session_start` → `resources_discover{startup}` | yes | no (yes if cwd changed) |
| `/fork`, `/clone` | `session_before_fork` (cancellable) → `session_shutdown{fork}` → factory → `session_start{fork}` → `resources_discover{startup}` | yes | no |
| `/tree` | `session_before_tree` (cancellable) → `session_tree` | no | no |
| `/compact`, auto-compaction | `session_before_compact` (cancellable) → `session_compact` **only on success**; Esc, failure or cancel emit nothing more | no | no |
| `/quit`, ctrl+d, double ctrl+c, SIGTERM/SIGHUP | `session_shutdown{quit}`, awaited before exit | – | – |
| dead terminal, uncaught exception | **no `session_shutdown`** | – | – |

`resources_discover` follows every `session_start`, with reason `reload` only after a reload. pi `await`s `session.abort` on the outgoing session before `session_shutdown`, so in-flight turns settle into the old session first. RPC `new_session`/`switch_session` emit `session_start` twice (a pi bug; harmless — `activate` re-sets header/footer/widgets and the MCP adapter keeps a lifecycle generation of its own).

The rules war-dogs derives, each paid for: the MCP adapter is instantiated once per factory run with its capture maps reset first; child-tool sources are keyed, not pushed; `installThemes` runs once per process; `/war-dogs` is a settings write plus reload, never process state; the compaction flag closes on the event's abort signal, the next input or session start, or age — never by waiting for `session_compact`; a switch or fork is refused while a run is in flight; the attachment id space is rebuilt from the entered session; `session_tree`/`session_compact` tell the pager the content was replaced (`contentReplaced`), and `agent_settled` ends the follow-hold (`turnSettled`), so neither a removed message nor the settle collapse is held on screen; the shared browser closes only on `reason:"quit"`.

# Design decisions

Why the shape is what it is. The invariants below (the ledger) are what a change must not break; these are the choices that set the shape, and the alternatives that were weighed and rejected. Distilled from the design records the code cannot express.

## Delegation — the `agent` tool

- **Delegation is how the main session lasts, not a way to fit work into contexts.** The leader's window is the one that must survive the project; workers exist to keep it clear. Everything in the tool's description follows from that frame: errand versus worker, heavy results to files, replies that carry the judgment and the pointer.
- **Errand versus worker is decided at recruit time, not per message.** An errand is spent on its task and released; a worker is kept for what it has learned. Re-tasking a worker starts from everything it knows. The earlier "a veteran is worth more than a fresh one" was dropped: it was situation-dependent and taxed every spawn with a re-task question.
- **No cross-session succession.** An agent is not meant to outlive the session it serves — the point of the tool is the opposite, that the main session lives long because it delegates. Continuity across sessions is the directory's job (files), and session-after-session is the explicit fallback. So there is no verb to adopt a dead session's runs, no registry for it.
- **Worktrees are doctrine, not mechanism.** The tool already has the mechanism (`cwd` per run, `bash` in every agent's hands), and a merge is exactly where judgment lives — what to accept, who resolves a conflict, when to integrate. Auto-worktree-and-merge would make the tool take those judgment calls and own worktree lifecycle; rejected. A `workspace` convenience parameter stays available for later without contradiction.
- **The recruiting standard is taught as a loop, not a written persona.** A full written standard for defining an agent would bind to today's models and stale. What survives model generations is the loop that produces standards: define, judge the definition by the work that comes back, revise against evidence, save a proven one as a named agent. The loop binds to output, not style.
- **Steering is demoted.** A steer is a correction; needing one means the brief was wrong or the world changed. The brief is first-class; the steer is the fix you also fold back into the next brief.
- **The doctrine lives in the description**, not on a scale-gated surface. The description is the one surface that always travels in the request and survives any custom `SYSTEM.md`, so the whole doctrine is there rather than in prompt snippets a user's prompt would erase.
- **Cost left the model surface.** Tokens and tool calls are the context economics the model owns; dollars are the user's and change no decision the model makes, so `$` appears only under `agent.discloseCost`. Model choice is user-curated, so there is no "use a cheaper model" clause.

## What the model is told

- **The base prompt is pure conduct** — no machine or pi facts. Those live in the session brief, injected once per session as a message, so the conduct prose never drifts with the environment.
- **A user `SYSTEM.md` wins whole.** When the user replaces pi's prompt, war-dogs' base and brief both stand down — the user's context engineering is honored, not merged. The base is swapped per turn through pi's own assembler, which makes compaction survival free and leaves `AGENTS.md`, skills and the cwd line exactly where pi puts them.
- **A child gets main's base verbatim** plus one `<agent-exchange>` block on being a subagent. There is one prose, one voice; everything different about being an agent is that block and the provenance line on each message, not a separate persona.

## Memory

- **Not a tool.** The model keeps notes with the file tools it already has; war-dogs contributes only a prompt-block rider, a per-turn index injection, and the store scaffolding. A dedicated memory tool was rejected — the file tools are enough, and a tool would be one more thing to teach.
- **On by default, and the rider survives a foreign base.** Memory is exactly the context that must outlive a user's own `SYSTEM.md`, so its rider is appended after the base decision, not stood down with it — the opposite of the base and brief.

## Canvas

- **No model-facing tool, no harness rendering.** A deliverable is the model's ordinary `write` under `canvas/`, taught by the base prompt (self-contained HTML for people, raw markdown/CSV/SVG for machines). war-dogs adds only two affordances on the files: the pager's canvas act, and `/canvas` to serve them.
- **Serving is the user's consent, never the model's.** `/canvas` is a typed command that names the LAN exposure; the model never touches networking, and there is no auto-serve — exposure is a decision the user makes out loud.

## MCP

- **The default browser is a runtime registration, not a file.** `@playwright/mcp` is bundled (pinned exact, like the adapter) and registered through the adapter's own `registerMcpServer` on the facade object the factory was installed with, under the name `playwright`. That API is what makes the precedence structural instead of policed: a configured server of that name — any mcp.json, `/mcp setup` — makes the call throw "already registered", so the user's entry runs and ours is skipped without a merge, a notice or a file to reconcile; a runtime server dies with the adapter instance, so a boot-off has nothing and `/new`/`/fork`/`/resume` simply re-register. Two alternatives were tried on the machine and rejected: a programmatic `config` makes the adapter skip every config FILE and disables `/mcp setup`, enable/disable and the panel (`index.ts` 198, 767–893 of the adapter); a default `<agentDir>/mcp.json` is a file the user cannot delete without it coming back.
- **Bundled, not `npx`.** The folder is self-contained by principle: the CLI is run by the node running pi (`process.execPath`), so a copied folder works offline, Windows needs no `npx.cmd`, and nothing drifts under `@latest`. Cost: a second `playwright-core` at the alpha `@playwright/mcp` pins, 19 MB.
- **Proxy-only is not a loss.** Runtime servers are forced `directTools: false`, but a file entry defaults to the same (`direct-tools.ts resolveDirectTools`: nothing set → off), so the surface is what the maintainer's own entry had: the `mcp` gateway, which children already carry.
- **Nothing but the Chrome is passed.** The one probe (`util/chrome.ts`, shared with WebFetch) gives `--executable-path`; without a hit, `--browser chrome` lets Playwright find a Chrome that is not on PATH. Headless, sandbox and profile are deliberately left to playwright-mcp, which already decides them from the environment (the ledger entry below).

## Injected messages

The user's own text, verbatim, never wrapped. Unlike the base and brief it is NOT stood down by a `SYSTEM.md` — it is the user's context engineering, so it accumulates like `AGENTS.md` rather than overriding. It never reaches children: a child's context is its definition and its briefs, not an inherited pile.

# Maintaining it

## Extending

**Before changing what a tool says or returns, read `dev/reference/tools/`** — the per-tool reference of every model-facing string and situation — and after the change re-run `node dev/reference/tools/dump-definitions.mjs` (definitions.md is generated from the live code) and update the tool's page by hand.

**Time awareness** : pi's default system prompt carries NO date or clock at all, so the model was clockless for the whole session. Every tool result, error, receipt, delivery, and USER PROMPT now ends with one fixed line, `[timestamp: 14:32:07 +07:00]` (local time with offset, completion time; a few hours of shipped the shorter `[at …]` label — the parsers and display strips accept both) — `util/stamp.ts`, applied at every registration choke point (`reg`, the subagent publishes, the MCP facade's `registerTool`), in the input pipeline for prompts (registered after attachments, so transforms compose; idempotent — appendStamp replaces an existing trailing stamp, which is what keeps a `/fork`-restored message from stacking two), on the run-view routing path for child-directed messages, and on the child's FIRST prompt — the task the parent hands over (it arrived clockless, since the parent's input pipeline never sees it) — and on a SKILL invocation: pi emits `input` BEFORE expanding `/skill:name args` into `<skill …>…</skill>\n\nargs`, so the stamp rides the args and lands last (the no-args form gets it after a SPACE — pi finds the name at the first literal space, and a newline made `name\n\n[timestamp…]` an unknown skill, sent raw). The transform had skipped every slash-prefixed text as a command; prompt templates still are (their args substitute mid-body). Uniform on purpose: tools run constantly, so stamping everything gives the model a continuously updating clock as a side effect. The `timestamp:` label matches the house bracket grammar and keeps a log tail's own bare timestamp line from impersonating it. Self-teaching: NO description mentions it. Children's results are stamped too since (their skins are stamped at build; until then stock bash/write/edit left a child clockless on its three most-used tools). The stamp is the FINAL line of everything, so `splitTrailer` consumes it after the run id; on the pretty surface it is hidden EVERYWHERE (the wire view shows it back — see the root README, The screen); read's NOTICE test knows the form.

**A new tool's TEXTS follow the house register** everything in `description` — no `promptSnippet`, no `promptGuidelines` (a SYSTEM.md replaces pi's prompt; the description travels in the request always); ZERO-DIRECTION IS RETRACTED (maintainer): a description may guide — when to use, how to write a task — so long as every sentence is true of the tool and changes a decision (the agent tool's description is the model; the reasoning is in Design decisions above); tools stay SELF-CONTAINED — nothing the model needs may depend on a system prompt, skill or context file; one-line-per-paragraph, machine metadata as `[…]` bracket lines at the end of results; a description STATES THE SUBSTANCE and never names another tool as the only route (maintainer: tools and their schemas are customizable context — `webfetch` being off must not strand a model that could curl; "read the page itself", never "webfetch it") (`[agent id: …]`, `[Read lines …]`), and schemas that are AUDIENCE-SOUND: a parameter inert for its reader is omitted from that reader's schema, not documented as inert; values a description names (defaults, caps) are interpolated, never guessed.

**A model-facing tool needs three registrations or it half-works**: `pi.registerTool` (the model can call it), `registerToolDef` in `visual/pager/toolmap.ts` (a subagent transcript renders it with the real renderer instead of raw JSON), and `setChildExtraTools` in `agents/childtools.ts` (children load no extensions, so they must be handed it). Wire all three from `index.ts`, inside `installOnce` — that is what makes it vanish when war-dogs is off (a boot-off never runs it); add its name to `WAR_DOGS_TOOLS` so it takes its place in the canonical active order. (The toolmap also keeps render aliases `WebFetch`/`Kimi-WebSearch`/`subagent` for transcripts recorded before the renames — render-only, never model-facing.) A tool set that is not known at load — the MCP adapter's is: direct tools appear after an async init, and it deactivates ones it stops offering — registers a keyed live source instead: `setChildExtraToolsSource("mcp", => mcp.childToolDefs)`, consulted at child-build time; keyed, not pushed, because the factory re-runs per session.

**A tool renderer** lives in `visual/tools/`; `renderCall`/`renderResult` return a pi-tui `Component` and run inside pi's render loop under a try/catch that silently falls back — keep it pure and cheap. For a built-in re-skin follow `tools/read.ts`: spread the stock tool, re-declare `promptSnippet`/`promptGuidelines` from the `create*ToolDefinition` factory, pass `stockToolOptions`, attach the renderer. Re-declaring is not optional ("`wrapToolDefinition` drops prompt metadata", Load-bearing); `createBashTool` is the one factory that `Object.assign`s them back.

**A pager view** is a new branch in `PagerComponent.render` plus its key/mouse handling in `mod.ts`. Reuse `flattenLive`/`renderSubCached` for anything that shows pi components and `childEntriesToRawLines` for the raw fallback. Fold against source text (`srcLines`), never display rows.

**A named beat** (something pi draws that should read as an act) owes `foldName` a name, `actSentence` a case, `sigFor` its own O(1) state, and the cluster summary a verb. **A component of ours in pi's tree** (a header, a status) that renders from state rather than text owes `sigFor` a `wdSignature` — or the cache freezes it at its first frame (Load-bearing, `flatten.ts`).

Where the extension lacks authority — spacing or layout stock pi hardcodes outside renderer reach — do not hack around it: implement fully in the pager, which war-dogs owns end to end, do what is cleanly possible inline, and report the gap with the mechanism. A documented limitation beats a fragile workaround.
## Debugging

pi loads this TypeScript through jiti with no typecheck, and wraps every renderer and event handler so a throw is swallowed into a silent fallback. Nothing tells you a change is broken: a type error, a missing import, a shadowed binding, a wrong arity after a refactor all present as "the UI is a bit off" — a missing stats line, a tool rendered as raw JSON, a row laid out wrong. So correctness is established by asking the machine, escalating through these instruments.

**Typecheck after every change — non-negotiable.** `npm run typecheck` (or `npx -y -p typescript@5.9 tsc -p tsconfig.json`). The tsconfig is self-contained: the pi type declarations are pinned devDependencies resolved by relative paths, `pi-mcp-adapter` maps to `mcp/pi-mcp-adapter.d.ts`, and it covers the whole tree at zero errors with `noUnusedLocals`/`noUnusedParameters` and the incremental strict flags. Full `strict` is not on — the pi boundary is `any`-heavy by necessity — so this catches the silent-failure classes, not everything. **Formatting is enforced**: `npm run format` / `format:check` (prettier, tabs, 120 columns; `.editorconfig` covers editors; markdown is in `.prettierignore` and hand-wrapped).

**Run one module in isolation** through pi's own jiti — the same loader pi uses, so what runs is the real module (`tsx` cannot: it resolves the pinned packages to their `.d.ts` entries and dies; plain `node` against pi's `dist/` works only for pi's own classes). `util/` needs only the pi-tui alias; a module that imports pi's agent API needs `@earendil-works/pi-coding-agent` mapped to `<pi>/dist/index.js` too.

**Boot it headless.** `echo '{"id":"1","type":"get_state"}' | pi --mode rpc --no-session` loads every extension and exits; `[war-dogs] <name> failed to load` on stderr names a feature whose registration threw, and silence is a clean load — which proves the module parsed, not that anything behaves. In Windows PowerShell 5.1 the same line works (`'{"id":"1","type":"get_state"}' | pi --mode rpc --no-session`; `pi` is a `.ps1` shim that forwards stdin), but PowerShell's pipe hands the JSON to the native process with a UTF-8 BOM whatever `$OutputEncoding` says (tried; through the shim and against `node.exe cli.js` directly), so the `get_state` reply is a `parse` failure — harmless for the stderr instrument. When the reply matters go through cmd, whose `echo` writes bare bytes: `cmd /c 'echo {"id":"1","type":"get_state"} | pi.cmd --mode rpc --no-session'` (verified: `"command":"get_state","success":true`). `pi -p "…" < /dev/null` drives tools and subagents end to end (needs a model). `tmux new-session -d -x 140 -y 40 pi` drives the full TUI, and interaction is scriptable: `tmux send-keys` the SGR mouse bytes (`\x1b[<0;col;rowM`) and read back with `capture-pane -e -p`.

**Isolate the agent dir when a setting is under test.** `PI_CODING_AGENT_DIR=<dir> pi …` boots against a private agent dir: copy `auth.json`, `models-store.json` (and a `settings.json`), symlink war-dogs under `<dir>/extensions/`, and pre-copy `visual/theme/*.json` into `<dir>/themes/` if the comparison involves a war-dogs `settings.theme`. **Settle geometry with the trace, never with arithmetic.** `PI_WARDOGS_TRACE=/tmp/wd-trace.log` (read once at process start) records the pager's per-frame layout plus click and fold events, written only on change. Per-frame fields: `src` (main/child/raw), `rows`, `tail`, `raw` (the flatten's own height), `total` (rendered after a follow-hold), `drop`, `held`, `hw`, `cacheN`/`liveN` (this flatten's cache hits / fresh renders), `body`, `offset`, `follow`, `ms` (the last flatten's cost — healthy p50 1–2 ms; a cold render legitimately spikes once). Events: `ev=click` (`idx`, `cc`, `offset`, `total`, `ranges`, `hit`, `span`), `ev=toggle` (`tool`, `partial`, `before`, `after` — `after` disagreeing with `!before` means the override landed on a different object than the one rendered), `ev=flash` (`at`, `len`, `offset` — the collapse-return jumped and flashed `len` rows from `at`; absent after a fold means the head was on screen, so no jump), `ev=settleflash` (`n` rows), `ev=uncluster`/`ev=recluster` (`n`), `ev=wire` (`tool`, `on` — a per-beat wire-view toggle), `ev=overflow` (`tool`, `row`, `w`, `max` — a beat row that would not fit the content width after its seat shift; the cut-off audit, see Load-bearing: any count above zero is a defect), `ev=grab` (`tool`, `rc`, `call`, `out` — the evidence split reading a tool's call/result children; it dominates the file, so `grep -v ev=` for frames). `drop>0 held=0` is a flicker frame.

**`dev/instruments/win/` is the Windows acceptance rig** — the tmux of a platform without tmux: `rig.mjs` boots pi inside a ConPTY (node-pty) and feeds its VT stream to a headless xterm, so a scenario reads the screen, sends keys, SGR mouse reports and bracketed pastes, and asserts; `setup.mjs` builds two private agent dirs under `%TEMP%\wd-rig` (war-dogs on and off; your settings, auth and sessions untouched; the war-dogs folder as a junction) and the test image; `scenarios.mjs` is the suite (`node scenarios.mjs` for all, names for some; `npm install` in that folder first — node-pty and @xterm/headless are prebuilt for node 22). Three facts the rig paid for: ConPTY never forwards DECAWM (`?7l/h`) and swallows the mouse-mode RESETS (`?1003l`, `?1006l`) and pi's `?1004l` while forwarding the SETS and `?1049h/l` — so the exit-path witness is pi-tui's write log (`PI_TUI_WRITE_LOG=<file>`, everything through `terminal.write`, the pager's teardown included), never the pty stream; PowerShell's `Start-Process -Wait` waits for the descendant tree; and pi's `/exit` is not a command (it is a prompt — `/quit`, ctrl+d or double ctrl+c end a session). **`./dev/instruments/acceptance-test.sh` is the off=stock regression harness** — run it after any change to the mode switch, the HUD, the renderers or the active tool set. It needs tmux, `pi` and a configured model, and its exit code is the verdict. # The invariants — the load-bearing ledger

These are the load-bearing invariants: the rule that must hold, the mechanism that makes it hold, and the dead end that proves it — written so you do not rediscover it as a bug. Each was paid for once. Overturning one takes a demonstration, not an argument; change code because you understand the cause, never to make a symptom disappear. Grouped by area.

### Children and runs

**Child sessions are configured by us, not by pi.** `createAgentSession` only reloads a `ResourceLoader` it created itself, so a loader we pass must be `await loader.reload`-ed or it reports no system prompt and no extensions. Everything a child needs — system prompt, tools, model, thinking level, model runtime, context files — is handed over explicitly on **both** paths, spawn (`tools/agent.ts`) and rehydrate (`agents/session.ts`), continue included. A missed value fails silently: the run answers, with the wrong prompt, model or thinking level or a missing tool (the thinking level was inherited by neither path until a probe compared the manifest against the parent's `--thinking`). Keep the two call sites identical; the child-parity check is how you prove it.

**The rename is structural, not cosmetic.** `subagent` became `agent` with seven actions on one schema; states became working / queued / idle / stopped / error, mapped from legacy manifests at the READ boundary (`listManifests`), never rejected — reject and every old run vanishes from the station. `stop` interrupts and the run STAYS continuable (`message`); only a provider/build failure is `error`. Depth defaults to 0; concurrency is an OWNED budget (`agents/slots.ts` — acquire under the run's own signal, release exactly once at settle via `rec.slotHeld`; a copied cap overshoots, the fan-out rule the research demonstrated 30/30). There is no foreground: every run and message returns a receipt and the reply is delivered where a conversation exists (`canDeliver`), held for with `wait` elsewhere — `wait` races the work promise against the call's signal, and an interrupted wait leaves the run working. `ask` is a tool-less `completeSimple` over a transcript snapshot (live messages + streaming partial), auth via `runtime.getAuth` (an Upgrade Contract reach beside `sharedModelRuntime`), pi-ai's compat module loaded by ABSOLUTE path from the running pi — the jiti alias covers `@earendil-works/pi-ai`, not its subpaths. The `message` verb is promptRun for a working run (steer; the owning turn delivers one reply covering both) and the continue flow for an idle one; the two must not each deliver.

**The stress audit — six mechanisms, each paid for by a reproduced bug** (an Opus auditor drove the mock rig; findings in the commit trail). (1) A CLAIM is per-turn: `rec.claimed`/`rec.schemaReply`/`rec.activity` are cleared at every owner-turn start in `sendToRun` — left set, the next turn's delivery was skipped forever (a wait then a message: the message's reply reached the model ZERO times). (2) Only the send that OWNS a turn gets a work promise and a delivery (`onAccepted(ownsTurn)`): a steer that joined another send's turn resolved at acceptance and delivered the PREVIOUS reply as a fresh completion. (3) wait treats a pending send/build as working (`hasPendingSend`) and claims a work promise the moment it appears mid-poll — the acceptance gap made wait return "(earlier)" during a message it should have held for. (4) The pager's prefix rollback must never cut inside a component's own rows: a class-change drain mid-component (an errored message's thinking, then its error-class act) froze the flushed thinking into the prefix while `flatPrefixComps` stayed at that component, and every fast-path frame re-emitted it — the "thinking rendered twice" screenshot; `drainPending(keepComp)` keeps the current component's tail pending under a fresh mark. (5) `ask` reads `session.systemPrompt` (a PROPERTY; `getSystemPrompt` is the extension context's accessor and `?.` silently yielded undefined — every agent ask ran promptless), and a released run's prompt is rebuilt from `run.config`/the named agent's body, since the transcript never carries it. (6) The batch parser's section split and dispatch know all three sentence heads (`Background bash "`, `Subagent `, `Agent "`) — after the rename, a two-agent batch parsed as ONE nameless bash job. Also: `flushDeliveries` runs at session_shutdown before the clear, so a reply landing inside the batching window in a session's last moments is written into its transcript instead of vanishing. DOCUMENTED LIMITATION: a tool call that never ran (its turn died mid-stream) renders with past-tense sentences; the honest tell (`executionStarted === false`) does not survive a `/resume` — pi's restore path never marks it and installs the same synthetic error result — so labelling on it would mislabel genuinely-failed historical tools; the sentence guard is the safe part that shipped (`messaged (no agent named)`, never `0 agents`).

**Cost is off the model surface; context and folds are on it (draft 10).** `[agent stats:]` shows duration, tokens, tool calls and `context N% (tokens/window)`; `$` needs `agent.discloseCost: true` (the maintainer's ruling: with model choice user-curated, dollars change no decision the model owns — tokens and tool calls are the context-economics facts). Context and the compactionSummary count are SNAPSHOT AT SETTLE (`agents/run.ts`): the session is released the moment a run ends, so status/replies on idle runs would otherwise have nothing — the same discipline as the stats snapshot. The compaction note compares the settle count against a PER-TURN baseline (`rec.compactionsAtTurnStart`, set on both owner paths — doRun and sendToRun; a joiner shares its owner's turn). The family roll-up aggregates SETTLED descendants only and names `· N still working` — a lead can reply while a background descendant works, and a silently understated roll-up is worse than none.

**An instrument's shared derivation has many readers — audit them all before changing it.** The mock's `text` was both the keyword key AND the literal-last-message the follow-up triggers tested (`Started "Status probe"` → status); the brief-skip patch repointed `text` at the last USER message and every tool-role trigger went silently dead (demonstrated: substat's status call never fired, found only because the build needed that flow). The triggers now read `lastMsgText` (the literal last message), the keyword walk stays user-only.

**The stock nav tools are trimmed on three surfaces at once, or the trim lies.** Main's active set (`activateCustomTools`), the child's excludeTools (BOTH build paths — createAgentSession defines grep/find/ls whatever the active set says), and the agent tool's grantable enum (`childToolNames`) all read the one switch (`war-dogs.stockTools`); trimming fewer than all three leaves a name the model can be offered but never given, or a child with tools main claims not to have. The bash description's rg/fd line is CAPABILITY-TRUTH, probed once per process (`which`/`where` on the process PATH, then pi's own `<agentDir>/bin`, where pi downloads rg and fd when they are not on PATH and which its shell tools put FIRST on the command's PATH — a PATH-only probe stayed silent on the first Windows machine while every command the model ran had both; silence when neither finds them) — never a conditional the model must resolve.

**ONE SHELL PER PLATFORM: powershell on Windows, bash elsewhere, both only by the user's explicit choice (the maintainer's rule, the first Windows run).** Three pi facts decide the mechanism: pi REGISTERS `powershell` on every platform (`createAllToolDefinitions`) but ACTIVATES only `read, bash, edit, write` by default (`sdk.js defaultActiveToolNames`; `--tools`/`defaultTools` are the documented knobs, "on Windows select powershell instead of bash, or include both"); pi activates every tool an extension registers, so the powershell skin `tools/powershell.ts` registers is in `getActiveTools()` on every platform (probed); and `getPowerShellConfig` refuses to run off Windows. The first guard trimmed powershell "beside a present bash", reasoned on Linux for a Windows pi imagined to have powershell INSTEAD of bash; a real Windows pi finds Git Bash under Program Files, so bash is always present and the guard removed the platform's own shell — the maintainer's first Windows session ran every command in Git Bash and was never offered PowerShell. A second cut kept both on Windows; the maintainer ruled two shells redundant. The answer is DECIDED AT LOAD (`agents/childtools.ts decideShells`: the platform, plus the user's explicit choice — `--tools`/`-t`, `--exclude-tools`/`-xt`, `--no-tools`/`-nbt` on the command line, `defaultTools` in any settings file — then pi's set stands as written) and published in `installOnce` BEFORE the agent tool registers, because that tool's `session_start` handler bakes its `tools` enum and installOnce registers it ahead of the handler that sets the active set: an answer published only from `activateCustomTools` reached the enum one boot late — the ConPTY rig's first agent run had the enum offer `bash` and refuse `powershell` (`1 failed`) while the child, built later, got powershell. `activateCustomTools` then ENFORCES the same answer: unless the user chose, on `win32` it replaces `bash` with `powershell` at bash's seat (a pi that no longer auto-activates the skin gets it spliced there), off Windows trims powershell as the dead tool it is; then the nav trim; then re-publishes the shells main actually has (`setMainShells`). Children read the same answer on both build paths: `stockTrimExclusions` excludes the shell main lacks (pi's `_refreshToolRegistry` applies excludeTools to custom tools too, so the name is gone whatever is handed), the `skins` source hands the bash skin only where main has bash and the `powershell` source the powershell skin only where main has it, and `childToolNames` follows (bash from the built-in list only when present, powershell through the extras). The session brief states the shell main has and what it runs, from pi's own resolver (`getShellConfig` with the user's shellPath; `$SHELL` was the login shell, and Windows has none); an explicit bash on Windows is named a POSIX bash with `/c/Users/...` paths. Probe: a throwaway `-e` extension that writes `pi.getActiveTools()` from a delayed `session_start` (stdin held open with `cmd /c "(echo {…} & ping -n 10 127.0.0.1 >nul) | pi.cmd --mode rpc --no-session -e …"` on Windows; `get_state` does not carry the tool list) — on Windows `on` reads `read, powershell, edit, write, agent, webfetch, kimi-websearch, mcpScript, mcp`, stock `read, bash, edit, write`, and `--tools read,bash,powershell,edit,write` keeps both; off Windows the shell is bash and powershell is absent. And the jiti probe of `agents/childtools.ts`: shells `{bash:false, powershell:true}` → exclusions `grep, find, ls, bash`, enum `read, edit, write, powershell, agent`; `{bash:true, powershell:false}` → the Linux answer. AND THE INSTRUMENTS ARE READERS OF THIS API: the agent harness declares its wiring "mirrored from index.ts installOnce()", so a rename here must be chased through `dev/instruments/` too. Three names from the rework's intermediate cuts (`setShellIsPowershell`, `isShellPowershell`, an ungated bash hand) survived in the scenario and the harness mirror and were invisible until the Linux suite first ran `shellps`: the win rig cannot run the mock suite (bash+tmux), so a scenario written on Windows executes for the FIRST time on Linux — and `childExtraTools`'s `safeCall` swallows a source's throw into "no tools", so a stale name inside a source closure reads as a child quietly missing a skin, not as an error. Two greps settle it after any wiring change: the old name across `dev/instruments/`, and duplicate keys in `setChildExtraToolsSource` calls — the map is last-write-wins, so a second registration under one key silently replaces the first.

**A fresh SettingsManager trusts every project — child loaders must not (the precedence stress-test's finding).** pi's `SettingsManager.create` defaults `projectTrusted: true`, so a child loader built without one LOADED an untrusted project's `.pi/SYSTEM.md` and `.pi/settings.json` — main gates both, children did not (demonstrated on the wire: an undecided cwd's SYSTEM.md became a child's base prompt). Both build paths now pass a trust-gated manager into the loader AND `createAgentSession` (`settings.ts childProjectTrusted`: the parent's LIVE answer for its own cwd — which in `-p` is pi's own resolution and may be true, mirroring pi exactly — and pi's trust STORE alone for any other cwd, undecided = untrusted; the foreign-cwd branch is proven by the subcwd probe, an untrusted project's file ignored). Verified by the six-case matrix: untrusted project → pi stock (our base stands down on existence, pi refuses the file); trusted project → the user's file wins whole.

**A child gets MAIN's base verbatim; being a subagent is the exchange block, and the relay is stated on every message (the maintainer's ruling) — and SYSTEM.md is main's.** From an adhoc child ran on a GENERATED regrounding of the base (a since-deleted `prompt/child.ts`, "principal" for "user", a generator that anchored on exact base text so drift failed loudly) with a facts paragraph in the rider (agents, per-turn limit, fold or die, reach, the reply rule, the interrupt); the description said "the standing agent default" for it. Both are gone: `childBasePrompt` returns `BASE_PROMPT` — the ladder is call > named body > `SUBAGENT_SYSTEM.md` (project, trust-gated through `childProjectTrusted`, then global) > main's base > pi stock, on BOTH build paths and the ask rebuild; SYSTEM.md does NOT flow to children (maintainer: SYSTEM.md is main's; the always-passed base overrides the child loader's own discovery) — and the `<agent-exchange>` block rides `appendSystemPrompt` on both paths, block first, `SUBAGENT_APPEND_SYSTEM.md` next, the call's own append LAST (the user's context engineering has the final word). The block is the maintainer's words: what a subagent is, how the first line of every message reads, the one-way rule. Two facts are substituted at build, the mechanism the ruling named for reach: the ask sentence rides only where the child HAS an agent tool (depth > 0 — the default depth-0 child has no `ask`, and telling it to use one would be false), and the reach sentences ride only under `reach: "session"` (team: dropped). The child's NUMBERS live where the model reads numbers, its agent tool's parameter descriptions (`prompt/child-base.ts` states none): `depth` and `concurrency` already said "yours"; `timeout_s` gained "Yours is N seconds." / "You have none."; `reach` gained "Yours is team|session." THE PROVENANCE LINE states the relay: `[from the agent that started you • your final output goes back to it: agent_…]` (main: `… goes back to the main agent`; another agent with session reach: `[from agent agent_… in your session • … back to it: agent_…]`) for a message that owns the turn; `[from your user • your final output stays with the user]` for a turn the user opens on an idle run; `[from your user • this turn is still the agent's; its final output goes back to it: agent_…]` for the user's steer inside an agent's turn or the follow-up inside an interrupt episode (`… the main agent's; …` when main started it). The receiver is a FACT of the send, decided in `sendToRun` — own turn: the sender, or the user (the interrupted turn's receiver inside an episode, which is what `armInterruptFollowUp` delivers to); join: the turn's receiver, except an agent joining a user turn, which arms that turn's delivery for itself (doMessage) and so takes it; held: the holder's receiver for the user, the sender for an agent — so the line is composed THERE: `promptRun` takes the body and a `from: Party`, nobody prepends a line or a stamp any more (the run view, doMessage, the queued-steer drain and the harness all changed together), and every owned turn records `rec.turnOutput` (the task's is the run's starter, set in doRun before the queued steers drain). The wording of the line is the maintainer's to polish; the facts are these. Regression: `dev/instruments/agent-scenarios.mjs provenance` (the three forms on the wire, read from the child's transcript); the reference shows the block per variant and every line a run produced. AND THE TASK CARRIES THE LINE TOO (2026-08-31, the maintainer's ruling on the stress session): the exchange block teaches "the first line of every message names who sent it", but the one message a fresh child had ever seen — the task — carried only the stamp, and two children independently MINTED their own header (`[from orchestrator]`, a word that appears nowhere in war-dogs or in anything they were sent; one wrote `[from orchestrator] This turn goes back to the orchestrator.`, and told the user afterwards "my instructions tell me to open every message with a first line…"), which `status` then honestly previewed as `reply so far: [from orchestrator]`. The fix is the missing information, not prompt prose: doRun sends the task as `provenanceLine(starter, starter, run)` + blank line + task through the SAME composer as every later message, so the convention's first example arrives with the convention. The pretty surface strips it like every provenance line (the `^\[from …\]` regex); Windows rig regression `task_provenance`; the Linux `provenance` scenario should gain a task-line assertion, and the mock's last-user-message keyword walk sees the task's new first line (keywords match by substring, but re-verify on the first Linux run).

**The strip is footer rows, not a widget.** pi's widget placements are aboveEditor/belowEditor only; the maintainer wants the strip BELOW the footer, and the footer is ours — so StatusStrip's rows are appended to the footer component's own render output, which the pager composites and stock scrollback draws alike; the widget (and its aboveEditor stacking rationale of) is gone, the ticker's tui handle is captured from setFooter, and the /ask progress joins as a third strip-styled row (setAskProgress) instead of a plain footer status.

**A settled run's session is released.** Stats are snapshotted onto the manifest at `settle` and a later chat rebuilds the session from its transcript through `ensureSession`, so memory is O(runs working). Two rules follow: never dispose a session while its `prompt` is unwinding (`dispose` detaches the subscription that persists turns — it answers but writes nothing), and never let two builds race — `ensureSession` shares one in-flight promise per run and the tool path refuses to resume a still-running run, because two `AgentSession`s over one transcript is how a run replies with garbage.

**A run with no session yet is not a run with no session.** Sharing one build covered only builds that started in `ensureSession`; the spawn path built its own, and for the ~40 ms (longer on a big transcript) between recording the run and assigning `rec.session`, a chat at that run saw neither a session nor a build and constructed a second one over the same transcript — reachable by typing at a run the moment it appears. The spawn path now publishes its build with `reserveSession` before awaiting it. The gap had a second face: pi decides steer-versus-new-turn on `isStreaming`, which flips only after the owner's whole preflight, so a message in the gap became a second turn, was rejected with "Agent is already processing", and the typed text vanished. `promptRun` waits (bounded, 5 s) for the turn it means to join, serialises sends per run behind pi's `preflightResult` acceptance, and takes the turn itself only when nothing is streaming by the deadline.

**A delivery needs a turn to ride, and a receipt must not lie (the message-hardening cycle, five reproduced bugs).** `message` used to fork on `run.status`: a working run got `void promptRun.catch(=>{})` (fire-and-forget, receipt returned before acceptance), an idle run got a bespoke work promise. Both leaked. (1) A message to a run in a USER-DRIVEN turn (the run view, `promptRun` with no `onAccepted`) joined that turn as a steer — but a user turn sets no `rec.work`, so `deliverWhenDone` had nothing to fire on and the steered reply, though the child wrote it, **reached the model zero times** (silent lost output; demonstrated `dev/instruments/agent-scenarios.mjs usersteer`). Fix: every owner turn arms a per-turn completion signal (`beginTurn`/`rec.turnDone`/`resolveTurn` in `agents/run.ts`, resolved by `settle`), and a joiner whose turn has no owner delivery (`!rec.work`) arms that turn's one delivery on `turnDone` (guarded by `rec.deliveryArmed`, so two joiners never double-arm). (2) The idle path swallowed send failures in a `catch{}` and answered "Delivered … it starts its next turn", then delivered the PREVIOUS turn's reply as a fresh completion. Fix: the receipt is written only at genuine acceptance (`preflightResult(true)`; pi calls it with `false` when its own preflight threw, which is a failure, not an acceptance), and a failed send THROWS its provider error to the caller. The reply body is built from the turn's OWN stream (`currentTurnText`), never `lastReplyFromTranscript`, which is the previous turn's text when this one died mute. (3) A message to a QUEUED run has no session or transcript yet; `promptRun` threw "transcript is missing" into that swallowed catch — Delivered, and nothing was. Fix: `promptRun` holds the text on `rec.pendingSteers` and `doRun` drains them as steers the instant the task turn is under way; the receipt says "queued … reads it as soon as it starts". (4) The tail race: a message landing between the child's `agent_settled` (`isStreaming` false) and the tool's `settle` (session disposed) was judged "join a turn", found nothing streaming, and took the turn ITSELF on a released session — pi ran it detached from persistence and it vanished. Fix: when a join promotes to taking the turn, re-resolve the LIVE session (`rec.session ?? ensureSession`) before prompting. (5) `rec.claimed` was a FLAG: two waits on one run with one interrupted un-claimed what the other had consumed, and the reply arrived twice (once as the surviving wait's return, once as the delivery). Fix: `rec.claims` is a COUNT — a completed wait keeps its claim, an interrupted wait releases only its own. AND THE CLAIM IS PLACED UP FRONT FOR EVERY ID, NOT AT VISIT TIME (the maintainer's stress session, 2026-08-31): doWait's sequential loop claimed each id only when it REACHED it, so every id behind a slow one sat unclaimed for the whole earlier hold — three of six runs settled in that window, `deliverWhenDone` found `claims === 0` and composed deliveries (16:45:52–16:46:23) that pi consumed right after the wait's own result (16:47:21): the same three replies, twice each. A pre-pass now claims one per resolvable occurrence (mustFind + gateReach; peers and refusals claim nothing) before the first hold, and the loop's interrupt path still releases one per aborted occurrence. The fourth duplicate had the opposite shape — a run finished and DELIVERED between two waits, and the later wait repeated the body — so `rec.deliveredTurn` (set at deliverWhenDone's two dispatch points, cleared at owner-turn start beside claims) makes every wait branch, the settled-earlier one included, point instead: `…; its reply was delivered as its own agent result and is not repeated here.` Windows rig regressions `wait_nodup` (three staggered runs, one multi-id wait: zero deliveries, each reply once) and `wait_after_delivery` (delivered once, the wait points, the body reaches the model exactly once); the Linux harness scenarios that exercise claims (`twowaits`, `claims3`, `usersteer`) must be re-run after any change here. All five are reproduced and re-verified green in `dev/instruments/agent-harness.mjs` (the in-process rig that drives the real tool through pi's jiti with exact timing; scenarios `usersteer`, `sendfail`, `queuedmsg`, `tailrace`, `twowaits`, `interleave`, `schematwice`, `claims3`, `stops`). Also fixed alongside: `wait`/`status` on a continued run report the last TURN's duration and text, not the run's whole lifetime or its previous reply.

**The stress-cycle rulings** (the twelve harness scenarios in ci.sh are the regressions). **THE LEAD RULE** (report 155/46, the maintainer's real question): a run's reply reaches its principal only when its turn ends AND none of its own agents is still working. History: children once ran foreground, so a lead's turn could not end before its workers'; background made a lead reply early and strand its workers' results. **A run IS its transcript.** Continuing a run means opening the file it wrote; `SessionManager.create` is not a fallback for a missing one. **A child's failure lives in its stop reason, not in its text.** A turn that dies at the provider still produces an assistant message — `stopReason:"error"`, an `errorMessage`, no content blocks — and `prompt` resolves. Reading text blocks alone reported a 401, a context overflow or a truncation as `(no output)` on a run settled `done`: silent wrong output. `lastAssistantOutcome` carries the stop reason beside the last text (from different messages on purpose — "I found 3 of 10 files…" then a 401 is partial output *plus* a failure); both call sites settle `failed` with the provider's message, and the tool THROWS, since a thrown error is the only way a tool result reaches the model marked as an error. `stopReason:"length"` says so in the body. Aborts keep the same discipline: expiry, a user's ✕ and a parent tearing down its subtree are three sentences, so every `abort` is given a cause (`abortCause`/`abortKindOf`) and the body, the manifest and the background follow-up all read it — "finished in 4s" on a run that quietly timed out is the same lie in a friendlier voice.

**No timeout means NO TIMER.** `timeout_s` is undefined unless the call, an agent file, or settings asked for one (the no-default-timeout change) — but the abort timer stayed armed unconditionally, and `Math.max(1, undefined) * 1000` is `NaN`, which `setTimeout` treats as 0: EVERY run without an explicit timeout aborted the moment it spawned — settled `failed`, delivered `(timed out after undefineds — no output)` — silent wrong output on every default-config subagent, shipped for a day and demonstrated with the mock's `sub` (fixed). The timer is gated on the value now. The general rule: an OPTIONAL number must never meet arithmetic that feeds a timer, cap or budget without an explicit undefined branch — `setTimeout(fn, NaN)` fires immediately, it does not throw.

### The inherent prompt and the brief

**The base is swapped per turn, and a user SYSTEM.md stands everything down.** `prompt/index.ts` rides `before_agent_start`: when `systemPromptOptions.customPrompt` is falsy it returns `buildSystemPrompt({...options, customPrompt: BASE})` — pi's own assembler, reached from `dist/core/system-prompt.js` through pidist.ts because pi's package index does not export the function — so APPEND_SYSTEM.md, context files and skills survive exactly as under a user SYSTEM.md, and compaction survival is free (the hook runs on every turn, idle-time deliveries included since the delivery-turn rule below; there is no re-injection path to maintain). When `customPrompt` is truthy the handler returns NOTHING — base and brief both: the user's context engineering is honored whole. The base prose lives in `prompt/base.ts` as a baked constant, the source of truth (the maintainer's prose); nothing runtime reads it from anywhere else. VERIFY ON THE WIRE, never via `ctx.getSystemPrompt`: at `session_start` that accessor returns the BASE pi built, not the per-turn override, so an sp.ts dump "proving" the ON swap proves nothing — the sp.ts prompt-parity check stays OFF-only by design, and the ON checks read the mock's `DUMP=` request bodies (demonstrated : the first wire check "failed" for exactly this reason before the instrument was corrected).

**The memory rider is STAGE 2, outside the stand-down.** The prompt handler's stage 1 (base + brief) returns nothing under a user SYSTEM.md; memory appends AFTER that decision, to whichever prompt is in force — moving it inside stage 1 silently kills the contract's survival requirement (the rider exists precisely to outlive a foreign base; demonstrated on the wire: `My own prompt…` + `# Keep the memory` in one request). Scaffolding rules, each honest: `reference.md` is the HARNESS's and is rewritten whenever its bytes differ; `MEMORY.md` is the MODEL's and is created (legend only) but never overwritten — a scaffold that "refreshes" the index destroys the memory. Everything gates per turn on `memory.enabled` (+ `WAR_DOGS_MEMORY`), so `/memory on|off` needs no reload and OFF appends and reads nothing.

**A persisted custom message is its OWN entry type — scan for both shapes.** The brief's once-per-session check reads the transcript, and a custom message lands on disk as `{type:"custom_message", customType:…}` (session-manager.d.ts), NOT as a `.message`-wrapped message entry; scanning `.message` alone re-injected the brief on every `pi -p --continue` (demonstrated on the wire: two `[session brief:` messages in one request). `briefAlreadyInSession` reads both shapes and memoises by session id only after SEEING one in the branch — never at injection, so a first turn that dies before persisting cannot mark the brief as delivered. A `/fork` copies the entries, so the brief travels with the fork and is never doubled.

**A turn that a DELIVERY starts skips `before_agent_start` — "per turn" means per USER prompt.** pi emits the hook only inside `AgentSession.prompt` (agent-session.js:882); a background agent reply, peer message or bash result that lands while main is idle goes through `sendCustomMessage(…, {triggerTurn})` → `_runAgentPrompt` directly (1062-1094, 744-757), no hook. FIXED the same day, the delivery-turn rule (`tools/delivery.ts sendDelivery`): an idle-time delivery — agent reply, batch, background bash result, peer message — goes through pi's public `sendUserMessage`, which runs `prompt` and the hook, as a user-role message carrying the same provenance line and body; mid-turn deliveries stay steering custom messages (a steer joins a turn whose prompt is live). Demonstrated: the wake turn's request carries the base and memory prompt and a fresh PER_TURN message after the delivery.

**One `before_agent_start` handler yields ONE message; several messages need several handlers.** `BeforeAgentStartEventResult.message` is singular and the runner pushes each handler's into `messages` in registration order (runner.js `emitBeforeAgentStart`), then agent-session persists each as its own `custom_message` after the user's prompt. ### The pager and rendering

**A working snippet is a control, complete or not (overturning an earlier rule).** The rule was: in the working window the sentence and its leaked rows light and click as one control, but a snippet that hid nothing was "complete — no light, no click", and an own-kind act (the session brief, a delivery) registered a handle for its sentence alone. Demonstrated with injected mouse bytes and the trace (`ev=toggle tool=session-brief before=0 after=1` from a click on its body while main worked; before: `hit=0 span=none`).

**A steered delivery is held until pi consumes it.** While main streams, a delivery rides pi's steering queue (`sendMessage(deliverAs:"steer")`), and pi's Esc handler clears every queue (`restoreQueuedMessagesToEditor({abort:true})`): typed text goes back to the editor, a custom message has nowhere to go, and a worker's reply that arrived during a long foreground bash was simply gone when the user pressed Esc (the maintainer's question,; verified: no `agent-result` in the transcript, nothing on the next prompt). `sendDelivery` now stamps each steered delivery with a nonce in `details`, holds it, drops the hold on `message_start` with that nonce (pi consumed it), and re-sends whatever is still held at `agent_settled`. Demonstrated: Esc on main mid-bash, nothing for seven seconds, then the reply beside the next prompt (`user` → `agent-result` in the transcript and on the wire).

**An interrupted agent is woken by nothing on its own (the maintainer's rule; the silent loss).** The audit reproduced the maintainer's report by harness and in the TUI: a depth-1 lead interrupted mid-`wait` (Esc in its view), followed up by the user, its worker finishing, the lead summarising — and main never told (`dev/instruments/agent-scenarios.mjs leadinterrupt`, before the fix `deliveries=0`). A second face: alt+x stopped the team and the stopped worker's report woke the lead into a fresh turn (`leadaltx`). The maintainer's rule replaced the flag dance: an interrupt ends everything the agent was doing, the team hold included (`holdForTeam` returns on `userInterrupted`, `interruptRun` wakes it through `rec.holdWake` and counts a held lead as interruptible), the run settles idle inside the episode at once, and NOTHING wakes it on its own — while it is idle inside the episode, or the interrupt is still unwinding (`parkedForInterrupt`, agents/run.ts), its agents' replies park on `rec.pendingDeliveries` (`deliverToRun`) and are appended to its transcript as plain custom messages ahead of its next turn, whoever starts it (`sendToRun`'s owner block, `sendCustomMessage(…, {triggerTurn:false})` on the idle session). **A delivery to a run is a steer only with `triggerTurn: true` (the real-model audit, drive 2: a lead told main its worker was still working after the worker had replied).** pi's `sendCustomMessage` reads `triggerTurn` in its STREAMING branch too — `isStreaming && triggerTurn !== false` is the steer (`agent.steer`) — and since 0.84.4 a streaming session given `triggerTurn: false` takes its fourth case: the message is deferred to the turn's end (`_pendingCustomMessages`, flushed at `turn_end`) and appended to `agent.state.messages` and the transcript. **The field palette runs on pi's highlighter, reached from the running pi.** pi's public `highlightCode` paints with the live theme's `syntax*` tokens and nothing else, so prose code blocks and panel evidence had one palette; `visual/tools/syntax.ts` loads pi's `dist/utils/syntax-highlight.js` (`highlight(code, {language, theme})` — a scope→painter table over highlight.js) from `realpath(process.argv[1])`'s directory — argv[1] is the `pi` bin symlink, not `dist/cli.js` (demonstrated: the un-realpath'd test failed and every panel silently fell back to the stock palette) — and paints with `wdSyntax*`; a miss falls back to `highlightCode`. Read/write/edit/bash keep every character (highlight.js wraps, it never transforms). And the pager no longer strips EVERY background from tool rows: pi's card tint is removed sequence-exactly (`stripBgSeqs` with the theme's tool*Bg opens and the `49m` closers), so a diff tint or a code pill survives; the old `stripBg` made a tinted diff impossible.

**The model's prose is the terminal's colour unless a theme says otherwise.** pi's `getMarkdownTheme` paints headings, links, code, quotes, bullets — never the paragraph — and `AssistantMessageComponent` builds prose with no `defaultTextStyle`, so the body reaches the screen with no foreground SGR at all; the theme's `text` var was never on it, and an ivory `text` changed nothing (demonstrated by the gallery: the captured prose row carried no fg). `wdProse` is the token that does reach it, through `renderProseChild`'s shadow Markdown; `""` keeps the terminal default. Do not paint prose by wrapping rendered rows — the inline `\x1b[39m` resets after every code span end the wrap mid-row.

**A truncator is not a splitter.** `wrapPlain`'s hard-break called pi-tui's `truncateToWidth` with no ellipsis argument, so it appended `"..."` plus a reset and `head.length` counted characters never shown — 30 in, 14 out. Use `sliceByColumn` for splitting: a true prefix for plain text, lossless across ASCII, CJK and emoji, with `strict` keeping a wide grapheme inside the column. **`stripAnsi` handles APC (`\x1b_ … BEL`) before the catch-all** — pi marks the hardware cursor that way and the subagent renderer marks run rows the same way — and strips the charset designators (`ESC (0`, `ESC) B`, `ESC *`, `ESC +`) and `ESC #`/`ESC %` whole, because the two-byte catch-all left their payload byte as text (`\x1b(0lqk\x1b(B` → `0lqkB`).

**The wire view rides CTRL+CLICK; the head-row button is retracted.** The first build (morning) put a visible `raw`/`pretty` control on every expanded head row; the maintainer retracted it the same day ("looks weird") for ctrl+click — `ctrl?: boolean` on a click range, invisible to plain clicks, resolved in `handleCtrlClick` AFTER token-open (a path still opens) and BEFORE the "Can't open" notice. (2) A solo cluster summary takes its click action from the beat's first `s === 0` range — with ctrl ranges on collapsed beats that find must SKIP them, or every solo summary silently becomes a wire toggle instead of a fold. (3) `renderSubCached` copies RenderedBeat fields EXPLICITLY into the cache — the button's `wireBtn` field was never added to that list, so cluster members rendered from cache silently lost it (latent, removed with the field); any new RenderedBeat field must be added to that copy list or it exists only on fresh renders.

**Every row a beat contributes must fit AFTER its seat shift — width-10 for evidence, width-5 for a sentence.** A beat renders once and is drawn in two seats: standalone, and as a cluster MEMBER three columns to the right (its evidence chunks deeper still). Three cut-offs were paid for on before the rule was written down: a thinking text wrapped at width-6 lost its last characters as a member (`Now the fina`), pi's error rows taken at the full width did the same (`please try aga`), and head sentences truncated at width-2 overflowed by one column as members. So: every wrapped body wraps at `width - 10` (the tool branch's `toolW`, the own-result branch's `inner`, thinking, error turns, wire evidence), every head sentence truncates at `width - 5`, and nothing appends to a row without slicing it to its visible width first. The INSTRUMENT is the trace: `PI_WARDOGS_TRACE` logs `ev=overflow` for any row that breaks this (emitBeat and emitMember check every row of a fresh beat against the content width plus its shift — trace-only, zero cost otherwise). The audit that ships a change to any renderer: replay a session with every tool kind, `ctrl+o`, and `grep -c ev=overflow` at 140, 80 and 60 columns — zero each (: 0 / 0 / 0 on the 4,900-row reference session).

**Emoji width is a known, unfixable one-column offset.** Terminals that ignore `U+FE0F` draw `base + VS16` in one column while pi-tui counts two. Correcting our own measurement makes the line `width + 1` by pi-tui's reckoning and `compositeOverlays` truncates overlay lines with *its* measure — taking the scrollbar. A bar one column in beats no bar; do not retry this from inside the extension.

**The run-status glyphs are one decision (`visual/glyphs.ts`): defaults per terminal, overrides in settings, width-1 enforced.** Windows Terminal's DirectWrite falls back per codepoint when Cascadia lacks a symbol, and any codepoint with an EMOJI FORM comes back from Segoe UI Emoji as a colour picture — `✳` U+2733 rendered as the green-square asterisk emoji, while `✔` U+2714 happened to land in the monochrome Segoe UI Symbol (the maintainer's screenshots); VS15 (`︎`, text presentation) is IGNORED there, demonstrated on screen, so no selector fixes it — only a codepoint with no emoji form anywhere (`✻` U+273B, `✓` U+2713). The maintainer keeps the classic `✳ ✔` on Linux (proportionate there) and wanted taste settable, so: `RUN_GLYPHS` decides once at module load — TEXT_SAFE under Windows Terminal (`win32` OR `WT_SESSION`, which Windows Terminal exports into WSL shells, where `process.platform` is linux and the renderer is still DirectWrite), CLASSIC elsewhere, then `war-dogs.glyphs` per-key overrides accepted only at `visibleWidth(v) === 1` (a base+VS16 pair measures 2 and is rejected — the emoji-width entry above is why a wide glyph must never reach a painted column). Every painter reads it — the subagent tree and result line, the footer tally, the pager's status mark (`runGlyph`) — because the same status painted from two literals is how the sets drift. The spinner frames (`✺✹✸✶`), `⚠` and `⚙` are unchanged: no emoji form in the first set; the other two have one and are accepted as-is (the maintainer, 2026-08-31: not worth the surface).
### The mode switch and pi's surfaces

**CONTROL IS SETTINGS-ONLY; OFF-AT-BOOT REGISTERS NOTHING.** pi cannot unregister a tool, command, renderer or message renderer, and it wires a tool's input and renderers at `session_start`/build time — so a LIVE toggle both froze the pager (registering its `onTerminalInput` handler after `session_start` had already fired left the overlay deaf) and leaked rendering into off (a component holds the tool wrapper it was built with). The robust answer is to have no live apply at all: `/war-dogs on|off` WRITES `war-dogs.enabled` into `<agentDir>/settings.json` (`writeEnabledSetting`, preserving every other key, temp+rename) and calls `ctx.reload` — every state is a fresh BOOT. `installOnce` (all tools, skins, pager, HUD, MCP, attachments, the theme-file install) runs once at LOAD when `bootEnabled`, BEFORE `session_start`, so the pager's input handler is in place when it fires. A boot with war-dogs off calls `installOnce` never; the ONLY unconditional registrations are the `/war-dogs` command (the way back on) and the invisible lifecycle handlers. So a boot-off is byte-for-byte stock because the extension made no calls — proven by replaying a transcript full of MCP/subagent/bash/webfetch calls under boot-off and diffing against `--no-extensions` (identical, text and colour). Default is OFF (`settingsEnabled` is `enabled === true`). Do NOT reintroduce a live apply or move registration off the load path — that brings back the freeze and the leak. The live-toggle machinery was deleted once each piece was proven unreachable (no caller, or a flag with no writer): `applyMode`'s off branch and its stock-definition re-registration, the HUD/attachments/pager `disable`s, `resyncToolComponents`, the renderer gates (`gateRenderersOnMode`), the in-memory `enabled` flag and every `isEnabled` gate, the slash-list filter, the MCP facade's skill parking and `disable`. What makes the deletion safe is pi's own `setBeforeSessionInvalidate(=> resetExtensionUI)` plus a fresh `ExtensionRunner` on every `/new`, `/resume`, `/fork` and `/reload`: nothing registered in one boot state can be reached from another, so no gate has anything to defend. The ON system prompt was byte-identical before and after the deletion; off = stock on every instrument.

**A skin re-declares prompt metadata and passes `stockToolOptions` — `wrapToolDefinition` is why.** An extension tool REPLACES the built-in in the registry the system prompt is built from (`_refreshToolRegistry`; `_toolPromptSnippets`/`_toolPromptGuidelines` derive from it with no built-in fallback), and `wrapToolDefinition` — which every `create*Tool` factory returns — drops `promptSnippet`, `promptGuidelines`, `renderCall`, `renderResult` and `renderShell` (`createBashTool` alone `Object.assign`s its metadata back). Registering a bare `create*Tool` result under a built-in's name therefore strips its snippet and guidelines from the prompt — it did, for as long as the old live-off path re-registered the stock factories (three snippets and six guidelines gone whenever war-dogs was off); renderers fall back to the built-in, prompt metadata does not. And an option-less definition is not the stock one: the skins pass `stockToolOptions` — `settings.shellPath`, `shellCommandPrefix`, `images.autoResize` — because without them the model's commands ran in a different shell than stock. The skins check in Debugging is how you prove the four stay byte-identical to pi's definitions.

**Anything PERSISTED needs its renderer ABSENT while off, not only its write site gated.** `loader.ts` appends `gen-time` entries into the session JSONL and pi has no `unregisterEntryRenderer`, so gating only the append left every earlier session drawing `✸ Generated in …` while off. Under the live toggle the renderer returned a falsy component when disabled — exactly stock (`addCustomEntryToChat` bails on a missing renderer, `CustomEntryComponent.rebuild` on a falsy one; it must not throw, which paints an error box). Today the renderer is simply never registered on a boot-off (`installOnce`), which is that fallback by construction; the rule that remains is never to register an entry or message renderer outside `installOnce`.

**Never "restore" pi's header/footer/widget slots from the extension.** pi keeps ONE `customHeader`/`customFooter` slot and `setHeader(undefined)` restores pi's built-in — no stack, no memory of a previous owner — so the old live-off's restore, when ungated, evicted a surface war-dogs never installed (with `{"banner": false}`, turning off tore down another extension's header). There is no restore path any more: pi's `resetExtensionUI` clears the slots before every session switch and reload, and off never installs. Do not add one.

**Off restores the theme pi HAD, not a theme war-dogs derives.** Stock resolves the startup theme from `settings.theme`; re-deriving a default painted a different palette than `--no-extensions` for anyone with a non-default theme (`light` → off showed dark), and a hand-rolled COLORFGBG rule disagreed with pi's on 88 of 256 indices. So the user's theme is SAVED, never derived: `/war-dogs on` keeps it under `war-dogs._prevTheme` and `/war-dogs off` writes it back. **The MAIN theme is pi's, set via `settings.theme` + reload; only the pager's `visor` sub-theme is an in-memory object.** war-dogs installs its palette FILES into `<agentDir>/themes` on the first ON, and `/war-dogs on` writes `settings.theme` to the war-dogs palette (saving `_prevTheme`) and reloads — pi then applies it to chrome and content in one pass, no race. An in-memory `setTheme(object)` was tried and RETRACTED: it ran AFTER pi's reload had already rendered the transcript, so pi's content components cached the old palette while war-dogs' chrome showed the new one (code spans stayed dark). Because control is settings-only (reload), the save/restore is clean: OFF puts `settings.theme` back exactly (deleting it when there was none). `visor` stays an object — it is the subagent view's own canvas, not pi's global theme, and `warDogsTheme`/`loadThemeFromPath` (via `pidist.ts`) build it on demand. No stderr on the happy path (any stderr line lands in pi's TUI pane and would fail the harness).

**Project settings are ignored unless the project is TRUSTED, and war-dogs must mirror that exactly.** pi blanks `<cwd>/.pi/settings.json` for an untrusted project and treats an undecided one as untrusted until the prompt is answered. Reading it regardless booted war-dogs OFF from a file pi had refused to load, and made the MCP adapter yield to a `packages` entry pi never installed. `settings.ts projectAllowed` is the single gate (`ctx.isProjectTrusted` once pi says; before that pi's `ProjectTrustStore` plus `--approve`/`--no-approve`); the feature block, `packages`, `war-dogs.expect` and `.pi/subagents/*.md` all go through it, and anything new that reads a project file must too.

**Never let the adapter see its own tools missing from the active set.** Its init calls `setActiveTools([...real, "mcp"])`, and the facade reads the adapter's writes as its intent (`wanted`): a tool of its own absent from `real` at that moment reads as "the adapter no longer wants it" and is dropped from `wanted` for good — demonstrated under the old live toggle (off stripped the set; off→on came back without `mcpScript`). So the facade never strips or parks MCP names any more — pi activates every registered tool at boot, the adapter's writes go through untouched, and `activateCustomTools` only reorders (pi's tools as they are, then ours in registration order, MCP names as the adapter wants them), which is why the prompt's tool list is the same on every boot. Anything that removes an MCP name from the active set behind the adapter's back re-creates the bug. **One adapter instance per factory run**: pi re-runs the factory on `/new`, `/fork`, `/resume` without re-importing the module, and keeping the previous instance's captured handlers dispatched `session_start` to N instances while a stale forwarding set left the new object with no shutdown forwarder — MCP servers outlived pi. `register` resets every capture map before installing.

**The default browser passes only the Chrome; the environment decisions are playwright-mcp's.** A "no display → `--headless`" flag was designed and then shown redundant: with `DISPLAY` and `WAYLAND_DISPLAY` unset, Chrome's argv already carried `--headless --ozone-platform=headless`, and with a display it carried neither (read off `ps` during a held MCP handshake, `/tmp/pw-handshake.mjs` style: initialize → `browser_navigate` a `data:` URL → hold → `browser_close`). The same read showed `--no-sandbox` on by default (root in a container launches) and the persistent profile at `~/.cache/ms-playwright-mcp/mcp-*` (logins survive). Every flag we would have added either duplicates one of these or fights it, so `registerDefaultBrowser` passes the CLI, `--browser`, and the probed `--executable-path` — nothing else. A flag added here needs the argv read again, not a reading of `--help`.

**The sanctioned model-facing changes in the built-in re-skins, each deliberate; a new one needs the same scrutiny.** (5) The powershell skin carries exactly bash's set — our description, the `description` and `background` params, the background branch of `execute`, the abort completed with who — and nothing else; snippet and guidelines pi's verbatim; the rg/fd line is bash's alone. (1) All four DESCRIPTIONS are ours since — one voice, zero direction, facts and contract only (the implemented spec is the tool descriptions themselves); `promptSnippet`/`promptGuidelines` stay pi's verbatim on all four. (2) bash's optional `description` and `background` params, and the background branch of its `execute` (the only bash behavior divergence). (3) edit's `execute` wrapped only to make a rejected BATCH say so — pi applies a batch atomically but its error names one failing `oldText`, and the model retried edit-by-edit believing the others had landed. (4) read's TEXT path is ours : cat -n numbered results, a bracketed metadata line on every read, an explicit `limit` honored past the cap (pi re-cut even explicit asks), the default cap pi's numbers line-aligned; images and all errors delegate to pi's execute byte-stock, and children are handed the same read. The custom tools (subagent/webfetch/kimi-websearch) carry NO snippet/guidelines — description-only, because a SYSTEM.md replaces pi's prompt and those fields reach nobody there. The skins check in Debugging verifies what must still match.

**The install lines `cd` into the folder; `npm install --prefix <dir>` is not portable.** It worked on Linux, and on Windows (the maintainer's PowerShell, npm 11) npm read `package.json` from the shell's cwd instead and failed with ENOENT on `Desktop\package.json` — the first thing a Windows user saw. Both README one-liners clone, change directory, then run a bare `npm install`; do not reintroduce `--prefix` without running it on Windows.

**The repo pins LF through `.gitattributes`; a Windows checkout without it is CRLF.** Git for Windows ships `core.autocrlf=true` in its SYSTEM config (invisible to `git config --global`), so the first Windows clone checked every file out as CRLF: prettier (`endOfLine` lf) flagged all 103 files, and any file the extension reads at runtime with `readFileSync` — `scout-system-prompt.md` — would have carried `\r` into what a model is told (template literals are safe: the language normalises CRLF inside them, which is why the typecheck and the headless boot were clean and nothing said a word). `* text=auto eol=lf` makes the checkout LF on every platform, and the `.ans` captures are marked `-text`. To renormalise an existing CRLF checkout use git's own recipe — `git rm --cached -r . && git reset --hard` — since `checkout-index -a -f` skips stat-matched entries and leaves the files as they were (tried).

**It is one extension, not several.** pi loads each extension via a separate jiti call, so two extensions cannot reliably share a module; an earlier version passed state through `globalThis.__pi*` handles. One `index.ts` makes them ordinary imports; split it back apart and that coupling returns.

### The terminal and input

**Autowrap is OFF while the pager owns the screen (DECAWM, `?7l`).** pi-tui UNDER-measures complex-script graphemes — its clustering gives a Devanagari/Bengali base+matra ONE column while the terminal draws the matra as its own spacing cell (`[अंगिका]` measures 5, draws 7 in tmux; `[বিষ্ণুপ্রিয়া মণিপুরী]` measures 11, draws 18) — so a composited row padded to width-1 by pi-tui's count can be DRAWN past the terminal width. With autowrap on, the terminal then inserted a physical line break, the screen SCROLLED, and pi-tui's diff model no longer matched the screen: stale frame fragments — a second title bar with a stale scrollback %, banner shreds mid-panel, URL tails at column 0 — persisted until a full repaint (demonstrated : the maintainer's Wikipedia fetch in VTE, reproduced byte-for-byte in tmux with the cached fetch file). `?7l` rides `MOUSE_ENABLE` and `?7h` rides `MOUSE_DISABLE` and every restore path (close, exit hook, SIGTSTP; the crash-recovery `printf` in Troubleshooting carries it too), so an overwide row now CLIPS at the last column — the benign, emoji-class artifact. Do NOT fix this by correcting the measurement instead: that is the emoji entry's dead end (compositing truncates with pi-tui's measure — the scrollbar goes). Stock pi never touches DECAWM, so the unconditional `?7h` restore is always right.

**A missing opener is an ASYNC crash, not a caught throw.** `spawn("xdg-open", …)` for a binary that is not on PATH does NOT throw — it returns a child with no pid and emits `error` a tick later, and an `error` event with no listener is an uncaught exception, so pi exits 1 with no `session_shutdown` (the alt screen and mouse modes stranded, the entry below). The old ctrl+click openers wrapped the `spawn` in `try/catch`, which the async error walks straight past. `util/opener.ts` (`openExternal`) listens for `error` and `spawn` and resolves `{ ok, reason }`, so a ctrl+click on a machine with no opener says `Open failed: xdg-open: spawn xdg-open ENOENT` on the footer instead of taking pi down (probed: a scrubbed PATH returns `ok:false` and the process stays alive; with `xdg-open` present, `ok:true`). It is also the one place the opener command is chosen by platform — `xdg-open` on Linux, `open` on macOS, `cmd /c start "" <target>` on Windows (the empty title argument keeps a quoted path from being read as the window title); the non-Linux commands are reasoned from their manuals, not yet driven. The general rule this pays for: a `spawn` whose failure must not crash pi needs an `error` listener, never only a `try/catch`.

**The alt screen and mouse reporting are OUR terminal state; pi restores only what it enabled.** Two exits bypass every hook — an uncaught exception (pi calls `process.exit(1)` with no `session_shutdown`) and `ctrl+z` (pi stops its TUI and SIGTSTPs the group) — and both left the shell in the alt screen with mouse tracking on, moving the mouse typing junk into the prompt. While the pager is open `mod.ts` registers a `process.on("exit")` restore, a SIGTSTP hook that restores the modes, parks the cursor below pi's stale frame and then really stops (SIGSTOP — a listener replaces node's default), and a SIGCONT hook that re-enters; all removed at teardown. On a quit the teardown must run synchronously inside `session_shutdown`: pi's `done` settles our promise on a microtask, and pi printed its resume line and exited before that ran. When pi owns the alt screen itself (0.84+ fullscreen) none of the 1049 writes happen — DECSET 1049 is not reference-counted and our close dropped pi out of its own alt screen.

**Esc takes an accidental prompt back by rewinding the leaf, never by holding the prompt (the maintainer's ask).** Two designs were weighed: hold every prompt for a window before sending (nothing ever enters the transcript, but every submit pays the delay and the held text must be re-fed through the stamp and attachment transforms by hand), or rewind after the fact with pi's own primitive. The rewind won: `navigateTree(id)` is what `/tree` does — it moves the leaf, rebuilds the agent's context from the branch, emits `session_tree` (the pager already follows it), and destroys nothing (the entries stay on the abandoned branch). The rule that makes it safe: the undo runs only when the aborted turn was the one the prompt started (recorded at `input`, taken by the next `agent_start`) and every entry after the remembered leaf is the prompt, war-dogs' own riders on it (the brief, the inject files — re-injected honestly on the next prompt, since the once-per-session scan reads the branch) or the cut assistant message; a tool result or a DELIVERY after the leaf refuses it with a status line — a reply consumed into the turn would be lost with the branch, the maintainer's worry, and background agents and jobs are process state the rewind never touches. A reply that arrived while the turn streamed prose is a different case: it waits in pi's steer queue (a steer is read at a tool boundary), pi's Esc clears that queue, and the held-delivery rule re-sends it with the next prompt — so the undo proceeds and nothing is lost (asserted: the job's reply rides the prompt after the undo). Two pi facts paid for: `navigateTree` is on the COMMAND context only (`ExtensionCommandContext`; event handlers get the general context), so the settled hook arms the undo and dispatches `/war-dogs undo` through `sendUserMessage({expandPromptTemplates:true})` — pi executes an extension command before it persists or emits anything (`agent-session.js prompt`); and the raw text is what the recorder sees because it is registered FIRST among the input handlers, before the attachment and stamp transforms. Regression `dev/instruments/undo-test.sh` (tmux, the mock): Esc mid-stream restores the prompt and clears it from the branch; Esc after a tool ran keeps it; Esc after a delivery landed in the turn keeps it.

**The external editor is a TUI stop, not a signal (the pi-settings review).** `ctrl+g` (`externalEditor`) makes pi `ui.stop` its TUI, spawn the editor, `ui.start` again; the SIGTSTP/SIGCONT hooks never fire and pi restores only the modes it enabled, so the editor ran inside the pager's alt screen with any-motion mouse reporting on (demonstrated: a script as the editor read `alternate_on 1, mouse_any_flag 1` from tmux). `this.ui` is a Proxy that resolves the method on the live TUI at call time, so the pager overrides `stop`/`start` on that instance (arguments forwarded — `stop` takes options), restoring the modes on stop and re-entering on start, and puts the originals back at teardown. Inside the editor: `0 0`; the pager back after. Regression: the acceptance harness's `--editor` leg. And the stop wrap PARKS the cursor below the stale primary frame (`parkBelowStaleFrame`, the SIGTSTP hook's move) before pi prints "Launching external editor: … / Pi will resume when the editor exits." — pi writes those two lines to stdout right after `ui.stop()`, at the cursor `?1049l` restored, i.e. the editor line of the frame from the moment the pager entered; with an editor that runs INSIDE the terminal (nano) they are covered at once, with a GUI editor (`notepad`, pi's Windows default; `code --wait` anywhere) the terminal showed the stale frame with the footer overwritten and scrolled up two rows per press (the maintainer's Windows screenshot, four presses stacked). Seen by the maintainer on Windows; the Linux `--editor` leg is to be re-run on the next Linux session (it asserts the modes and the pager's return, not the primary frame). Two smaller findings of the same review, fixed: a background bash job ran without the user's `shellCommandPrefix` (the foreground skin passed it through pi's option; the job spawned the raw command — `bgprefix`); and the trust gate read the store alone for a never-asked project while pi reads the store, then `defaultProjectTrust` (`always`/`never`), so a user whose global policy was `always` saw war-dogs refuse `.pi/inject`/`memory`/`subagents` that pi itself allowed (`dev/instruments/inject-test.sh`, the `always` case). And the review's method: every key in pi's `docs/settings.md`, its reader in `dist/`, its reader in war-dogs — recorded in the root README's configuration reference.

**Close OUR overlay, never "the top one".** pi's `done` → `hideOverlay` pops the LAST overlay — the adapter's `/mcp` panel or any extension overlay pushed after ours vanished with its promise never resolving while ours stayed drawn. `done` is used only while we are the top; otherwise the `OverlayHandle` from `onHandle` splices our entry by identity and the promise stays pending (pi leaves it pending on `/reload` too). And `wantOpen` gates the 120 ms open timer: a teardown inside that window (then a live off; now a `session_shutdown`, e.g. an immediate `/reload`) finds nothing to close and the timer would open the pager anyway — demonstrated as war-dogs off with the pager live.

**`onTerminalInput` runs before the focused component.** While a selector, the `/mcp` panel or a dialog holds focus every key is theirs — the pager's `ctrl+s`/`ctrl+r`/`ctrl+o`/PgUp bindings swallowed their save/reconnect/cycle keys (`/scoped-models` ctrl+s never saved). The handler bails whenever `tui.focusedComponent` is not the editor; `CTRL_O`/`CTRL_R` name the exact modifier (`;5u` — the loose form matched shift+ctrl+o, pi's tree filter cycle); PgUp/PgDn/Home/End and the station arrows follow Enter's yield rule (typing wins); a bracketed paste is one event and never a mouse report (a paste containing `ESC [ <` was swallowed whole as clicks); the station composites the live bottom UI like every view — pi's editor keeps focus everywhere, and a station without it was an invisible, live input bar (an unseen confirm dialog was answered Yes).

### The editor and attachments

**Rewriting the editor goes through the LIVE COMPONENT, never `ctx.ui.setEditorText`.** Turning a 45-character `/tmp/pi-clipboard-<uuid>.png` into `[^image 1]` is the feature, and it must work mid-sentence, because that is where people paste (drag/drop rewrites its bytes before the editor sees them; CTRL+V cannot — pi reads the clipboard itself and calls `insertTextAtCursor` with the temp path). The public route cannot do it: `setEditorText` is `editor.setText`, which clears the paste registry and drops the caret at the end (a tail-only guard was tried and rejected — it left exactly the mid-sentence case broken), and `getEditorText` returns EXPANDED text, so a collapsed `[paste #N +M lines]` block is inlined by any round-trip. So `syncEditorPaths` walks the TUI (captured from our own widget factory — `ctx.ui.getEditorComponent` returns the factory) to the live `EditorComponent`, reads `getText` (marker form), snapshots `pastes`/`pasteCounter`/`getCursor` around the write and restores the caret via `state.cursorLine` + `setCursorCol` — replacements never add newlines, so only the column moves, by the delta of every ref substituted before it. Every reach is optional: a missing field skips the write rather than doing it badly. Two rules bound the write: the paste REGISTRY is transformed with the text and read when the pipeline scans the editor (a ref inside a collapsed paste is invisible in the marker text and very much part of the message — scanning the expanded view while writing the marker form renumbered such a ref and left the text naming the old id); and a `!bash` or `/command` buffer is never touched — pi dispatches those itself, and a rewrite made the command run on the ref (`ls: cannot access '[^image'`).

**The attachment store survives `teardown`, and its id space is PER SESSION.** Clearing it on teardown orphaned any unsubmitted `[^image N]` — no image, no def, dangling text — and because the watermark survived while the store reseeded from it, the id went to the next paste and the stale ref rebound to a different image. `rebuildFromHistory` carries editor-referenced entries back, and rebuilds the watermark from the ENTERED session alone: pi replaces the session on `/new`, `/fork`, `/resume` without restarting the process, and carrying the previous session's high-water mark let a pending `[^image 1]` (blue.png) resolve to the resumed session's `[^image 1]` (red.png) — the model described red. A collision never lets the visible ref mean the other file: with a live editor the pending ref is renumbered and the text rewritten in place; without one, the pending attachment keeps the id and history's def moves. Three rules of the same family: the rebuild is driven by the SESSION, not the UI — it runs from `session_start` (headless `pi -p --continue` attached without ever anchoring: one transcript held two files under `[^image 1]`) and again on `session_tree`/`session_compact`; the authority for "is this id taken" is HISTORY's def table, not the store (a def whose file was deleted freed its id, and the next message defined the same label for a different file); and a message pi RESTORES into the editor (`/fork`, `/tree`) carries its own footer, whose defs are re-registered before the footer is stripped — stripping them against a store that never saw those ids sent a bare `[^image 1]` and deleted the path the user could plainly read.

**A path's SHAPE is a dialect, decided once (the first Windows run).** Every scanner that recognises an image path — the typed-text rewrite (`IMAGE_PATH_RE`), the two footer-definition parsers (`adoptFooterDefs`, `rebuildFromHistory`), the paste tokenizer (`pastedImagePaths`) and `expandHome` — was a POSIX literal (`(?:~\/|\/)`), so on Windows pi's clipboard file `C:\Users\…\Temp\pi-clipboard-<uuid>.png` stayed a raw path in the prompt (the maintainer's first observation on Windows; probed: `pastedImagePaths` → `[]`, the typed regex → `null`, and `C:/Users/x.png` matched the FRAGMENT `/Users/x.png`), a drop never attached, and a `/fork`/`/resume` would have rebuilt the id space from none of the defs. `tools/library/image.ts` now owns the dialect (`WINDOWS_PATHS`, `absPathLead`, `imagePathPattern`, `defLinePattern`, `isAbsoluteOrHome`, `expandHomePath`) and every scanner builds on it; under the Windows dialect a drive letter (`C:\`, `C:/`) and a UNC prefix are absolute, `~\` is home, `file:///C:/…` drops its leading slash, and the shell-word tokenizer treats a backslash as a SEPARATOR — bare or inside double quotes (Windows Terminal drops `"C:\dir with spaces\shot.png"`); the POSIX rules would have read `C:\Users` as `C:Users`. Each function takes the dialect as a parameter defaulting to the platform, so the jiti probe exercises both on one machine and the POSIX behaviour is pinned (gnome's `'…it'\''s…'`, backslash escapes, `file://`, unpaired quotes — all unchanged). Any new path scanner in the pipeline builds on `absPathLead`, never on its own literal. Also corrected: the `IMAGE_PATH_RE` note described a left-boundary lookbehind the regex does not carry — there is none, so a path glued to a word (the caret's position at paste) still converts, and the on-disk check is the guard against prose fragments.

**Never send bytes pi's own image pipeline refuses, and never send bytes older than the file.** `resizeImage` returning null (or throwing) is a REFUSAL, exactly as pi's `processImage` reads it; keeping the raw bytes let a file with valid magic and undecodable content reach the provider, come back `400 failed to decode image`, and — the message being persisted — fail every later request in that session. A refusal attaches nothing, drops the def, says `[^image N] omitted: …` in one line and shows in the widget. Freshness: attachments are keyed by PATH and each matched ref is re-stat'ed at SUBMIT (`refreshAttachment`), because the old check ran only while the raw path was still in the text — a screenshot tool overwriting the same file re-sent the first capture for the rest of the session.

### WebFetch

**A tool's TEXT is the only thing the model reads — `details` is for rendering.** WebFetch rendered its `notes` only in the error branch, so every warning on a successful-looking fetch went nowhere (an empty extraction printed `[webfetch: ok · …]` and nothing). Empty says so; a small curated set of degradation notes rides on non-error statuses — small, because the fix for an unheard warning is not a wall of notes. **When you add a status rule, add it everywhere the status is decided** — the oracle (HTML), the non-HTML render branch and the static tier each decide, and each has been the one missed (no 401 case → a sign-in page classified `ok`; the ≥400 catch-all lived only on the non-HTML branch → a 402/451 error page with a paragraph of body was read as the article). Two cache rules of the same family: a FORCED refresh must REPLACE the cached entry (`noCache` used to bypass read and write, serving the superseded copy right back), and the in-flight dedupe must key on the render options as well as the url.

**A route handler fires ONCE, and a redirect is a second request.** Playwright calls `context.route` for the intercepted request and never again for a 30x it is allowed to follow — not after `route.continue`, not after `route.fulfill` of the 30x — so every render-tier SSRF check ran on the ENTRY url only, and a public page that 302'd to `127.0.0.1` was handed back as the article, `ok`, on `render` and on the default `auto`. The handler now owns the chain: `route.fetch({ maxRedirects: 0 })` per hop, `guardUrl` on every `Location`, a hop cap, cookies and `Authorization` dropped across an origin change, the final response fulfilled at the original request — so `finalUrl` comes from a requested→resolved map and HTML gets a `<base href>` injected. `context.request` (the PDF byte fetch) is not route-intercepted and follows its own guarded chain. Client-side vectors were always blocked; only the transport-level redirect was free.

**An IP is a number, not a string.** `isPrivateIp` matched IPv4-mapped IPv6 with a regex for the dotted form, but the WHATWG parser normalises `::ffff:127.0.0.1` to `[::ffff:7f00:1]` — which walked through every guard on every private range. The v6 test parses the eight groups and judges the embedded v4 target of v4-mapped, v4-compatible, v4-translated, NAT64 `64:ff9b::/96` and 6to4 `2002::/16` with the v4 rules; anything that does not parse is denied. Never re-introduce a textual match for an address family with many spellings of one address.

**One extractor, both tiers.** The static tier ran Readability+Turndown while the render tier ran `extract.ts`, so one URL gave two answers and the cheap one was quietly the worse: no table rule anywhere in that path (Wikipedia's S&P-500 list came back as 4 KB of prose, 0 table rows, gate `static-ok`, notes `[]`), unresolved relative hrefs, empty alts, and `structured`/`links` hard-coded empty. Both tiers run `extract` on the HTML now (verified by identical saved-content hashes). Fork the two paths again and you have re-created a tool that answers differently depending on how fast the page was.

**A cap the reader cannot see is a lie about the page.** `extract` and `pdf.ts` cut at 200 KB silently, and `capContent` computed "showing 1860 lines of 7223" from the already-capped string and saved that string — "read the rest from line 1861" pointed at a file holding a third of the page. Those caps are memory bounds now (5 M chars), announced in the content and in a note when they fire, and the saved file is the uncapped extraction; the reading limit is `truncate.ts` alone. Related: `cut` counted a partially kept line, so "resume at `keptLines + 1`" skipped that line's tail (a one-line 200 KB page said "resume at line 2"); `CutResult.partial` says when the cut landed inside a line and the text hands over a byte offset instead.

**Bytes are not UTF-8, and text is not binary.** `res.text` decodes UTF-8 unconditionally, so Shift_JIS/GBK/latin1 pages arrived as mojibake, `ok`; the static tier decodes by Content-Type charset, then the document's declaration, then UTF-8, with a windows-1252 retry only when nothing was declared and the bytes are invalid UTF-8. `text/plain` threw on that tier (a null `documentElement` for a body with no leading tag) while the render tier captured the text and called it "binary resource", `ok` — robots.txt, raw READMEs and RSS were unreadable on every tier while reporting success. Textual bodies are returned verbatim, XML/RSS goes through the extractor, only real binaries get the placeholder; the three content-type tables (`static.ts`, `render.ts`, `fetch.ts`) must stay in step.

**Anything that recognises pi's entry script must know BOTH shapes — `dist/cli.js` and `dist/bundle/cli.js` — and the scout's copy of that pattern was the third site to miss it.** pi 0.84.3 moved the bin to the bundle; pidist.ts and the dev instruments absorbed it (`(?:bundle[\\/])?`), but scout.ts's `PI_ENTRY` regex still demanded `dist/cli.js`, so the derivation failed EVERYWHERE and fell to the bare-name fallback: on Linux the scout silently ran whichever `pi` was first on PATH — precisely what the derivation exists to prevent, invisible because it worked — and on Windows, where `pi` is a `.ps1`/`.cmd` shim that `spawn()` cannot exec, every expect evaluation died with `failed to launch "pi": spawn pi ENOENT` (the maintainer's screenshot; the tool text degraded honestly: "The URLs were not evaluated; you may need to fetch them yourself"). Fixed by adding the bundle segment; demonstrated end to end on Windows by a jiti probe that sets `process.argv[1]` to the real bundle path before importing and calls `runScout` against python.org — `ok: true`, verdict and extract from the spawned pi. The rule: a new reach that parses pi's entry path copies the pattern from pidist.ts, never retypes it from memory; and a fallback that "works" on the developer's machine (bare `pi` on PATH) is how a broken derivation hides for weeks.

**A lock nobody owns is a lock nobody can break.** The daemon's `mkdir` spawn lock recorded no owner and was released only in a `finally`, which does not run when a process is killed; its window is the whole 25 s spawn-and-poll, so one Ctrl-C could wedge the render tier permanently. The lock carries its owner's pid AND that pid's `/proc/<pid>/stat` start time, and is broken on ESRCH, on a start-time mismatch (a recycled pid), or once it outlives the spawn budget by 10 s whoever holds it (an "alive" lock that could never be broken was as permanent as an unowned one — a 2-hour-old lock on a recycled pid cost every fetch 25 s, forever). On a dead pid break immediately — falling through to an age check kept a fresh orphan honoured for another 35 s. The refusal names the lock directory. And the daemon is spawned as ONE process — `process.execPath --import <file URL of tsx's loader>` — with an `error` listener: a missing or non-executable `.bin/tsx` shim was an uncaught `spawn ENOENT` that killed pi, and tsx's CLI (the previous shape) spawns a second node for the script, whose freshly allocated console Windows 11 hosted as a visible Windows Terminal window for the daemon's whole lifetime (the maintainer's screenshot; reproduced as two new console-host processes per spawn, gone with the single-process shape).

**A deadline race clears its timer, or the process outlives its work (the first Windows pass).** `npm run fetch -- <url> --tier render` printed its report at t≈5 s and returned at t≈47 s, every time. Not the network and not Windows: `NODE_OPTIONS=--require <preload>` dumping `process.getActiveResourcesInfo()` from inside the runner showed `{"Timeout":2}` as the ONLY live resources from t+15 s to the exit at +46 s — the two `Promise.race([work, new Promise(r => setTimeout(r, deadline - now))])` sites in `render.ts` (the API-body wait and `page.content()`), whose timers stay armed after the work wins and hold the event loop for the rest of the 45 s budget. `withDeadline` (render.ts) is the one race helper now and clears its timer in `finally`; the CLI exits when its report is done (measured after: the runner exits at ~t+6 s). Inside pi the process lives on anyway, so the tool never showed it; the CLI and any headless pi that waits for a natural exit did. Two instrument lessons from the same hour: PowerShell's `Start-Process -Wait` waits for the DESCENDANT tree, so a CLI that spawns the detached daemon blocks it until the daemon's idle exit (read as a five-minute hang before the preload settled it); and `| Select-Object -First N` on a native command closes the pipe early and reports the exit code as -1.
